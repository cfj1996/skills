# API 契约阶段

## 评审前置门禁与正式来源搜索顺序

生成首轮评审卡前，按以下顺序完成 API 证据闭环：

1. 建立消费需求清单。把交付单元拆到 API 需求一致的具体消费点，例如页面内容区、应用壳层、路由守卫、权限入口或跨页面会话逻辑。
2. 为每个消费需求记录 `required` 或 `none`。`none` 必须带不适用证据；`required` 必须继续执行正式来源搜索。
3. 按项目规范声明的入口搜索正式来源；未指定时依序检查 YApi、OpenAPI、Query Contract、`defineQuery`，再检查项目规范声明的其他正式契约入口。
4. 形成接口事实清单，记录已搜索来源、当前可验证契约事实、能力归属、运行时范围和本次交付关系。
5. 最后判断复用现有接口，或进入缺少正式契约的 Mock / 后续 Draft 分支。

消费需求未全部分类、任一 `required` 需求未完成正式来源搜索，或接口事实清单缺少来源证据时，API 设计维度保持阻塞。

## 归属与关系

API 的能力归属由业务能力确定，不由页面、组件或当前交付模块确定。运行时范围说明能力在请求、页面、应用、会话或跨页面生命周期中的有效范围。本次交付关系只使用：

- `直接消费`：本次交付中的具体消费点直接调用或绑定该能力。
- `继承依赖`：能力由应用初始化、路由、会话或其他上层机制提供，本次交付只依赖其结果。
- `契约变更`：本次交付确实修改或新增接口契约。

“不涉及接口”只用于一个有证据的具体消费需求，不是 API 状态，也不得提升为页面或模块的接口归属结论。不同消费点结论不一致时，交付单元只汇总客观数量，不生成单一 API 结论。

评审只记录 API 业务目的、触发、读写、请求响应语义和关键状态。不得猜 method、URL、字段、参数位置、类型、必填、可空、枚举、默认值、包装结构、媒体类型、状态码或 Schema。

## reviewing 阶段

`reviewing-page-delivery` 不得生成 Draft OpenAPI，也不得将交付单元设为可实施。它仅评审、呈现冲突并在用户确认更新 Plan 后回写评审范围内的事实。

## 后续 planning 阶段

后续 planning 只有同时满足下列门禁才可生成 Draft：

1. 对应消费需求为 `required`，已确认确实没有正式契约，且业务语义已经确认。
2. method、URL、参数位置、请求与响应媒体类型、状态码、安全要求及 Schema 等机器事实已全部确认。
3. Draft OpenAPI 位置、命名和编号已由适用项目 `AGENTS.md` 或其委托规范唯一确认；不得使用插件默认目录。
4. Draft operation、消费功能点和 Plan API 编号已建立双向关联；只有本次存在实施工作时才关联任务。

任一门禁缺失或冲突时，仅报告缺口和候选证据并等待用户确认，不生成 Draft。
