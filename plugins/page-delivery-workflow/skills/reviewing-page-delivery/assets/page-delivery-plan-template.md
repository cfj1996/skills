# 页面交付 Plan

> 一个页面或一个内聚功能模块对应一个 Plan。仅在适用项目 `AGENTS.md` 已确认产物位置规则且用户确认更新 Plan 后创建或更新此文件。

## 交付单元

- 交付单元类型：页面/模块
- `deliveryUnit.kind`：`page` 或 `module`
- 交付单元键：`<稳定键>`
- 交付单元名称：`<项目确认的名称>`
- 产物位置规则来源：`<适用 AGENTS.md 或其委托规范>`
- Plan 内容指纹：`<写入前读取的指纹>`
- 产物位置规则指纹：`<适用规则的指纹>`

模块须有可独立实施、对接和验收的边界；弱关联页面或跨业务域内容应拆分为多个 Plan。

## 消费需求与运行时依赖

- `F-001`：消费点：`<页面内容区/应用壳层/路由守卫/权限入口/跨页面逻辑>`；API 需求：`<required/none>`；能力归属：`<业务能力域或不适用>`；运行时范围：`<request/page/application/session/cross-page 或不适用>`；判断证据：`<E-001>`

同一功能内不同消费点的 API 需求不一致时必须拆分功能点。`none` 只表示该具体消费点“不涉及接口”，不得提升为页面或模块结论。

## 组件与功能实现方案

- `DESIGN-001` / `F-001`；关联：`<UI-001, API-001, E-001>`
  - 一句话实施方案：<面向当前项目的具体方案>
  - 怎么实现：<项目证据确认的组件、组合方式、复用边界和代码落点>
  - 怎么联动：<触发条件 → 判断/动作 → 状态变化 → 页面反馈>
  - 数据怎么走：<状态归属、API 消费点、参数/返回映射、请求时机和错误反馈；无 API 时写明本地数据流>
  - 怎么验收：<三至五项最容易跑偏的关键场景>
  - 实现依据：`<E-001, E-002>`
  - `implementationPlan.status`：`ready`

仅将评审确认且证据完整的 `ready` 实施契约写入 Plan。组件体系、代码落点、
功能联动或数据流仍有缺口时保持评审“阻塞”，不得用“使用弹框”“增加筛选”
“完善表单”等通用描述代替具体实现方案。

## API 与 Mock

- `API-001`：<业务目的、契约来源和已确认事实>；能力归属：`<业务能力域>`；运行时范围：`<request/page/application/session/cross-page>`；本次交付关系：`<直接消费/继承依赖/契约变更>`；状态：`<证据确认后从接口固定状态集合选择>`；正式来源搜索证据：`<E-001>`；双向关联功能：`<F-001>`；可选双向关联任务：`<T-001>`
- `MOCK-001`：<Mock 场景或不适用原因>；关联：`<API-001, UI-001>`

不存在接口实体时不得创建状态为“不涉及接口”的 API 记录。`required` 需求必须先完成正式来源搜索；找到正式契约时复用，未找到时记录“正式契约缺失”，再评审 Mock 或后续 Draft。`none` 必须有 API 判断证据。

`继承依赖`只记录当前消费点依赖的现有能力；本次没有接入或修改工作时不得制造实施任务。

## 回写前冲突检查

重新读取 Plan 并比较 Plan 内容指纹及产物位置规则指纹。`validate-page-plan.js` 校验消费需求 API 判断、正式来源证据、API 能力归属、运行时范围、本次交付关系，以及所有已声明的功能点↔API、功能点↔任务、API↔任务双向关联。`继承依赖`未声明实施任务时不要求 API↔任务关联。任一冲突或指纹、稳定编号、状态变化均停止写入、展示冲突并等待用户确认；不得部分回写。

不得使用隐藏 JSON、自动生成 Draft、从 Markdown 解析、插件默认 Plan 目录或插件默认 Draft 目录。
