# 页面交付 Plan

> 一个页面或一个内聚功能模块对应一个 Plan。仅在适用项目 `AGENTS.md` 已确认产物位置规则且用户确认更新 Plan 后创建或更新此文件。

## 交付单元

- 交付单元类型：页面/模块
- `deliveryUnit.kind`：`page` 或 `module`
- 交付单元键：`<稳定键>`
- 交付单元名称：`<项目确认的名称>`
- 产物位置规则来源：`<适用 AGENTS.md 或其委托规范>`
- Plan 内容指纹：`<写入前读取的指纹>`

模块须有可独立实施、对接和验收的边界；弱关联页面或跨业务域内容应拆分为多个 Plan。

## 功能模块与行为契约

每个模块使用以下结构，子模块沿用同一结构；父模块和子模块均使用稳定编号。
Markdown 与面板使用同一模块内容，临时规范化模型使用 `schemaVersion=3`、
`features[].module` 与独立的 `features[].reviewConclusion`，不把 JSON 写进文档。

- `F-001`：<模块名称>；父模块：`<稳定编号或无>`；模块版本：`<正整数>`；功能状态：`待实施`；需求结论：`<未评审/已确认/待修改/阻塞/不适用>`；双向关联：`<API-001, T-001>`；关联：`<UI-001, AC-001>`
  - 职责与范围：<本模块解决什么问题，包含和排除什么>
  - 输入：<触发条件、前置条件、所需数据与参数>
  - 输出：<用户可观察到的展示、事件、状态变化或业务结果>
  - 行为规则：<正常、边界与异常条件下应有的表现>
  - 验收例子：`<模块内唯一编号>`；给定 <输入>；当 <触发>；则 <约定输出>
  - 待确认问题：`<模块内唯一编号>`；问题：<具体缺口>；影响：<受影响行为>；责任方：`<user/agent>`；建议：<推荐选项或查证动作>
  - 本次变更：`<added/modified/removed/unchanged>`；说明：<具体差异和影响>
  - 内部实现：<对应下方 DESIGN-001；尚未知的事实如实保留缺口>

无需将布局、接口、权限重复拆成评审模块；以下技术记录作为模块的实现依据与后台检查结果。

## 消费需求与运行时依赖

模块汇总 API 需求：`<required/none/unknown>`。内部各消费点分别判断，模块的 required 不代表所有消费点均需接口；unknown 记录实现缺口，已有事实保持原值。

- `F-001`：消费点：`<页面内容区/应用壳层/路由守卫/权限入口/跨页面逻辑>`；API 需求：`<required/none>`；能力归属：`<业务能力域或不适用>`；运行时范围：`<request/page/application/session/cross-page 或不适用>`；判断证据：`<E-001>`

同一模块内不同消费点的 API 需求不一致时，分别保存消费事实并关联模块；不因此拆出用户必须确认的 API 模块。`none` 只表示该具体消费点“不涉及接口”，不得提升为页面或模块结论。

## 组件与功能实现方案

- `DESIGN-001` / `F-001`；关联：`<UI-001, API-001, E-001>`
  - 一句话实施方案：<面向当前项目的具体方案>
  - 怎么实现：<项目证据确认的组件、组合方式、复用边界和代码落点>
  - 怎么联动：<触发条件 → 判断/动作 → 状态变化 → 页面反馈>
  - 数据怎么走：<状态归属、API 消费点、参数/返回映射、请求时机和错误反馈；无 API 时写明本地数据流>
  - 怎么验收：<三至五项最容易跑偏的关键场景>
  - 实现依据：`<E-001, E-002>`
  - `implementationPlan.status`：`<ready/blocked>`
  - 实现缺口 `blockers`：<缺少什么、影响什么、后续如何补齐；ready 时为空>

需求结论与实现准备度分别保存。需求已确认但组件体系、代码落点、功能联动或
数据流尚未确定时，阶段 Plan 保留 `blocked` 方案及具体缺口，不强制需求结论
变为“阻塞”，不得标为可实施。`ready` 实施契约必须证据完整；不得用“使用弹框”
“增加筛选”“完善表单”等通用描述替代具体方案。适用模块的 `questions` 都是尚未解决
事项；进入可实施及后续状态前必须为空，并满足需求确认、实现 ready 和其余证据门禁。
问题已有建议不等于已解决；阶段 Plan 可以继续保存它们。

## 遗留问题

- `ISSUE-001`：<阻塞、待确认或冲突>；影响：<具体模块与行为>；责任方：`<user/agent>`；建议：<决定或查证动作>；关联：`<稳定编号>`

已确认需求、待修改需求和未决事项可以一同阶段保存。后续对话补充按同一稳定编号

## 回写前冲突检查

重新读取 Plan 并比较 Plan 内容指纹及产物位置规则指纹。`validate-page-plan.js` 校验模块层级、版本、行为例子、独立需求结论和实现准备度，以及消费需求 API 判断、正式来源证据、API 能力归属、运行时范围、本次交付关系，以及所有已声明的功能点↔API、功能点↔任务、API↔任务双向关联。`继承依赖`未声明实施任务时不要求 API↔任务关联。任一冲突或指纹、稳定编号、状态变化均停止写入、展示冲突并等待用户确认；不得部分回写。用户确认后先显示“已确认，待保存”；Agent 实际写入并读回核对后调用 `markPlanSaved`，才显示“已保存”。

不得使用隐藏 JSON、自动生成 Draft、从 Markdown 解析、插件默认 Plan 目录或插件默认 Draft 目录。
