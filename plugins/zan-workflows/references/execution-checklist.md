# 确定清单与执行清单

Bug 修复、小需求和大需求统一保留六列表格。清单是本轮范围、授权、依赖和
执行结果的统一索引；编号详情、实际引用的 Plan 内容和写入事项共同构成确认
内容，不能只确认摘要后忽略正式约定。小改动直接用对话说明，不为提供链接
创建文档或 Task。

## 限制与确认说明

面向中文用户时，限制、上线门禁、确认要求、阻塞原因和清理约束均使用完整
中文说明；从英文技能、引用规则、校验器或脚本结果取得的原因也先解释为中文。
说明“本次为什么需要确认”并链接出处时，同样引用该技能的中文确认条款；
不得因要求说明来源而照抄英文句子。用户未明确要求核对英文原文时，不附英文
规则引文；机器字段、错误码等准确标识仍按下文保留。

- 只解释本轮实际适用的限制，指出触发事实、暂停的具体操作、缺少的证据或
  授权，以及满足什么条件后可以继续。尚未核实的情况明确写“待核实”，不把
  网络失败推断为权限不足，不把缺少证据说成已确认违规。
- 机器字段、枚举、代码、命令、路径和链接保持原样；展示 `BLOCKED`、
  `AWAITING_MERGE` 等状态时配上中文含义。首次出现 Mock 时说明其为模拟数据
  或服务，后续沿用 Mock；区分测试环境授权、默认分支交付和正式发布。
- 确认提示说明准确对象、操作、目的与当前缺少的授权。仅在原规则要求且现有
  授权未覆盖时询问；已完整展示并确认的相同范围继续复用，不因阶段切换或
  改用中文重新确认。禁止事项不能通过普通确认解除。
- 已完成效果、当前阻塞和后续条件分别说明；等待人工合并、可选清理待确认
  不能笼统报告为整个流程失败。中文解释不得放宽或增加原有门禁、证据及权限。

## 名称与阶段

同一份清单随确认状态命名，不维护两份内容或新增运行状态字段：

- 初次展示、或实质调整后等待确认时，标题为 `## 确定清单`。
- 用户确认当前完整内容后，称为 `执行清单`，作为已授权实施依据。可简短
  说明“已确认，按执行清单执行”，无须仅为改名再重印或再问一次。
- 执行中实质调整时，暂停受影响写入，展示更新后的完整 `确定清单`；
  新确认后再转为执行清单。原已完成效果保留并标明不重复执行。
- 最终报告称为 `执行结果`，只包含真实完成范围、验证/评审和遗留。

## 围绕同一清单编排

`fixing-bug` 和 `developing-requirement` 共用此主线。各技能完成清单中对应的
工作，不重新定义整轮范围或另开一套确认。沿用 `TapdWorkDefinition`、
`ReviewedChange`、`SubmissionPlan` 及交付结果作为清单的结构化执行视图和证据；
不直接执行 Markdown，不增加总计划、运行台账、编号或状态机。

编排持有当前完整清单、实际引用内容、真实确认来源、各仓验证/评审及已完成
回执。下游仅接收对应范围和所需事实，结果关联回同一工作项、canonical
repo/origin/fixed_branch，不能按表格行号配对。完成情况由已有结果投影，
不手填通过标志，不往“需求待确认”列塞待办或审批进度。

### 节点处置

下表是内部执行规则，不改变用户清单的六列，也不要求每次重印本表。

| 节点 | 次数与触发条件 | 保留、合并或移除 |
| --- | --- | --- |
| 条目、规则和上下文收集 | 同一 Bug/Story 一次；各仓补自己的约束 | 合批独立只读查询，复用有效内容；移除换技能后的整套重读/路由 |
| 根因或需求语义、验收 | 对本轮准确范围检查 | 保留真实分析；已有完整且有效的 brief/Plan 复核复用，不重复 SCOPE_REVIEW |
| 历史引入证据 | Bug 有直接线索时窄查 | 未知如实记录，不为归责阻止明确修复，不扩展无关历史调查 |
| Task/正式 Plan/估时/排期 | 用户明确请求、需求独立页面/跨仓责任的实际协调或已有正式约定时 | 按准备分流核对完整范围，不能因静态页/Mock 降级；普通小改动不强建；保留真实 ID/owner/工时、估算独立评审及 Plan 关联/保存门禁；日期只按请求处理 |
| 完整清单确认 | 当前完整方案一次 | 覆盖本轮准确操作与终点；移除阶段切换、派发或机械补链引起的重复确认 |
| 固定分支与工作位置 | 每个实际仓库一次准备，写前刷新 | 同仓子项目共用分支操作；移除第二遍完整准备，保留 refs/祖先关系及无关改动检查 |
| 准备定义校验 | 主代理按真实证据和适用 helper 规范化 | 移除常规独立准备 validator；实质歧义才独立复核，缺证据/冲突仍 PENDING/BLOCKED |
| Bug 状态/处理人与开始记录 | 全 Bug 一次，源码前准确写入/读回 | 共享给各仓；常规字段匹配由主代理/helper 校验，不再单独派 PRE_STATUS_WRITE；Story/Task 不执行此节点 |
| 实施 | 按真实仓库、Task/步骤与依赖 | 小活主代理完成；只并行就绪且写入/资源独立的工作，不按 Task 数重复派整套流程 |
| 行为验证与项目检查 | 按项目实际配置、风险和验收 | 依照项目检查选择矩阵，共用检查一次；无配置不补装，既有错误按实际阻塞判断；全量检查按必要性触发 |
| 独立代码评审 | 覆盖每个变更仓库及跨仓验收 | 保留；复用仍匹配内容/依赖配置/验收/环境的评审，阶段变化或同内容新 SHA 不重审代码 |
| 前置依赖产出 | 仅清单明确列出并授权的必要包/测试服务 | 提供方自身评审和精确交付门禁通过后先产出，避免全仓验收与依赖发布互相等待；详见下节 |
| 完成记录与整轮实施交接 | 全部必要仓库及跨仓验收通过后 | Bug 共享完成记录一次；需求只报告所选范围，不自动标父需求/Task done；局部通过不冒充完整 REVIEWED |
| 准确技术 PLAN 与计划评审 | 按当前清单和实际实现结果导出 | 保留适用检查/独立评审，复用未变的已审内容；匹配原确认就连续 EXECUTE，不另问一次 |
| 提交/推送/MR/合并与所选构建 | 每个实际交付仓库，按真实依赖 | 用既有 helper 连续核对、执行、读回；移除每个动作之间的模型接力和已完成效果重放 |
| Wiki/回链与登记 | 同一归属 Story/Bug 汇总一次 | 全部必要交付门禁满足后处理；NO_WIKI 不查询文档；未选操作不进入流程 |
| 上线 | 明确授权的本轮终点 | 复用原分支和有效交付证据，只查当前增量/上线条件；未涉及库不进入包发布，已满足版本不重发 |
| 收尾与清理 | 相关交付结束后 | 保留工作区要求的只读检查/提醒，结果与业务交付分开；删除仍需准确单独授权，不把可选清理当交付失败 |
| 中断、异常与后续增量 | 核实真实效果后 | 只补缺失/失效节点及其依赖，不重启全流程；UNKNOWN 不当作未执行，不自动重试写入 |

### 前置依赖产出与整体完成

多系统可以没有公共库，也可以有包、接口或测试服务依赖。沿用原 brief/Plan
的步骤/依赖，不增加另一种固定流水线。先执行当前就绪且已授权的节点；
包真实可用后再消费，服务具备所需能力后再联调，独立工作不用等待无关节点。

若消费升级或跨仓验收必须先有新包/测试服务，不能反过来要求整轮 REVIEWED
后才允许产出该依赖。确定清单须事先展示前置节点的准确项目/原分支/目标、
Jenkins Job、环境/通道、目的、依赖顺序和验证局限，并获得对应明确授权。
提供方本身的代码验证、独立评审和精确 Git/Mock/CI/发布门禁通过后，编排
可用原子 Git 与 `running-release` 能力完成这个已授权节点；实施能力本身不
提交或发布。普通“开发/提测”不授权未展示的提前局部交付，也不推导生产服务
部署、正式包或清理权限。正式包仍须自己的完整发布门禁与准确显式授权。
明确“先不要提交/推送”“只实施”等限制优先；不能以验证依赖为由越过限制。
需要调整这些边界时先展示完整当前清单并补授权，否则保留依赖缺口。

此时只保留提供方真实进展，不交出部分仓的可提测 `ReviewedChange` 集合，
不写全 Bug 完成记录、共享提测 Wiki 或登记待测试，不让正式提测接受缺仓输入。
包须真实可获取且版本/内容匹配；服务须核实部署源码及后续联调所需能力。
队列接受、构建成功不单独证明依赖已就绪，跨仓真实验收仍待后续完成。
依赖就绪后续接原清单/分支/Task/Plan，最后按全仓门禁完成整轮交接。
失败/UNKNOWN 停止依赖动作，核实实际效果后只按原授权和正常门禁续接；
不得借此前置节点绕过会话写屏障或重放不明写入。

### 已完成交付的复用

进入正式提测或后续节点时，先核对同一执行清单中已完成的前置 Git/服务部署/
包发布回执，匹配当前仓库、实际目标包含关系与交付源码、Job、环境/通道、
参数和目的，并读回当前需要的真实部署/包内容。仍满足对应门禁就引用原回执，
不再次提交、合并、触发构建或发包，不重新包装为一次新操作。

原 `BUILD_SUBMITTED` 只证明准确构建已提交；`DEPLOYED` 保留真实部署及源码
证明；原 `RELEASED` 只满足对应工具仓的包发布门禁，并保留实际包版本/内容。
包发布不能代替消费仓部署，构建成功不能单独代替服务可用。计算版本包的源码
SHA 仍不是包版本。前置可用性与完整跨仓验收分别核实。

源码/目标/参数或实际内容漂移时，刷新受影响事实和计划，不能直接沿用旧成功。
仅执行当前授权覆盖且确实缺失的动作；UNKNOWN 先可靠消歧，不自动重放。
用户明确要求重新部署/发包时，保留为本次准确的新操作，不能用旧回执抵消。

### 下一步与失效范围

每次能力返回后，编排核对现有结果：已验证完成的保留；未完成但原授权覆盖、
依赖就绪且必要证据有效的继续；缺材料先只读补齐；真实业务取舍再请求用户。
只将稳定、已授权的一段确定性操作交给同一受控调用组合既有 helper，逐步
等待真实回执再释放下游。异常立即返回，不预填未来成功，也不声称已有新的
端到端执行引擎。独立代码评审不由清单确认、开发者自检或来源不明的标志代替。

源码/相关依赖配置/验收变化只补受影响验证与评审；目标 ref 漂移刷新对应交付
计划和必要目标差异检查；Wiki 变化只刷新该页补丁；评论失败只核实/补原记录。
操作集、关键方案、业务范围、分支目标、环境通道、人员等实质变化仍重新展示
完整当前确定清单，仅为变化补授权，保留已完成效果。技术 PLAN、真实用户
确认和执行成功分别判断；原仅实施授权不能覆盖后来单独提测或上线。

上下文压缩/续接保留当前清单及实际引用内容、真实确认来源、各仓最新绑定与
验证/评审/回执、剩余步骤和阻塞。长日志按需读取，不反复倾倒原始 JSON。
材料不足时从原对话或真实系统只读核实，不凭摘要恢复授权或重放写入；
不新增本地状态、恢复文件或任务台账。
稳定事实按原引用复用；每次只刷新会变化的 refs、状态、权限、正文和所需当前
证据。阶段返回以本次结果、失效项和下一就绪节点为主，不重传完整规则或原始日志。

## 执行清单的确认复用

仅由 `fixing-bug` 或 `developing-requirement` 编排且携带完整执行清单及真实
人类确认来源时，下游技能复用这次授权。首次清单一次说明本轮范围、固定
项目/分支、交付终点和实际操作：必要 Task/Plan 写入、修复记录、提交/推送、
MR 创建/复用及合并、测试构建/部署、Wiki/回链、适用 TAPD 状态/测试版本，
以及选定合并的自动冲突处理。未选择的生产发布、删除或其它项目不在授权内。

- 每个阶段先将当前准确操作计划与执行清单逐项核对。已覆盖且语义未变就
  连续执行，不因更换技能、进入提测阶段、工具的 PLAN 返回
  `AWAITING_CONFIRMATION` 或代码已完成而再问用户。PLAN/预检仍只读，
  编排核对授权后才能调用 EXECUTE；不跳过验证、前置条件和写后读回。
- 提交/MR/构建/页面 ID、经审查的本轮提交 SHA、实际验证结果，以及按已确认
  模板和事实生成的 Wiki 正文/最小补丁、测试版本文字可确定性补全。填充规则
  与用途需已包含在清单中；不伪造未来成功，不改变业务范围、人员、目标、
  发布通道或其它人的 Wiki 内容。补全后仍生成准确参数/正文/指纹并验证，
  不能把模板占位符直接交给写入工具。
- 缺失或变化的事实先自行只读查证。当前技术绑定过期仍须拦截本次写入；
  若查明只是同一已授权操作的技术补全，可刷新计划继续，不凭旧 SHA/正文
  哈希强写。新增项目/范围/操作、改变目标/关键方案/人员或需要业务取舍时，
  展示变化和完整当前确定清单，仅为这些变化补充授权，保留已完成效果。
- 单个技能独立执行时，仍按其原有确认流程展示具体计划并等待人类确认。
  不因该技能也被主流程使用就自动执行；普通“修复/提测”、旧实施授权、
  Agent 摘要或 `confirmed=true` 都不是完整授权证据。独立计划自身已有
  匹配确认时可复用，不重复询问同一操作；只读技能不新增审批，原技能允许
  以字段完整的明确操作请求作为确认时仍沿用该规则。
- 普通阶段通过简短进度继续推进，不以“是否继续下一步”结束。最终输出
  执行结果和下一步建议，不例行追加提交/合并/部署或清理确认。确实缺少
  用户信息、权限或业务决定才暂停；工具失败、未知写入或验证未通过不能
  伪装成功，也不能用重复确认替代查证。

这些依据留在现有内存交接和当前对话中，不新增台账、状态文件或运行模型。
跨会话续接须核实真实清单、人类确认及已完成效果，不能仅凭旧总结重放写入。

## 确认前准备

确认是本轮方案准备的最后一步。范围摘要、代码入口已找到或只读分支预检
返回，都不表示完整清单已经就绪；Agent 能自行只读核实的内容应继续完成：

1. 分开解析业务范围与交付终点。“只开发 B 端相关功能”“仅改前端”或
   “只做所选 Task”不表示不提测；普通开发仍默认合并、Wiki、测试构建。
   该默认不包含携带 Mock 到测试环境，含 Mock 必须满足专门的明确授权门禁。
   “仅开发验证”“不提测”才限制终点；单独关闭某项只影响该项。
2. 核实全部本轮项目、准确分支/基准和工作位置，以及范围、方案、验收、
   真实缺口。必要 Task/Plan 的拟写内容/差异和目标须可审阅；已有 Task
   只读复用不因此强制生成正式 Plan，Plan 也不提前保存。
   涉及新建/重估 Task 时，先按
   [增量工时规则](../skills/breaking-down-requirement/references/effort-estimation.md)
   核实范围、复用和新增工作，并完成独立评审及完整校验；准确保留旧工时不重复估算。
   这些检查在原确认前完成，不增加一次用户审批，对外仍只显示一个小时数。
3. 对选定合并查明实际 dev/develop；对选定部署取得准确环境、Jenkins
   Job 名称/URL及必要参数、涉及发包时的版本/通道；对选定 Wiki 读取
   规范模板并准备本次项目/分支预览。复用已有事实，不触发任何交付写入。
   尚未实施时不能调用要求 `ReviewedChange` 的正式提测 PLAN 来完成此步；
   该计划仍在评审通过后生成，只读准备不伪造提交、评审或构建结果。
4. 对照下方完整模板检查章节、顺序和本次内容。未选择的能力不查询；
   缺少可自行查证的内容就继续查证；业务问题进入需求待确认，外部条件进入外部数据与依赖，按实际受影响阶段保留阻塞。

通过上述准备后才发出一次执行确认。保留首次完整清单的确认门禁，不能
把普通开发请求当成未展示的合并、部署或外部写入授权。

## 直接提测与先人工检查

需求清单默认“直接提测：是”，沿用 SUBMIT，实施、验证和独立评审通过后
按已确认范围继续交付。普通修复仍沿用相同默认，分项关闭选择保持有效。
用户明确“先完成代码，我检查后再提测”“先不要提交/推送”或“暂不直接提测”
时沿用 IMPLEMENT，显示“直接提测：否”；本轮合并、Wiki、构建分别显示
否/不需要及本轮不执行的依据，不查询 Jenkins/Wiki 或展示空 Wiki 预览。
这不关闭实施必需且已获授权的 Task/Plan、Bug 状态/修复记录。

人工检查后可独立调用 `$submitting-for-test`，使用
[直接提测清单](../skills/submitting-for-test/references/direct-submission.md)。
它复用已完成实现及原分支，核实人工改动与验证/评审，只确认本轮准确交付
操作；不重新展示尚未执行的实施方案。“直接提测”不表示“不构建”，不能
自动选择 SKIP；仅实施的旧清单也不能授权新的提交、推送、MR、Wiki 和构建。

## 展示顺序与语言

按“简短概览 → TAPD 任务表（有任务时）→ 六列表格 → 外部数据与依赖 → Mock 范围与测试授权（有 Mock 时）→ 必要的编号备注 → TAPD 更新与修复
记录/需求写入事项 → 合并与测试环境 → 所选 Wiki 的模板预览 → 一次执行确认”展示。

标题下依次显示：

- **执行项目名称：** 支持多个，逐项列出已核实的业务项目/子项目名称；
  同名项目附简短代码标识帮助对应主表，不凭关联/依赖扩大本轮修改范围。
- **关联缺陷/关联需求：** 按实际类型显示准确 Bug/父 Story 编号、标题和链接，
  不再另印同义的“执行事项”。Task 输入保留真实父需求，本轮 Task 放入下面的任务表。
- **本轮任务（有任务时）：** 可简述所选数量，不在概览重复任务标题和链接。
- **本轮交付：** 简写仅开发验证、提测或上线，不重复固定开发步骤。

有任务时先展示 `### TAPD 任务`，再用 `### 执行内容` 引出六列表格。顶部只做概览，不重复分支长名、验证
安排、TAPD 字段核验过程；主表项目、分支和各自交付边界保持完整。

- 用中文说明本轮做到哪一步及实际风险。不设置工作规模/风险等级标签，
  `IMPLEMENT|SUBMIT|GO_LIVE` 等终点值只用于内部交接，不打印在清单中。
  确有风险就写具体
  影响和验证重点，例如“涉及金额计算，增加金额准确性回归”。
- 不向用户堆原始状态码、payload、字段核验过程、完整 SHA 或内部指纹。
  这些证据仍须准确读取、保存于当前内存交接并在写前复核；展示简化不
  降低分支、身份、状态、任务或授权门禁。用户询问或事实冲突需要解释时
  再提供相关技术依据。
- 表内已说明的项目、分支、范围和验证不再另列“分支安排”“验证安排”
  重复一遍。需要展开的是四项内容的增量详情，按下面的编号规则关联。

## TAPD 任务表

本轮有选定 Task 时，即使只有一项，也在执行内容前展示且只保留三列：

| 序号 | 标题 | 工时 |
| --- | --- | --- |
| #F01 | 【新建】〈拟创建标题〉 | 〈小时数〉 小时 |
| #F02 | 【复用】〈真实 Task 标题及链接〉 | 〈小时数〉 小时 |
| #F03 | 【调整】〈真实 Task 标题及链接〉 | 〈小时数〉 小时 |

同一 Task 只列一次，后续交付范围、方案、验收、需求待确认和写入事项直接用
`#F01`、`#F02` 引用，不重印标题/URL 或在 `#01` 下再建一张任务明细表。
具体范围、负责人/变更、依赖和验收仍须在对应主表、必要备注/Plan 或实际
写入事项中完整可审阅；三列表只是索引，不省略授权所需信息。
按 [准备分流](adaptive-workflow.md#需要-task-与正式-plan-时) 需要任务时，首次用于实施的
完整确定清单就包含真实/拟建 Task、核实负责人及经校准和独立评审的最终小时数，
不先以“无 Task”省略后再补建。缺项则明确为草稿，不发起执行确认。
页面开发与正式接口对接有独立交付时按阶段拆分；仅选 Mock 的未来接入候选
在原 Plan/外部依赖说明，不混入当前任务的工时或完成范围。

- 标题前固定显示本轮 Task 操作：【新建】对应 CREATE、【复用】对应 REUSE、
  【调整】对应 UPDATE；按真实提案或只读复用事实判断，不为补标签构造正式
  TaskBreakdown。开发代码不等于调整 TAPD 任务字段，标签也不表示任务状态或
  分支操作。前缀仅用于展示，不加入实际 name。若只调整人员/描述等、工时
  未变，工时格仍显示同一数值，不增加标签或变更箭头。
- 确认后本轮操作标签和序号保留。获准创建/调整并读回后补真实链接，并在
  写入事项注明“已完成，本轮不重复”；不改成“复用”而隐藏本轮已发生操作。
  工时写入已读回后仍显示同一数值，不添加“已写入”等工时标签。
- 序号在整份清单跨项目唯一；确认前后保持不变，新增任务追加编号，不因
  排序或项目分组重编号。移出任务不复用其编号，更新摘要并清理当前无效引用。
- `#F01` 是清单阅读索引，与详情 `#01` 分开，也不是 TAPD ID、Plan 的 `F-001`
  功能编号或任务 key。沿用真实 ID/稳定 key、`records`、`tapdTaskKey` 在原内存
  交接中的对应事实；不新增运行模型字段，不将阅读序号写入 TAPD/JSON 代替身份。
  不假设聊天锚点可点击；可点击链接只来自已核实的 Task 标题链接。
- 工时格只显示一个 `N 小时`，具体取值见下一节；不增加列或另一张
  工时表。未知值如实展示，需写入或已有正式 Task/Plan 门禁时，仍须满足其
  准确估时/读回要求，不能用表格占位解除阻塞。
- 拟创建任务不伪造 ID/链接；获准创建并准确读回后，在同一阅读序号下补
  真实标题链接，不能借机械补链改变范围、工时或批准的任务身份。
- 经准备分流确认无需 Task 时省略整个任务表，不为展示而建 Task/Plan；只显示本轮选定任务，
  其他任务可以在依赖说明引用，但不因同父需求自动纳入实施范围。
  未列入任务表的外部依赖不分配本轮 `#F` 编号，注明其真实来源与仅依赖边界。

## 工时口径

- 对话、确定/执行清单及 Plan 的任务工时都只显示一个 `N 小时`。不附加
  “预估”“原预估”“拟预估”“本轮剩余”“执行工时”等标签，不展示多组时间、
  旧值到新值箭头、计算构成或系数；用户明确询问时再解释对应事实。
- CREATE/UPDATE 取本轮确认的最终任务工时；REUSE 取已核实的 Task 工时。
  只改人员/描述时沿用工时。字段已读回为空显示“未填写”，无法核实显示
  “待核实”，不补零，也不拿内部剩余预测替代任务字段。
- 工时调整用任务标题的【调整】及写入事项说明“按表中工时更新”；工时旧/新值
  仍在内部提案、确认指纹及写前核对中准确绑定，不为简化展示省略真实写入动作。
  其他字段的必要变更说明保持可审阅。写后准确读回仍须与表中数值一致。
- 内部可按当前范围、已验证完成部分和剩余步骤预测后续投入。续修不把完整任务
  工时直接当作剩余，也不只按已花时间、进度或状态推算；不重复折算既有最终值。
  这些预测不默认展示在任务表、进度更新、备注或 Plan 正文中，不自动回写 TAPD。

只在三列任务列表的对应行展示工时；列表后直接进入六列执行内容，不追加
工时合计、小计、缺项数量统计或独立说明区块。同一 Task 跨项目只列一次。
内部预测不新增模型字段或 JSON 台账，不替换 Proposal/records/MCP effort，
不自动修改旧 Plan、填报实际工时或触发日期排期。预测未核实本身不增加开工
门禁；真实范围/实施缺口仍按原规则处理。单纯内部预测更新无需重做 Task 确认；
范围、人员、任务工时或拟写入字段变化仍展示完整确定清单并确认。

## 六列主表

按实际项目/仓库/固定分支展开，单项目也保留表格。相同仓库和分支的子项目
可以合并一行，但必须列明全部子项目及各自范围，分支操作只执行一次。
多个 Bug 保持输入顺序，
在项目格附准确 Bug 编号/链接；项目名和仓库须能唯一识别。

| 项目 | 分支 | 交付范围 | 实施方案 | 验收标准 | 需求待确认 |
| --- | --- | --- | --- | --- | --- |
| `<项目/子项目；准确条目链接>` | `<从已核实基准 ref 新建/复用完整目标分支>` | `<交付及排除项>` | `<方案摘要；详见下方 #01>` | `<通过条件；详见下方 #02>` | `<需求/闭环/外部条件缺口及阻塞范围；长内容用编号备注；无则写无>` |

占位符只说明结构，实际清单不照填。简短说明与正式 Plan 使用相同列名和
顺序；不增加合并、部署等列，不以卡片或散列项替代表格。

- **项目、分支**：完整目标分支不截断、不写“同上”；用“新建/复用”
  表达动作。多个模块共用同仓库分支时说明动作只执行一次，不按行数建 Plan。
  当前分支、完整基准 SHA 与原始动作枚举保留内部，不另起长段展示。
- **交付范围**：包含可观察的交付结果、明确排除项和必须保留的行为。
- **实施方案**：说明关键处理方式、复用能力和依赖，避免“完善逻辑”等空话。
- **验收标准**：说明关键场景、入口、通过条件及真实集成/Mock/静态检查局限。
  本地验证 build 属于这里；它与 Jenkins 测试环境构建分开。
- **需求待确认**：只展示尚未决定的业务范围、语义、规则、流程和验收，按下节判定。
  它不是待办进度或执行审批计数；没有适用缺口才写“无”。

## 需求待确认与外部条件的边界

主表“需求待确认”只记录业务范围、字段业务含义、角色行为、规则、流程闭环和
用户可观察的验收决定。每项说明具体问题、影响及决定方；无业务问题时写“无”。
等待执行确认、尚未编码或计划测试未执行不是业务缺口。

接口 method/URL、请求响应字段及类型、传输枚举、API Key 配置、环境、账号和
外部服务条件，集中记录到下节；组件、代码落点和内部技术决策仍放实施依据。
字段是否展示、业务枚举的含义和角色权限行为属于业务问题，不能按“字段/权限”
关键词机械移出。Agent 能查证的先查证，不把技术查证变成人类业务审批。

## 外部数据与依赖

六列主表后固定展示本模块，采用 [外部依赖规范](external-data-dependencies.md)。
它同时记录已确认事实与尚未就绪项，不只是缺口表；无新增依赖时给出实际判断
依据，未查证不能写“无”。正式 Plan/面板复用同一组记录，简短任务沿用原 brief，
不创建第二份台账或强制生成 Plan。

| 编号 | 关联功能/步骤 | 外部数据与依赖及来源 | 当前事实/环境 | 影响阶段与补齐条件 | 责任方 |
| --- | --- | --- | --- | --- | --- |
| 〈稳定依赖编号〉 | 〈实际功能、Task/步骤和验收引用〉 | 〈接口、字段契约、凭据配置引用、环境或外部服务；准确来源〉 | 〈已核实事实、尚未核实项及适用环境〉 | 〈阻塞的具体步骤/验收、可核验解除条件〉 | 〈有依据的补齐方或待核实〉 |

同一契约/配置记录一次，按消费点关联所有实际使用者。Key/token 只记录配置项、
保管位置引用、适用环境和配置/访问验证状态，不读取或展示实际值。未查到/读取
失败不等于不存在；保留查证限制、影响与下一步动作。

“需求待确认：无”不表示可实施。按本轮已批准步骤检查必需依赖，保留后续未就绪
事实：契约缺失可能阻塞真实接入，服务/账号缺失可能只阻塞联调或验收；UI/Mock
范围须明确批准。真实集成不能自动降为 Mock，未来步骤也不能默认为已获授权。
依赖补齐只解除有新证据支撑的阻塞，不重复业务确认；业务/关键方案或授权范围
变化仍展示完整当前清单，为变化补充确认，保留已完成效果。

## Mock 范围与测试授权

采用 [跨项目 Mock 规范](mock-development.md)。所有 Mock 实现必须有稳定
`MOCK-*` 编号及代码/配置中的 `MOCK_ONLY` 标识，关联功能、具体操作、路径、
正常场景、数据/配置层启停及必要重置、真实请求边界、验证局限和退出条件。
已接通 Query 的复用原链路，未接入的沿用既有 Mock 或功能数据入口；不默认
增加异常模拟、页面标识/调试控件或 Mock 分支后缀。异常模拟须引用明确的
用户/需求/已确认验收依据。没有 Mock 时仍先核实
当前源码范围，不能从缺少记录推断无 Mock。

含 Mock 时，在首次测试交付写入前展示下表，默认不允许；普通“开发/直接提测”、
“部署测试环境：是”以及通用 confirmed=true 均不授权 Mock 测试交付。当前完整
清单已准确展示并经人类明确确认时复用同一授权，不另问一次。范围、待交付
源码内容、目标测试分支/环境或用途变化须复核并重新取得受影响授权。
拟携带 Mock 时，应在完整预览中明确写“拟允许本次所列 Mock 测试交付，待确认”
并展示准确范围，再取得对应批准。清单仍写“否”时的普通“确认”不允许改成 ALLOW；
用户明确拒绝后保留拒绝，不因默认提测或重新调用技能覆盖。

| Mock 标识及范围 | 代码/配置位置与场景 | 真实调用边界/验证局限 | 目标测试分支和环境 | 是否明确允许本次 Mock 测试交付 | 退出条件 |
| --- | --- | --- | --- | --- | --- |
| 〈实际 MOCK-* 及功能/操作〉 | 〈当前路径、启用/重置方式〉 | 〈仍真实调用的操作；未完成真实验收项〉 | 〈准确测试目标〉 | 否；仅真实人类对当前完整内容明确批准后允许 | 〈正式接入、移除/隔离及验证要求〉 |

授权必须覆盖首次提交/推送/MR、合并、构建、Wiki和登记等本次选定操作；先核实
当前源码/差异和准确 Mock 清单，再按 [脚本交付规范](scripted-delivery.md)执行
统一门禁。生产/master/main 交付禁止活跃 Mock；正式制品和运行链路不得包含
Mock 模块、fixture、handler、runtime 或启用入口。关闭开关、移除标签或
Query Contract release-check 通过都不能代替退出与制品排除证据。

## 编号备注与 Plan

仅在交付范围、实施方案、验收标准或需求待确认需要更多内容时使用备注。
短内容直接放表内，不补空章节。表内保留可独立理解的摘要并写
“详见下方 **#01**”；表下对应标题只用 `### #01`、`### #02`，不再用
“验收标准”“实施方案”“验证安排”等类别标题代替索引。

- 编号在整份清单中按首次引用顺序连续分配，多项目不重新从 `#01` 起算。
  每个编号只对应一段详情；同一详情可被多个单元格引用。检查没有悬空
  引用、重复定义或无意义备注；同轮增量修改保留未变化内容的编号。
- 备注内用短条目展开实际步骤、边界、场景、问题选项/影响或证据。不要
  逐字重复表内摘要，也不把多条内容串成一段长句。关键问题短标题与
  阻塞数量仍须在表中可见，不能全部藏到备注中。
- 已有 Plan 时，编号备注可链接到已核实的对应模块/章节或准确行，同时
  说明拟更新差异。清单与 Plan 使用同一内容，不维护第二份详情文档。
- 首次尚无 Plan，直接在编号备注或已有评审面板中展示 brief/拟写正文和
  准确目标路径；未存在的路径不是可点击的 Plan。仍按原范围、分支、Task、
  位置与内容门禁确认、保存和读回后，才提供真实链接。
- 小改动不为备注或链接创建正式 Plan、Task 或临时详情
  文件。正式 Plan 按独立接手所需深度记录关键选择理由、复用/代码落点、
  联动/数据流、步骤依赖、验收证据及局限，不写逐行代码或工具流水账。
- 本地文件链接使用真实绝对路径，支持时定位到准确行；不假设聊天标题
  锚点能够跳转。`#01` 是对照索引，不承诺可点击。链接不可用就直接展开。
  已核实、用户可打开的正文可以作为详情展示，不要求证明点击过链接。

## TAPD 与本轮写入

Bug 只展示一个 `### TAPD 更新与修复记录` 区块：

- 开始修复状态：用实际中文状态展示“原状态 → 修复中”，在改业务源码前
  写入并准确读回；最终提测状态在下方“合并与测试环境”展示。
  已修复中的状态不重复流转，处理人仍按原规则核对；已待测试的续接沿用
  原保持策略，在此明确显示“待测试，保持不变”，不预览倒退为修复中。
- 处理人：显示已核实准确账号；同一人员仅分号/空白格式不同，写
  “某某，保持不变”，不制造人员流转。真实变更才显示“原人员 → 新人员”。
- 评论账号、开始记录和完成记录的时点逐项列出。
- 在该区块内直接给出 **【Bug 溯源与修复记录｜开始】**，按约定字段逐条
  排版预览，不再另起“开始评论预览”同级区块。没有关联需求时省略整行。

需求实际涉及的 Task 创建/复用/更新、人员、最终工时、Plan 目标路径和
拟写入内容仍须完整展示；放在一个按项目归属的中文写入区块，较长的
内容使用已引用编号备注或真实 Plan。不能只报数量或路径就声称内容已确认。
没有这些写入时不补空区块，Story/Task 不套用 Bug 状态或修复记录。

需求有任务时，按 [需求任务关联](../skills/developing-requirement/references/task-linked-delivery.md)
以父需求和本轮所选 Task 连接项目/分支、Plan 步骤、接口/依赖缺口、验收
证据及实际交付结果。主表仍为六列，所选任务先由上述三列表给出索引；
后续按 `#F01` 引用，详情 `#01` 只展开实际范围/方案等增量，不另建台账。
拟创建任务不伪造 ID，没有 Task 的小改动不为关联而补建 Task/Plan。

## 合并与测试环境

首次及调整后的完整确定清单固定列出 `### 合并与测试环境`，逐项表明本轮意图：

- **直接提测：** 需求默认是，表示实现、验证和独立评审通过后按已确认的
  分项选择继续交付。明确先完成代码供人工检查时为否，本轮停在 REVIEWED，
  不提交、推送、创建/合并 MR、写提测 Wiki、触发构建或执行提测登记。
  这只是现有交付终点的中文展示，不新增运行字段，也不推翻明确关闭的单项选择。

- **合并到测试分支：** 按项目列是/否；若是，列准确源分支 → 实际 dev/develop。
  包括提交/推送本轮已审查改动、创建/复用 MR 并合并；不能把某项目的目标或
  选择套到全部项目，单项目也可直接显示“合并到 dev/develop”。
- **是否需要提测 Wiki：** 需要/不需要。没有仍有效的明确选择时默认“需要”，
  对应 `STANDARD`；明确不需要时用 `NO_WIKI`。默认不覆盖本轮此前已明确关闭的选项。
- **部署测试环境：** 按项目列是/否；若是，列准确项目、测试环境与已核实
  Jenkins 任务/链接。此处是项目 Jenkins 测试构建/部署，本地 build 放在验收标准。
  提测以确切队列回执 `BUILD_SUBMITTED` 为构建门禁，不等待构建完成；
  清单说明“提交构建后继续提测”，结果只报任务已提交，不能报部署/发包成功。
  未核实的目标说明缺口，不伪造任务或把单项目成功当成全部完成。
- **TAPD 状态：** Bug 完整提测显示“待测试（提测交付完成后流转）”。这是本轮
  交付目标，不是当前状态或额外选择题；多个 Bug 按准确 Bug 分别列出，同一
  Bug 跨项目只列一次。仅修复验证、不提测时显示“修复中（本轮不流转待测试）”；
  已待测试的续接沿用原幂等策略，显示“待测试（保持不变）”。Story/Task 不套用 Bug 状态。

Bug 的常规完整流程为：开始修复先到“修复中”并核对修复处理人；修复、验证、
独立评审和记录完成后，等待全部必要项目的合并、所选构建/部署与 Wiki/评论
条件通过，再由提测登记流转“待测试”并核对测试处理人。每次状态写入都须准确
读回。完整执行清单覆盖这些操作时沿用原确认，不因进入正式提测计划再确认；等待合并、失败或部分完成
时保留实际状态，执行结果不得把目标状态当成已完成。

选定合并时，清单同时说明有冲突自动使用
[A → C → B](conflict-merge.md)：准确原分支/目标、派生临时分支及本仓库
`.worktrees/` 位置、冲突解决与 MR 交付、验证/评审和用途。长内容用数字备注。
确认后按该条件自动处理，不为同一冲突另问一次；删除临时/开发资源仍只在
已明确覆盖的精确清理授权内执行，未覆盖时保留并给建议。

同一 Bug/Story 的 Wiki 选择统一展示一次，需要时共用一页并包含各项目条目；
不因项目行数分别创建 Wiki。合并和部署则保留逐项目意图与目标。

普通“修复/开发”默认显示“合并：是、Wiki：需要、部署测试环境：是”，本轮目标
包含测试交付；先核实实际目标并展示模板，不把默认值当作执行授权，也不另弹 Wiki 选择题。
“仅开发验证/只修复验证、不提测”、PLAN_ONLY 或 BRANCH_ONLY 的明确终点优先；
“只开发 B 端相关功能”“仅改前端”“只做所选 Task”只限制业务范围，不关闭测试交付。
明确限制为不提测时，
三项显示本轮不执行；分别明确关闭某项则只关闭该项，不查询未选择的 Jenkins/Wiki。
已选择的同一项目测试构建/部署沿用同一实际任务，不重复触发。用户说“合并并构建”，默认理解为
合入实际 dev/develop 并构建该项目测试环境；不推导 master 合并或生产发布。
明确提测但不构建时按原部署策略显示“合并：是，构建：否”。已选择但
未能核实的目标分支/Job进入外部数据与依赖或交付准备缺口，不能当成“否”静默跳过。
默认不包含生产上线；测试 Job 如果涉及包发布，仍须在实际计划中明确包、
版本/通道和操作范围，不能用“构建默认需要”隐藏发布动作或跳过授权。
若必要项目明确不合并而其源码又是整轮提测前提，保留该选择并说明交付缺口；
不擅自合并、不把部分项目成功标成整个 Bug/需求提测完成。
若已手动合并，或测试分支已包含本轮已审查源码，则用只读包含关系核验
取得零写入回执后继续所选交付，不重复提交/推送、创建 MR 或宣称本轮新合并。

需要 Wiki 时，在确认问题前增加 `### 提测 Wiki 模板预览`，按
[现有 Wiki 模板](../skills/drafting-wiki/references/wiki-template.md#确定清单中的模板预览)
展示本次项目/分支的完整拟用结构。已核实字段填实际值，尚未发生的修复、验证、
构建或发布结果明确标为后续补充，不假定成功；未核实的身份/目标等事实注明缺口。
这只是执行前的模板预览，不是 `ValidatedWikiDraft`，不写 Wiki 或评论，不冒充
最终正文。完整清单须明确按本轮实际结果补全正文、计算最小补丁、创建/更新
归属页面并回链的操作；获确认后正式提测生成并验证无占位符正文，按上述
确认复用规则执行和读回。单独模板、默认意图或未核实的业务字段不授予写权限。
不需要 Wiki 时不展示空模板、不定位 Wiki，也不要求用户提供 Wiki URL。

这些字段连同完整范围、操作及填充规则构成确认内容；后续仍准备准确提测/
合并/部署计划并核对原授权，不强制再进行人类确认。明确要求上线才进入上线
流程，且只有已展示并获准的上线目标/操作可以复用，不能从测试交付推导生产授权。

## 用户调整后的重新展示

用户修改交付范围、关键方案、验收、分支或人员/任务预估，或改变合并、Wiki、
部署选择时，先复用有效事实核实变化，再重新展示完整的当前确定清单：概览、所选任务表、六列主表、
必要的编号详情、本轮 TAPD/Task 写入、上述三项选择，以及需要时的 Wiki 模板。
先简述本次变化，未变化的行和编号也保留供对照；不能只写“其余沿用上份清单”。
不为重印而重新路由项目或重复读取仍有效证据。

例如“改用新版组件，合并 dev，需要 Wiki，部署”是调整提案，不能直接开始
源码、分支或 TAPD 写入；先更新确定清单及 Wiki 预览，再问“是否按以上确定清单执行？”。
“确认，另外改……”含实质变化时也一样；只回答“需要 Wiki”仅确定该选项，
不能代替对调整后完整清单的确认。不单独再问一遍“是否需要 Wiki”。

仅回复“确认/执行”且完整清单未变化时直接使用有效确认，不制造循环确认。
已有部分效果时如实列出“已完成/本轮不重复”，保留准确分支及记录读回，暂停
受影响后续写入；新确认不重建分支、不重发开始评论、不回滚已有代码。
最终提测计划的操作集变化同样重印完整计划再确认；已授权操作产生的确定性
提交/MR/构建 ID 等回执以及纯排版变化，不触发额外一轮。

## 确认与就绪

清单、编号备注、实际关联的 Plan 内容和本轮写入共同构成确认内容。
隐藏内部英文码不隐藏具体操作，详情未生成或版本不明时不能视为已展示。
有阻塞先解决或明确调整范围；全部适用门禁通过后，只问一次
“是否按以上确定清单执行？”。确认请求不回填为“需求待确认”；取得确认才称执行清单。

`BRANCH_ONLY` 只说明本轮分支准备及读回条件；`PLAN_ONLY` 验收针对计划
完整性，保留实施缺口，不自动授权源码或 Task 写入。范围、关键方案、
验收、人员/任务预估、分支基准或实际写入发生实质变化时，按原门禁展示差异
并重新确认；排版、索引调整和同一分支创建后的预期动作切换不加确认。

本规范不新增交接字段、状态/恢复文件或运行编号。备注编号仅用于用户
阅读对照，不能充当任务身份、执行状态或授权凭证。
