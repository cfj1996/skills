# 确定清单与执行清单

Bug 修复、小需求和大需求统一保留六列表格。清单是同一份方案的摘要；
已有 Plan 承载详情，小改动直接用对话说明，不为提供链接创建文档或 Task。

## 名称与阶段

同一份清单随确认状态命名，不维护两份内容或新增运行状态字段：

- 初次展示、或实质调整后等待确认时，标题为 `## 确定清单`。
- 用户确认当前完整内容后，称为 `执行清单`，作为已授权实施依据。可简短
  说明“已确认，按执行清单执行”，无须仅为改名再重印或再问一次。
- 执行中实质调整时，暂停受影响写入，展示更新后的完整 `确定清单`；
  新确认后再转为执行清单。原已完成效果保留并标明不重复执行。
- 最终报告称为 `执行结果`，只包含真实完成范围、验证/评审和遗留。

## 展示顺序与语言

按“简短概览 → 六列表格 → 必要的编号备注 → TAPD 更新与修复
记录/需求写入事项 → 合并与测试环境 → 所选 Wiki 的模板预览 → 一次执行确认”展示。

标题下依次显示：

- **执行项目名称：** 支持多个，逐项列出已核实的业务项目/子项目名称；
  同名项目附简短代码标识帮助对应主表，不凭关联/依赖扩大本轮修改范围。
- **执行事项：** 本轮 Bug 修复或所选需求/任务的简短名称。
- **关联记录：** 准确 Bug/Story/所选 Task 链接。
- **本轮目标：** 用中文说明做到开发评审、提测或上线的哪一步。

随后用 `### 执行内容` 引出六列表格。顶部只做概览，不重复分支长名、验证
安排、TAPD 字段核验过程；主表项目、分支和各自交付边界保持完整。

- 用中文说明本轮做到哪一步及实际风险。不设置工作规模/风险等级标签，
  `IMPLEMENT|SUBMIT|GO_LIVE` 等终点值只用于内部交接，不打印在清单中。
  确有风险就写具体
  影响和验证重点，例如“涉及金额计算，增加金额准确性回归”。
- 不向用户堆原始状态码、payload、字段核验过程、完整 SHA 或内部指纹。
  这些证据仍须准确读取、保存于当前内存交接并在写前复核；展示简化不
  降低分支、身份、状态、任务或授权门禁。用户询问或事实冲突需要解释时
  再提供相关技术依据。
- 表内已说明的项目、分支、范围和验证不再另列“分支安排”“验证安排”
  重复一遍。需要展开的是四项内容的增量详情，按下面的编号规则关联。

## 六列主表

按实际项目/仓库/固定分支展开，单项目也保留表格。相同仓库和分支的子项目
可以合并一行，但必须列明全部子项目及各自范围，分支操作只执行一次。
多个 Bug 保持输入顺序，
在项目格附准确 Bug 编号/链接；项目名和仓库须能唯一识别。

| 项目 | 分支 | 交付范围 | 实施方案 | 验收标准 | 待决事项 |
| --- | --- | --- | --- | --- | --- |
| `<项目/子项目；准确条目链接>` | `<从已核实基准 ref 新建/复用完整目标分支>` | `<交付及排除项>` | `<方案摘要；详见下方 #01>` | `<通过条件；详见下方 #02>` | `<需求/闭环/外部条件缺口及阻塞范围；长内容用编号备注；无则写无>` |

占位符只说明结构，实际清单不照填。简短说明与正式 Plan 使用相同列名和
顺序；不增加合并、部署等列，不以卡片或散列项替代表格。

- **项目、分支**：完整目标分支不截断、不写“同上”；用“新建/复用”
  表达动作。多个模块共用同仓库分支时说明动作只执行一次，不按行数建 Plan。
  当前分支、完整基准 SHA 与原始动作枚举保留内部，不另起长段展示。
- **交付范围**：包含可观察的交付结果、明确排除项和必须保留的行为。
- **实施方案**：说明关键处理方式、复用能力和依赖，避免“完善逻辑”等空话。
- **验收标准**：说明关键场景、入口、通过条件及真实集成/Mock/静态检查局限。
  本地验证 build 属于这里；它与 Jenkins 测试环境构建分开。
- **待决事项**：展示本轮需求与落地条件中尚未补齐的缺口，按下节判定。
  它不是待办进度或执行审批计数；没有适用缺口才写“无”。

## 待决事项的内容与边界

适用于 Bug 修复、小需求和大需求，重点检查四类缺口：

| 类型 | 应记录的事实 |
| --- | --- |
| 需求不完整 | 范围、业务规则、角色、边界条件或验收语义缺失/冲突，无法确定本轮行为 |
| 流程不闭环 | 触发后缺少结果反馈、失败处理、状态恢复或必要后续动作，关键链路无法闭环 |
| 接口与字段缺失 | 本轮需要的接口契约、输入输出字段、类型/枚举、状态码或数据来源缺失/未核实 |
| 外部条件未就绪 | 本轮依赖的测试环境、账号权限、授权 Key 配置、外部服务或必要测试能力不可用/未核实 |

表内保留具体缺口摘要、影响及阻塞范围/数量；长内容在对应 `#01` 备注或
同一 Plan 中逐项记录：**缺口、影响、责任方、补齐条件、阻塞范围**。责任方
必须有依据，未知就写“责任方待核实”；补齐条件给出可核验的解除标准，
例如正式契约/字段含义已明确、所需环境访问验证通过，而不只写“待确认”。
依据不足时同时注明已查证范围、当前证据和下一步查证动作。

- 只列本次交付范围内实际适用的缺口，明确影响需求确认、实现、联调或
  验收的哪一步，不笼统把所有缺口都称为“需求未确认”。沿用既有需求/
  实施门禁，不新增状态枚举；缺少必要外部条件不能把真实集成标为通过。
- Agent 能从现有代码、契约、配置或工具查证的先查。区分“已确认缺失”
  与“尚未核实”：检索无结果、网络/权限读取失败不证明接口不存在或 Key
  未配置。不能用猜测填齐字段，也不能把这类限制直接交给用户作业务决定。
- 授权 Key 指外部服务的访问配置，与用户是否批准本轮执行不同。只记录
  “未配置/权限不足/尚未验证”等已核实状态及补齐方式，不在清单、备注、
  评论或 Plan 中展示密钥值，也不要求用户把密钥贴进聊天。
- 等待最终执行确认、尚未编码、按计划还没跑测试不是缺口；没有测试环境
  导致必需验证无法运行才是缺口。不得写“执行确认 1 项”。历史引入人或
  时间未知且不影响修复时，只留在溯源记录，不计入这里。
- 明确只做 UI/Mock 时，不把未请求的真实接口联调当作隐含门禁。反之，
  必须真实集成的交付不能自行降成 Mock 来清空缺口；调整范围仍须明确确认。
- 建议方案不等于缺口已补齐。获得新的决定或证据后复核对应解除条件，
  更新同一备注/Plan 和阻塞计数；只重开受影响范围，不重新制造整套问题。

## 编号备注与 Plan

仅在交付范围、实施方案、验收标准或待决事项需要更多内容时使用备注。
短内容直接放表内，不补空章节。表内保留可独立理解的摘要并写
“详见下方 **#01**”；表下对应标题只用 `### #01`、`### #02`，不再用
“验收标准”“实施方案”“验证安排”等类别标题代替索引。

- 编号在整份清单中按首次引用顺序连续分配，多项目不重新从 `#01` 起算。
  每个编号只对应一段详情；同一详情可被多个单元格引用。检查没有悬空
  引用、重复定义或无意义备注；同轮增量修改保留未变化内容的编号。
- 备注内用短条目展开实际步骤、边界、场景、问题选项/影响或证据。不要
  逐字重复表内摘要，也不把多条内容串成一段长句。关键问题短标题与
  阻塞数量仍须在表中可见，不能全部藏到备注中。
- 已有 Plan 时，编号备注可链接到已核实的对应模块/章节或准确行，同时
  说明拟更新差异。清单与 Plan 使用同一内容，不维护第二份详情文档。
- 首次尚无 Plan，直接在编号备注或已有评审面板中展示 brief/拟写正文和
  准确目标路径；未存在的路径不是可点击的 Plan。仍按原范围、分支、Task、
  位置与内容门禁确认、保存和读回后，才提供真实链接。
- 小改动不为备注或链接创建正式 Plan、Task 或临时详情
  文件。正式 Plan 按独立接手所需深度记录关键选择理由、复用/代码落点、
  联动/数据流、步骤依赖、验收证据及局限，不写逐行代码或工具流水账。
- 本地文件链接使用真实绝对路径，支持时定位到准确行；不假设聊天标题
  锚点能够跳转。`#01` 是对照索引，不承诺可点击。链接不可用就直接展开。
  已核实、用户可打开的正文可以作为详情展示，不要求证明点击过链接。

## TAPD 与本轮写入

Bug 只展示一个 `### TAPD 更新与修复记录` 区块：

- 状态：用实际中文状态展示“原状态 → 目标状态”。
- 处理人：显示已核实准确账号；同一人员仅分号/空白格式不同，写
  “某某，保持不变”，不制造人员流转。真实变更才显示“原人员 → 新人员”。
- 评论账号、开始记录和完成记录的时点逐项列出。
- 在该区块内直接给出 **【Bug 溯源与修复记录｜开始】**，按约定字段逐条
  排版预览，不再另起“开始评论预览”同级区块。没有关联需求时省略整行。

需求实际涉及的 Task 创建/复用/更新、人员、最终工时、Plan 目标路径和
拟写入内容仍须完整展示；放在一个按项目归属的中文写入区块，较长的
内容使用已引用编号备注或真实 Plan。不能只报数量或路径就声称内容已确认。
没有这些写入时不补空区块，Story/Task 不套用 Bug 状态或修复记录。

需求有任务时，按 [需求任务关联](../skills/developing-requirement/references/task-linked-delivery.md)
以父需求和本轮所选 Task 连接项目/分支、Plan 步骤、接口/依赖缺口、验收
证据及实际交付结果。主表仍为六列，任务明细复用交付范围引用的编号备注
或已有任务表，不重复生成台账；Task 很少时可直接在项目格附真实链接。
拟创建任务不伪造 ID，没有 Task 的小改动不为关联而补建 Task/Plan。

## 合并与测试环境

首次及调整后的完整确定清单固定列出 `### 合并与测试环境`，逐项表明本轮意图：

- **合并到测试分支：** 按项目列是/否；若是，列准确源分支 → 实际 dev/develop。
  不能把某项目的目标或选择套到全部项目，单项目也可直接显示“合并到 dev/develop”。
- **是否需要提测 Wiki：** 需要/不需要。没有仍有效的明确选择时默认“需要”，
  对应 `STANDARD`；明确不需要时用 `NO_WIKI`。默认不覆盖本轮此前已明确关闭的选项。
- **部署测试环境：** 按项目列是/否；若是，列准确项目、测试环境与已核实
  Jenkins 任务/链接。此处是项目 Jenkins 测试构建/部署，本地 build 放在验收标准。
  未核实的目标说明缺口，不伪造任务或把单项目成功当成全部完成。

同一 Bug/Story 的 Wiki 选择统一展示一次，需要时共用一页并包含各项目条目；
不因项目行数分别创建 Wiki。合并和部署则保留逐项目意图与目标。

普通“修复/开发”默认显示“合并：是、Wiki：需要、部署测试环境：是”，本轮目标
包含测试交付；先核实实际目标并展示模板，不把默认值当作执行授权，也不另弹 Wiki 选择题。
“只开发/只修复验证、不提测”、PLAN_ONLY 或 BRANCH_ONLY 的明确范围优先，
三项显示本轮不执行；分别明确关闭某项则只关闭该项，不查询未选择的 Jenkins/Wiki。
已选择的同一项目测试构建/部署沿用同一实际任务，不重复触发。用户说“合并并构建”，默认理解为
合入实际 dev/develop 并构建该项目测试环境；不推导 master 合并或生产发布。
明确提测但不构建时按原部署策略显示“合并：是，构建：否”。已选择但
未能核实的分支/任务进入待决事项，不能当成“否”静默跳过。
默认不包含生产上线；测试 Job 如果涉及包发布，仍须在实际计划中明确包、
版本/通道和操作范围，不能用“构建默认需要”隐藏发布动作或跳过授权。
若必要项目明确不合并而其源码又是整轮提测前提，保留该选择并说明交付缺口；
不擅自合并、不把部分项目成功标成整个 Bug/需求提测完成。

需要 Wiki 时，在确认问题前增加 `### 提测 Wiki 模板预览`，按
[现有 Wiki 模板](../skills/drafting-wiki/references/wiki-template.md#确定清单中的模板预览)
展示本次项目/分支的完整拟用结构。已核实字段填实际值，尚未发生的修复、验证、
构建或发布结果明确标为后续补充，不假定成功；未核实的身份/目标等事实注明缺口。
这只是执行前的模板预览，不是 `ValidatedWikiDraft`，不写 Wiki 或评论，不冒充
最终正文或授权未知内容。实际正文仍在正式提测计划中依据结果展示、确认和读回。
不需要 Wiki 时不展示空模板、不定位 Wiki，也不要求用户提供 Wiki URL。

这些字段表达交付意图，不替代后续精确提测/合并/部署计划的原有授权与
验证。明确要求上线才进入上线流程，并按实际目标单独说明。

## 用户调整后的重新展示

用户修改交付范围、关键方案、验收、分支或人员/工时，或改变合并、Wiki、
部署选择时，先复用有效事实核实变化，再重新展示完整的当前确定清单：概览、六列主表、
必要的编号详情、本轮 TAPD/Task 写入、上述三项选择，以及需要时的 Wiki 模板。
先简述本次变化，未变化的行和编号也保留供对照；不能只写“其余沿用上份清单”。
不为重印而重新路由项目或重复读取仍有效证据。

例如“改用新版组件，合并 dev，需要 Wiki，部署”是调整提案，不能直接开始
源码、分支或 TAPD 写入；先更新确定清单及 Wiki 预览，再问“是否按以上确定清单执行？”。
“确认，另外改……”含实质变化时也一样；只回答“需要 Wiki”仅确定该选项，
不能代替对调整后完整清单的确认。不单独再问一遍“是否需要 Wiki”。

仅回复“确认/执行”且完整清单未变化时直接使用有效确认，不制造循环确认。
已有部分效果时如实列出“已完成/本轮不重复”，保留准确分支及记录读回，暂停
受影响后续写入；新确认不重建分支、不重发开始评论、不回滚已有代码。
最终提测计划的操作集变化同样重印完整计划再确认；已授权操作产生的确定性
提交/MR/构建 ID 等回执以及纯排版变化，不触发额外一轮。

## 确认与就绪

清单、编号备注、实际关联的 Plan 内容和本轮写入共同构成确认内容。
隐藏内部英文码不隐藏具体操作，详情未生成或版本不明时不能视为已展示。
有阻塞先解决或明确调整范围；全部适用门禁通过后，只问一次
“是否按以上确定清单执行？”。确认请求不回填为“待决事项”；取得确认才称执行清单。

`BRANCH_ONLY` 只说明本轮分支准备及读回条件；`PLAN_ONLY` 验收针对计划
完整性，保留实施缺口，不自动授权源码或 Task 写入。范围、关键方案、
验收、人员/工时、分支基准或实际写入发生实质变化时，按原门禁展示差异
并重新确认；排版、索引调整和同一分支创建后的预期动作切换不加确认。

本规范不新增交接字段、状态/恢复文件或运行编号。备注编号仅用于用户
阅读对照，不能充当任务身份、执行状态或授权凭证。
