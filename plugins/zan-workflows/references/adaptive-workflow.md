# 按工作规模选择流程

需求和 Bug 共用本规则。流程长度由复杂度和未决问题决定，验证强度由风险决定，
交付终点由用户请求决定。入口先利用已有事实作一次轻量判断，并说明选择理由；
不要求用户填写分级表，也不为分级重新扫描项目或重复确认。

## 三个独立选择

| 选择 | 取值与用途 |
| --- | --- |
| `workflow_profile` | 输入允许 `AUTO`，解析为 `QUICK|STANDARD|FULL`，决定准备和文档深度 |
| `verification_risk` | `NORMAL|HIGH`，决定验证和审查重点，不决定是否生成正式 Plan |
| `delivery_mode` | 沿用入口的枚举；普通开发/修复为 `IMPLEMENT`，明确提测/上线才选择 `SUBMIT|GO_LIVE` |

`workflow_profile=STANDARD` 与 `submission_profile=STANDARD`（提测 Wiki 策略）
含义不同，始终带字段名传递。QUICK 不推导 NO_WIKI，FULL 不推导部署或上线。
`BRANCH_ONLY`、`PLAN_ONLY` 按需求入口的原有终点处理；请求正式 Plan 至少 STANDARD。

## 路径选择

| 路径 | 选择依据 | 准备与执行 |
| --- | --- | --- |
| QUICK | 单仓库、单内聚交付边界；行为、排除项和验收明确；实施位置与依赖已有证据；无未决阻塞；无需正式 Plan、任务写入或多人拆分 | 简短范围与执行摘要 → 既有准备/分支授权 → 实施、验证和独立审查 |
| STANDARD | 局部模块有若干关联行为，需少量设计决定或可交接的正式 Plan；或者明确请求任务拆分/更新 | 关键问题澄清 → 紧凑的任务/Plan → 分步实施与审查 |
| FULL | 跨项目或复杂依赖、多个独立业务决定、复杂状态，需要协调多个交付单元 | 完整范围评审 → 协调任务与各模块 Plan → 按依赖实施与审查 |

- 缺少事实时先做最小查证，不能把未知当成“简单”。QUICK 需满足全部条件，
  用户偏好 QUICK 不能替代查证。用户要求更充分的计划时尊重该要求。
- 路径不以需求/Bug 类型、修改行数或固定工时判断。多个独立小 Bug 可以逐项
  QUICK，保持原有一次预检、共享分支和有序执行；单个复杂 Bug 也可以 FULL。
- PANEL 是评审交互方式，独立沿用 `writing-plans` 的适用条件；FULL 不自动要求面板。
- 在入口由 AUTO 选择合适路径；下游收到未携带档位的旧交接时按 STANDARD，
  保留原 Task/Plan 要求。已有正式 Plan、TaskBreakdown 或项目强制规范时，
  不得选择 QUICK 来绕开其中的阻塞、人员、工时、任务读回或验收要求。

## QUICK 的交接

复用准确的 `TapdWorkDefinition`，附内存 `implementationBrief`。它是人能读懂的
执行摘要，不是新的持久化模型：说明本次改变与必须保留的行为、排除项、当前
证据引用、少量有序步骤，以及验证入口、关键预期与已知局限。没有新 schema、
流程文件或额外指纹。下游语义核对同一条目、范围和分支，不另写一套重复摘要。

Story 输入绑定真实 Story 和本次窄范围；Task 输入读取其真实父 Story、所选
Task 和责任范围，尊重既有分配，只执行用户选定的工作。不把 Git 作者当成
TAPD 开发人员，不扩大到兄弟任务。QUICK 不创建/更新 Task、不补估时、不制造
`TASKS_READY`，也不为生成排期而强行拆任务。

QUICK 不进入 `PLAN_WRITE`，不将摘要伪装成通过校验的正式 Plan。需要保存正式
Plan、修改 Task 或多人协作时升到 STANDARD/FULL；正式 TAPD Plan 仍需原有
`TASKS_READY`、Task→步骤关联与完整校验，不能删除 TAPD 身份或设置 QUICK
标记以逃避校验。只请求简短执行说明时直接在对话展示摘要。

Bug 各档位都从复现/实际现象和修复范围开始，不强制生成需求 PRD 或拆需求 Task。
STANDARD/FULL Bug 的调查说明可保留在对话；用户要求文档或实际跨会话交接时再
保存适用文档，并遵循对应能力的产物规则。

## 验证强度

涉及权限、安全、金额、订单、库存、账务、数据迁移/一致性、兼容性或广泛共享
能力时，用 HIGH 并说明具体风险；风险尚不清楚时先按 HIGH 查证。NORMAL 也
必须完成项目要求与本次行为相关的验证。HIGH 增加风险对应的异常、回归、
兼容或权限场景，不通过堆无关测试替代行为证据。

所有档位保留 `implementing-work` 的独立最终审查和 `REVIEW_PASSED` 交接要求。
QUICK+HIGH 可以缩短准备，但不能降低验证和审查深度。验证命令、Mock 结果、
浏览器交互与真实集成分别说明能证明的行为和局限；未运行不得报通过。

## 澄清、执行与反馈

- 按决定之间的依赖提问，先解决会影响后续方案的选择，每题给出建议与影响。
  Agent 能查的事实先查；只追问影响本次交付、风险或返工成本的决定。
- 需要运行才能确定的问题，明确探索范围、待验证假设和停止条件，再回填结论。
  保持只读阶段与业务源码实施的边界，不把待验证方案写成已证实事实。
- 正式 Plan 用独立接手能力检查：只凭任务、Plan 和项目规则，能否解释交付行为、
  排除项、关键选择和完成证据。复杂交接可独立检查，不新增用户审批或必跑 Agent。
  业务约定与基于当前代码的实施导航分清；保留有用的路径和基线证据。
- 在现有 Task/范围内按可验证行为组织步骤，优先验证最可能推翻方案的完整路径。
  完成一个行为并获得反馈，再扩展场景；不强制一个行为新建一个 TAPD Task。
- 新事实提高复杂度时只补受影响的分析、计划和验证，复用仍有效的证据与授权。
  范围、分支、拟写入内容改变时沿原规则重新确认；档位变化本身不是新的授权门禁。

## 始终保留的边界

准确条目/仓库/范围、固定分支及所需确认、相关验证和独立审查始终保留。
Bug 状态与修复人员的联合授权/读回、待测试续接保护始终保留。业务实施与
Task 写入、提交、推送、MR、Wiki、部署、上线、清理的权限相互独立。
低档位不取消项目硬性规则，高档位不扩大用户授权。只执行 IMPLEMENT 时，
不为未请求的提测提前解析 Wiki/部署策略，也不展示相应确认问题。

重复错误优先修复导航、信息访问或确定性检查；需要判断的规范才写入长期规则。
只沉淀可复用知识，不为每个小改动生成复盘报告、运行记录或额外台账。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 明确的小 Story，无既有正式 Plan/任务拆分 | QUICK 摘要可交接实施，无 Task/Plan 写入；验证与审查完成后按交付终点返回 |
| 选定已有 Task，只改其明确范围 | 核对真实 Task/父 Story 和责任范围，不扩展兄弟任务，不改人员或工时 |
| 范围窄但涉及权限的修复 | 可 QUICK+HIGH，保留权限回归、独立审查及所有 Bug 写入保护 |
| 多模块调查，只请求修复 | FULL+IMPLEMENT，审查完成后返回，不进入提测 |
| QUICK 后明确要求正式 Plan 或任务拆分 | 升级后走原能力，不给正式校验器增加豁免 |
| 旧正式 Plan 缺任务读回或带阻塞 | 不以 QUICK 降级绕过；保留原阻塞和补齐路径 |
| QUICK 开发并明确提测 | 使用原提测 PLAN/确认/EXECUTE，Wiki 与部署策略独立解析 |
| 继续已待测试 Bug，仅要求修复反馈 | 复用原分支和状态，未明确的提交终点不得由已有 Wiki/状态推出 |
