# 准备深度与验证

Bug 修复和需求开发共用一条主线：查清范围与缺口 → 确定清单获确认 → 按执行清单实施、
验证和独立评审 → 按明确意图交付。按实际工作需要选择产物，不再分配流程档位
或风险等级枚举，也不为缺少旧字段补一条兼容路径。
各节点按 [同一清单编排](execution-checklist.md#围绕同一清单编排) 执行：
确定清单获准后沿用为执行清单，已有能力结果作为它的事实视图，阶段不重新
规划整轮。节点次数/条件、可移除的机械代理、前置包/测试服务产出及局部失效
处理统一维护在那里；不因优化再造一个计划、台账或执行引擎。

## 直接使用范围说明

行为、排除项、实施位置/依赖和验收已经明确，且没有本轮实施阻塞时，使用
内存 `implementationBrief`：`behaviors`、`exclusions`、`evidence`、`steps`、
`verification`。内容包含少量可验证步骤、入口/预期和已知局限；复用准确
TAPD 身份、项目、分支和原有授权，不保存为新运行模型或临时详情文件。

小 Story 没有 Task 也可按已确认窄范围开发。这里的“小”指交付边界集中，
不是编码量少、已有静态页或采用 Mock；先按下节核对完整所选范围。已有 Task 先核实父需求、
负责人和所选范围，不扩展到兄弟任务，不为展示链接补估时或强建 Task。
Bug 各种规模都从现象、复现与调查说明开始，不强制生成需求 PRD 或拆 Task。

## 需要 Task 与正式 Plan 时

用户明确要求正式 Plan、Task 创建/更新，实际需要多人/跨模块交付协调，
或继续已有正式 Plan 时，使用既有任务拆分和 Plan 能力。对准备实施的本轮 Story 范围，
多个页面/模块有各自的业务行为、依赖或独立验收，或跨仓库有需分别交付和衔接的
责任范围，属于实际协调需要，即使同一人开发、已有静态页、复用成熟组件或先做
Mock，也应准备真实/拟建 Task 和按交付单元拆分的正式 Plan，不能仅按编码增量
降为 brief。反之，同一明确的小改动机械应用到多个文件/页面，不因数量多就强建产物。
输入仅为选定 Task 时仍限于该 Task，不据父 Story 规模扩大到兄弟任务。
复杂程度只决定内容深度与依赖安排，不增加另一条执行路径或确认轮次。

- 正式需求实施保留真实 Task、人员、最终工时、TASKS_READY 精确读回和
  Plan 步骤 `tapdTaskKey` 对应关系；不能换成简短说明来绕过已有阻塞。
- Plan 记录交付边界、关键选择及理由、复用/代码落点、数据与交互流程、
  步骤依赖、验收证据和局限，以独立接手所需深度为准，不预写逐行代码。
- 用户只要计划时可保留明确未就绪的阶段 Plan；保存不等于可实施。
  Task 尚未创建不能伪造 ID，准确读回后只按已确认规则补系统字段。
- 只有实际需要或用户选择面板评审时加载面板运行时；多文件不自动要求面板。
- 已有 Task/Plan 就维护原记录，不创建第二份清单详情、台账或恢复文件。

首次用于实施的完整确定清单就列出本轮真实/拟建 Task、负责人和经校准及独立评审的最终
工时，并展示各页面/内聚模块 Plan 的准确拟写路径与内容。缺人员、估时证据或
本轮必需依赖时先交明确缺项的草稿，不隐藏任务表、假称“不需要任务”，也不发起执行确认。
仅提出方案不等于已创建 Task 或已保存 Plan。页面开发与接口对接按
[任务阶段拆分](../skills/breaking-down-requirement/SKILL.md#页面开发与接口对接)
区分本轮与未来范围；Plan 仍按页面/内聚模块归属，不按阶段复制两份。

多任务实现由 `implementing-work` 按 [并行规则](../skills/implementing-work/references/parallel-execution.md)
统一派发：小任务直接完成，就绪且写入范围/资源独立的步骤可并行。开发子代理
协作本身不等于多人业务交付，不因此强制正式 Plan/Task；保留已有正式约束。

## 验证随实际风险调整

金额、权限、安全、订单、库存、账务、数据迁移/一致性和共享能力等风险，
直接反映在异常、回归、权限或真实集成场景中。局部改动可以少做准备，但
不能降低必要验证或独立最终评审。风险未知先查证，不能把未知写成低风险。

按行为选择项目测试、复现或浏览器验证，先验证最可能推翻方案的路径。
Mock、静态检查与真实集成各自说明证明范围，未运行或条件缺失不能报通过。
已有结果仍有效时复用；后续变化仅重验受影响部分。

复用绑定实际完整差异/文件内容、相关依赖配置、验收和验证命令/环境，不只看
HEAD。同一内容转为 commit、推送或生成 MR/队列 ID 时，核实内容对应关系并
更新内存绑定，不重做代码评审；目标分支新增未审差异、人工改动或冲突修改则
只补受影响验证/独立评审。每个实际变更仓库仍须有自己的独立评审和必要跨仓验收。
提测阶段按 [整体计划评审](../skills/submitting-for-test/references/submission-rules.md#whole-plan-review)
合并流程审核；计划通过不代替写前实时检查或任何实际回执。

本地命令遵守 [范围与资源预算](local-verification.md)：默认验证变更行为及受影响
文件/包，不机械执行全仓 lint + type + build；必要全量检查保留。
重检查同机串行并用有超时、进程组内存监测和取消能力的执行器；超限后停止，
说明缺口，不自动扩容或原样重跑。

## 展示、授权与复用

统一使用 [六列清单规范](execution-checklist.md)，确认前叫确定清单、确认后叫执行清单；长内容由 `#01` 备注关联
原有 Plan 或同一范围说明。仅展示真实缺口、中文本轮目标及具体风险；
不因排版、阶段推进或模型选择增加准备文档与确认。

有效的项目知识、原型/接口、TAPD、范围和分支证据在能力间复用，写前只刷新
可变事实。范围、分支、人员/工时或实际写入发生实质变化才重开受影响确认。
真实需求/外部条件缺口须补齐或明确调整范围，不能靠假设清零。

业务待决定问题与外部条件分别按 [外部数据与依赖](external-data-dependencies.md)
记录；内部实施依据仍在原方案。需求确认、依赖就绪、执行授权分别判断。按本轮
已选步骤/阶段计算必需阻塞，未来步骤继续保留未就绪事实，不清空全需求缺口。
接口就绪后续接原 Task/Plan/分支；仅技术事实补齐不重复业务确认，新增接入或
交付未在原授权内时展示完整当前清单，为变化补充授权。

所有 Mock 遵守 [跨项目规范](mock-development.md)：先识别项目实际能力，契约
未知使用功能数据场景，契约已知再模拟 HTTP；不强制引入 Query Contract。
已接通 Query 的复用其链路，未接入的复用既有 Mock 或最近的数据入口。默认只
提供正常数据；异常模拟须有明确需求依据。启停/数据选择/重置放在数据或配置层，
默认不增加业务页面标识、调试控件或 Mock 分支后缀。
Mock 必须有稳定标识和代码/配置位置，默认仅本地。普通测试交付默认不包含
Mock，必须对准确范围/版本/测试目标明确确认；生产禁止携带 Mock 模块、数据、
handler、runtime 和启用入口，源码与制品门禁不能被关闭开关替代。

两个入口的普通开发/修复默认包含测试交付：合并实际 dev/develop、测试构建和 Wiki，
均须先展示并确认；需求清单默认“直接提测：是”。明确只实施或
“先完成代码，我检查后再提测”时显示“直接提测：否”，到评审结束，本轮
不提交/推送/合并、不写提测 Wiki、不构建、不做提测登记；明确上线才进入上线能力。
人工检查后独立调用 `$submitting-for-test`，按
[直接提测](../skills/submitting-for-test/references/direct-submission.md) 核实原成果及
人工改动、补受影响验证/独立评审，展示准确交付清单并确认，不重复实施。
“只开发 B 端相关功能”“仅改前端”“只做所选 Task”限制业务范围，
不等于仅实施或不提测，不改变上述默认交付。
Wiki 模板在确定清单先预览，正式正文与准确测试部署计划在交付写前确认。
只有用户需要排期或日期安排才加载排期
规则，默认实施不输出日历建议，不自动回写工时、状态或日期。
