# 跨项目 Mock 开发与交付门禁

本规范适用于已接入 Query / Query Contract 和未接入的项目。统一行为、记录和退出要求，
实现绑定沿用项目实际能力；不因页面任务强制安装插件、迁移请求体系或
建设全局 Mock 平台。正式记录使用[评审模型](../skills/writing-plans/references/page-review-standard.md)
的 `mockModules`，与[外部数据与依赖](external-data-dependencies.md)及原 Plan
关联；无正式 Plan 时在原执行摘要中表达，不增加台账。

## 默认范围与页面边界

- 默认只提供本轮页面开发所需的正常业务数据和成功交互。普通“先走 Mock”
  不包含异常模拟；只有用户、PRD 或本轮已确认验收明确要求时，才增加对应
  异常数据或故障注入，并记录依据、操作和预期。没有该要求时不主动补齐
  超时、延迟、接口失败、权限拒绝、缺失详情、损坏数据等场景，也不默认
  建设空态、失败等可切换的场景集合。
- Mock 只改变数据来源。fixture、handler、启停、场景选择及重置放在数据层
  或开发配置层；业务页面沿用正式产品的布局、文案、操作和数据消费入口。
  默认不新增 Mock 横幅、说明模块、状态标签、场景选择器、重置按钮，也不因
  Mock 改写成功提示或导出文件名。用户明确要求页面调试入口时才按其范围实现。
- 通过代码/配置声明、开发日志和 Plan/交接识别模拟来源、命中操作和仍然真实
  调用的边界；无需把这些工程信息显示在业务页面。Plan 评审面板和提测记录
  仍应如实说明 Mock 范围，它们不属于产品页面。
- 分支按真实需求/功能命名，默认不附加 Mock、演示等阶段后缀，也不为 Mock
  阶段另建分支。已有固定分支继续使用，不为统一命名自动改名；正式接入续接
  同一需求分支、Task 和 Plan。用户明确指定的工作位置或命名例外按原规则处理。

## 低耦合与快速退出

Mock 的接入和拆除均限定在数据访问边界与开发配置中：

- 页面、组件、业务 hook/store、校验和流程规则不感知 Mock。不从这些位置
  导入 fixture/handler，不判断 `isMock` 或场景，不传递 `mockMode`、`mockId`
  等专用参数，也不向正常业务返回值塞入 Mock 标识。业务开发本身需要的
  页面或规则改动照常实施，不能把“Mock 无业务层改动”误解为不做业务功能。
- 复用正常数据访问接口；真实适配器与 Mock 适配器提供相同的业务输入输出。
  数据源只在已有配置/组装入口选择，业务调用方无需随模式切换而改变。
  Query 请求定义所需的声明元数据留在其数据访问层，不把 Mock 分支逻辑
  加入 Query 的业务编排或状态管理。
- Mock 数据、handler、最小模拟状态和启动依赖放在可单独移除的开发专用
  文件/配置中，按功能或 Query 归属组织。业务运行代码不直接依赖这些实现；
  不把 Mock 状态混入业务 store，不复制整套业务流程或建设全局模拟后台。
  沿用既有适配边界即可，不为隔离而机械新增多层抽象。
- 在同一 `mockModules.paths` 和实施依据中记录独立 Mock 文件、数据源选择
  入口及退出时需恢复/移除的绑定；不另建清理台账。Query Contract 的生成
  工件按其实际配置定位，不能靠手改生成文件绕过原始声明。
- 正式接口就绪后，恢复真实数据源、在数据适配层处理契约映射并补真实验证；
  删除/隔离该功能的 fixture、handler、模拟状态、开发配置与启动绑定。
  仅因退出 Mock，不应要求修改页面调用、业务函数签名、交互流程或业务规则。
  原契约/业务需求确有变化时说明其独立依据，不能归为 Mock 拆除成本。

评审核实数据源选择和业务调用之间的依赖方向，以及上述文件/入口能否独立
拆除。页面隐藏了控件但业务代码仍依赖 Mock，不满足低耦合；只关闭开关也
不等于完成退出，仍遵守后续源码和生产制品检查。

## 先识别实际接入程度

核实目标消费点的依赖/实际安装版本、Query 定义、执行入口、开发配置和请求
去向。用户已说明接入 Query 时优先沿其现有链路查证，不重新选型或另建 Mock
体系；依赖名存在不等于该消费点已接通。采用以下路径：

| 实际状态 | 本轮落点 | 必须核实 |
| --- | --- | --- |
| Query 与 Query Contract Mock 已接通 | 复用现有 Query、身份绑定、Mock 工件/handler 和开发代理/服务，只补本功能数据或配置 | 当前调用命中对应工件/handler，结果仍经现有数据映射、缓存和页面消费 |
| 已使用 Query / QueryAdapter，但未接通 Query Contract Mock | 优先使用现有执行器/数据源的可替换入口；项目已有可用 Contract Mock 链路、仅该消费点缺绑定时补必要绑定 | 当前包公开支持的替换能力、契约条件和真实请求边界；只安装包、metadata 或 header 均不证明命中 |
| 未接入 Query，但已有项目 Mock | 复用当前 handler、代理或功能数据 provider | 适用范围、选择规则、启停方式与实际命中 |
| 未接入 Query，也没有 Mock 设施 | 在本功能现有数据访问接口后提供独立 provider/adapter，由开发配置组装 | 页面消费形状、正常交互所需最小状态和开发配置入口 |

接入状态、版本和配置证据写入同一 Plan/brief 的实施依据。不能只因需要 Mock
就安装 Query Contract、迁移请求栈或搭建全局场景平台。用户明确要求接入时，
把实际必要改动纳入原方案；未接通就保留缺口，不假称已经可用。

## 先定契约边界，再选实现

| 条件 | 实现方式 | 证明范围 |
| --- | --- | --- |
| 业务已明确，接口机器事实未知 | 在最近的功能数据入口提供前端业务/展示模型场景数据 | UI、交互和模拟状态；不证明请求/响应或真实保存 |
| 正式契约已确认，服务暂不可调用 | 在现有请求边界按已知契约模拟响应 | 前端消费契约的路径；不证明服务、权限和真实业务链路 |
| 项目采用受管理 Draft 且机器事实已确认 | 按现有 Draft 生命周期生成类型与 Mock | 已确认 Draft 范围；保留正式契约迁移与发布限制 |

契约未知时不猜 method、URL、参数位置、DTO、类型、传输枚举、鉴权或
状态码，不为启动 HTTP Mock 随手生成 OpenAPI。Draft 必须同时满足
[契约阶段门禁](../skills/writing-plans/references/api-contract-stages.md)，包括
机器事实已确认、项目产物路径规则和可追踪关联。

以上契约条件适用于所有接入状态。使用 Query 本身不产生后端契约；机器事实
未知时，功能模型数据放在现有数据源边界，不为了经过 HTTP Mock 而虚构 URL、
响应包装或 Draft。后续契约补齐时显式映射，不能将本地模型当作后端已确认。

## 已接入 Query 体系的实现

### Query Contract Mock 已接通

1. 沿已有页面消费入口定位 Query、当前身份绑定、契约来源、工件/handler、
   开发服务和代理配置。复用现有查询与变更操作，不因 Mock 重写 Query key、
   缓存策略、字段映射、失效刷新或页面状态管理。
2. 静态正常响应优先使用现有 Mock 工件的数据配置；新建/编辑后需要列表和
   详情回显时，才在既有 handler/数据层补本功能范围的最小内存状态。无需
   状态的读取不增加状态服务，不在页面导入 fixture 绕过已接通的 Query 链路。
3. 启停、数据集及必要重置沿项目开发配置或现有工具入口管理。未明确要求
   多场景时只维护正常数据，不生成场景切换器或故障开关，不因 Mock 增加业务层改动。
4. 以实际安装版本的 Package Contract 和配置为准，查清契约同步、工件生成、
   服务启动与代理分别由谁执行，复用其公开能力；不复制旧版 CLI/Vite Recipe，
   不要求项目不存在的统一目录或字段。
5. 核实实际请求身份与命中证据。若该版本以 `X-Query-ID` 选择工件，核对 Query
   定义、metadata/header 和工件 ID 一致，不能只按 method/path 推断命中；若
   工件/handler 变更须重启，按该版要求处理。不能把类型或 build 通过当作命中。

缺工件、handler/transformer 异常可能触发某些版本的真实上游透传，必须核实
当前行为。仅当该版公开 API 支持时使用 `missingArtifact: 'error'` 等配置，
并查清它是否覆盖 handler 异常。声明为本地 Mock 的操作不能悄悄访问真实业务；
按既有能力配置隔离/明确失败。此处是数据源隔离，不要求新增业务异常场景。
`@api-mock true` 或 `release-check` 通过不证明符合本规范的生产禁令。

### 仅接入 Query / QueryAdapter，Mock 尚未接通

保留现有 Query 和页面调用，在该版本支持的执行器、数据 provider 或已有
适配边界替换正常数据来源。需要可写交互时，状态仍由数据层持有，沿原有
刷新/失效逻辑回显。不得臆造 Query 的配置选项或公共 API；能力不足时说明
缺口，只补本轮必要的适配。用户指定使用 Query Contract 时按其实际契约和
接入要求补齐，不用页面内 fixture 旁路冒充接入完成。

## 未接入 Query 体系的实现

- 已有 Mock handler/代理时复用其选择和配置方式。正式契约已确认才在请求
  边界模拟 HTTP；准确匹配服务、method、path 和必要条件，不扩大到无关请求。
- 没有现成设施时，在本功能已有数据访问接口后提供独立的最小替换，由开发
  配置组装；业务 store/service 继续调用同一接口，不包含 Mock 实现或分支。
  业务页面继续接收原有业务模型；不要在各组件添加 `if (mock)`、散放 fixture，
  或为单个页面建立多层 service、通用 Mock server 和场景管理平台。
- 启停和数据选择集中在开发配置或数据源组装处。不要为开启 Mock 新增业务
  路由、页面 query 参数、浏览器存储开关或按钮；已有项目配置机制可继续
  复用，须核实开发边界及生产排除，不能保留生产可重新激活的入口。
- 后续对接只替换对应数据源及真实契约映射，保留业务页面和已完成交互。
  范围只到本轮功能，不顺手迁移整个项目到 Query 或重构全局请求设施。

## 明确标识与实现边界

每个 Mock 模块使用稳定 `MOCK-*` 编号及机器可识别的 `MOCK_ONLY` 标识。
在数据层代码/配置、Plan/摘要和交接中关联同一编号；记录功能和 Task 范围、路径、
实现方式、场景、开启方式、真实请求边界、退出条件、验证局限和授权证据。
内置检查器支持以下明确声明；普通页面显示文字或检测代码中的标识字符串
不是 Mock 模块声明：

```ts
/** @mock-module MOCK-001 MOCK_ONLY */
```

JSON 配置可使用同一对象内的 `id: "MOCK-001"` 和 `marker: "MOCK_ONLY"`。
Query Contract 的 `@api-mock true` 声明还须在其源码位置关联同一稳定 Mock ID，
不能仅按目录登记。项目采用其他声明语法时，须提供受审查的识别适配和
验证；检查器未识别不能据此认定无 Mock。不得只在聊天中声明或仅靠文件名。

- 仅按明确操作启用。普通 HTTP handler 精确匹配已确认的服务、method、
  path 等；Query Contract 按其版本支持的身份选择。未匹配请求执行项目
  明确的报错/透传策略，不返回通用成功。
- 代码/配置与开发日志应能定位当前数据源和命中操作；混合模式在同一记录中
  逐操作说明真实 mutation 边界。读取已 Mock 不能掩盖保存仍实际写入后端，
  也不能用页面标签代替这项核实。
- 禁止真实请求失败后 `catch → fixture`，禁止把超时、鉴权失败、保存失败
  自动降级为 Mock 成功。有明确异常模拟要求时才增加受控场景，不依赖 handler
  意外异常构造该场景。

## 场景、状态与验证

`mockModules.scenarios` 默认只列本轮实际提供的正常业务场景，一个正常场景
即可，不要求异常场景数量。使用确定的 fixture/seed 和数据配置，不增加随机
失败、人工延迟或概率触发。需要异常时，在原 Plan/brief 引用用户、PRD 或已
确认验收的明确依据，再列对应操作、数据/配置、预期及恢复方式；不另建审批流程。

业务规定的“未通过可重提”“禁用”“余额不足”等状态和输入校验，按已明确的
需求实现；它们不自动授权额外模拟接口 500、网络超时、鉴权失败或脏数据。
正常筛选自然无结果时沿用正式空态，不为此另建异常 fixture 或场景开关。
页面原有或需求要求的加载、错误反馈和防重逻辑照常保留；不主动 Mock 异常
不等于删除这些产品行为，也不阻止按实际代码风险执行必要的隔离/单元检查。

两页有新建/编辑→返回列表→详情回显时，使用功能范围受控的内存状态形成
正常交互，明确刷新、重启或配置重载的重置行为，不模拟未请求的完整后端。
只有确需切换数据源/已要求场景时才处理切换；通过配置或数据层清理/隔离
缓存、加载、错误和分页状态，防止旧响应或旧 Mock 数据冒充真实接口结果。
不因登记 activation/重置方式就新增页面按钮或场景管理能力。

分别记录功能 Mock、HTTP Mock、契约检查和真实联调的实际结果。Mock
保存成功不等于真实保存，类型或 build 通过不等于接口已命中；验证必须
检查实际数据来源与局限。

## 测试交付：默认禁止，精确确认后才允许

Mock 默认仅本地使用。普通“开发”“直接提测”和测试构建默认项不能授权
把 Mock 带到测试分支或测试环境。首次 Git 交付写入前，确定清单必须列出：

- 准确 Mock 编号、功能/路径/操作和源版本或待交付差异。
- 实际目标测试分支、测试环境及本轮交付操作。
- 是否明确允许这些 Mock 进入该测试环境；默认否。
- 测试用途、真实请求边界、尚未覆盖的验收和退出条件。

取得人类对完整当前内容的明确确认后，才可执行该含 Mock 测试交付；没有
回复、普通确认布尔值或实现通过都不能代替。已获确认且范围、版本绑定、
环境和操作仍匹配时复用授权，不按技能重复询问。实质变化刷新清单确认；
如拟携带，预览应明确写出“拟允许本次所列 Mock 测试交付，待确认”；清单仍写
“否”时的普通“确认”不能变成 ALLOW，明确拒绝也不能被默认提测覆盖。
机械派生提交/合并 SHA 必须有原已批准差异到新版本的等价/包含关系证据，
不能把所有 SHA 变化都视为自动获准。

测试环境通过配置、命中日志、测试记录与所选 Wiki 标明“含 Mock”、对应
范围和真实链路未覆盖项，业务页面仍遵守默认不展示 Mock 工程信息的约定。
只报告本轮获准的模拟验证，不把整条需求、Task
或真实集成登记为已验收。明确拒绝或无法核实授权时，停止含 Mock 的 Git、
构建/部署和登记，不擅自切换默认选择继续。

运行时通过共享 [Mock 安全检查](../scripts/mock-safety.mjs)核实清单、受检
路径与当前来源版本/内容，并在各写入边界重新读取；会话不能缓存旧检查
作为永久授权。输入结构和错误结果以该检查器为准，不用 Plan 中的状态或
手填 `confirmed=true` 代替实际检查与人类确认来源。

清查必须绑定项目已核实的完整运行目录 `runtimePaths`、Mock/启动配置入口、
全部待交付差异、未跟踪文件及运行目录内可能加载的忽略文件。不能只检查
本轮改动目录；内置声明扫描不是完整导入图或运行语义证明，还须提供项目
清单、入口/引用和启用路径的查证依据。无 Mock 的项目也需明确清查，缺记录
不能按空清单放行。

源版本提交/合并后若目标带有额外内容，须针对准确不可变目标 revision 重做
清查并绑定 Git 交付回执；核对已批准源码和 Mock 配置未被改变，以及目标新增
内容的依赖/Mock 影响。仅有祖先包含关系不等于内容等价或授权仍有效。

## 生产门禁：不得携带或启用 Mock

生产制品和业务运行链路禁止 Mock 模块、fixture、handler、示例数据、Mock
服务启动入口及启用机制。关闭默认开关、隐藏入口、删除标识或“开发者已
确认”不能证明清理完成；生产也不能经参数或浏览器存储重新开启 Mock。
开发工件可在仓库的明确隔离位置保留，但不得进入生产制品或运行依赖。

正式分支 MR/合并和正式发布分别检查，独立 helper 与会话入口都须执行：

1. **源码与构建路径检查**：核实当前范围的 Mock 清单、代码引用、构建配置、
   真实替换及必要验收；本轮生产范围仍有活跃 Mock、清单缺失/过期或无法
   证明开发工件已隔离时拦截。
2. **最终制品检查**：对准确构建版本的制品与运行入口验证，不得携带上述
   工件或可激活路径。只搜 `mock` 字符串不足以证明不存在 Mock。
3. **先检查后发布**：项目的实际发布入口须在部署/上传/发包前执行制品
   检查，检查非零退出时停止后续发布。构建前核实项目脚本、配置和接入
   源码；构建后核对本次真实制品回执，不能提前声称未来制品已通过。

Mock 检查由项目脚本执行。可沿用已有的有效检查器，或将
[项目检查模板](../assets/project-mock-check/check-mock.mjs)和
[配置示例](../assets/project-mock-check/config.example.json)复制到项目后，按
实际源码、产物、运行入口和 Mock 隔离方式补齐并评审。模板不依赖 Query
Contract 或本机插件，不自动为业务项目安装脚本，也不修改 Jenkins Job。
不能只复制空配置或检查 `mock` 字符串就声称已接入。

模板配置须显式记录 `sourcePaths`、`artifactPaths`、`mockModuleIds`、
`forbiddenPaths`、`forbiddenContent` 和 `runtimeRules`。各阶段受检根必须
非空、存在并完整递归扫描，不提供任意排除目录；禁止路径是项目相对字面
路径/目录，禁止内容是项目专属精确字符串，不把常见单词作为通用判据。
运行配置规则按 `source|artifact` 阶段指定 JSON 路径和禁止保留的配置键；
键即使值为 false 也可能保留重新开启机制，不能仅以默认关闭放行。
导入链、生产入口、打包隔离和实际配置覆盖仍须项目评审，模板扫描不替代
这些事实。归档格式不在模板适配范围，应检查打包前最终 staging，并证明
实际上传/发包/部署使用同一内容；不能只扫描压缩文件的外壳。

例如将文件纳入项目的 `scripts/check-mock.mjs` 和
`scripts/mock-check.config.json` 后，将 `MOCK_CHECK_SOURCE_SHA` 设为已核实的
准确提交 SHA，源码检查的直接调用是：

```sh
node scripts/check-mock.mjs --phase source --config scripts/mock-check.config.json --source-sha "$MOCK_CHECK_SOURCE_SHA"
```

项目真实 CI 发布入口在产物生成后、发布前执行：

```sh
node scripts/check-mock.mjs --phase artifact --config scripts/mock-check.config.json --source-sha "$MOCK_CHECK_SOURCE_SHA" --job-url "$JOB_URL" --build-number "$BUILD_NUMBER"
```

入口必须检查退出码，失败立即停止后续发布。命令示例本身不证明已接入；
本地可执行源码/制品验证，发包或部署仍通过 Jenkins。制品阶段核对实际 Git
HEAD、受检源码的完整文件集合和字节必须与准确提交一致，并核实 Job 和构建
身份。构建改写源码、新增或删除受检文件时，在发布前失败停止；不能等发布
结束后才发现指纹不符。回执的源码内容指纹还须与触发前源码检查一致。

正式发布使用 [project-mock-gate.mjs](../scripts/project-mock-gate.mjs) 的
`projectMockGate` 契约，详见[脚本交付规范](scripted-delivery.md)：

- **源码阶段**：从准确 Git 提交导出临时快照，实际运行受审项目脚本的
  `source` 检查；校验脚本、配置指纹和 `MOCK_SOURCE_GATE` 结果。失败、版本
  不符或缺检查时，在 Jenkins 触发前停止；源码通过不表示制品已通过。
- **发布接入**：核实项目发布入口的固定版本源码和内容指纹，证明制品检查
  位于实际发布前、失败停止且没有绕过路径。接入可以位于已核实的 npm
  lifecycle、项目发布脚本或固定版本 Jenkinsfile；须审查真实调用关系，不能
  以自报布尔值、日志标识或命令文本中出现脚本名代替。评审的
  `filesFingerprint` 绑定全部入口文件的路径和内容指纹；PLAN 返回的
  `projectMockGateHash` 必须原样带入正式 EXECUTE。构建后检查器/配置的
  实际字节仍须与准确 Git 版本一致。评审须证明检查后发布同一份 staging，
  不得再修改内容、换包或走绕过路径；版本或接入变化后刷新受影响证据。
- **制品阶段**：Jenkins 沿用项目现有发布入口，对本次准确制品和运行配置
  执行 `artifact` 检查；非零退出必须阻止发布。成功后回读唯一
  `MOCK_PRODUCTION_GATE`，核对准确源码 SHA、Job、构建号、脚本/配置与制品
  指纹；其 `sourceFingerprint` 必须等于触发前实际源码检查回执的同名字段。
  队列身份来自本次准确构建读回，不假定 Jenkins 提供 `QUEUE_ID`
  环境变量。只有准确构建、源码和回执全部匹配才可报告发布成功。

发布流程不要求读取 Jenkins XML，也不解析 Groovy 或限制流水线必须是内联
单 stage。XML 读取权限不是 Mock 接入条件。项目尚无脚本、制品检查或有效
发布接入时，准确报告所缺项目能力并停止正式发布；不能将其报成配置读取
403，也不能因去掉 XML 校验而假定该项目已经具备检查能力。

现有 `release-check` 是补充检查，不能替代以上门禁。任何“测试确认”均不
授予生产豁免，测试环境可用或 Mock 验证成功也不能放行上线。

项目检查器、配置及发布接入证据均绑定准确仓库、不可变源码版本与内容指纹；
不能用旧版本的正确脚本为当前版本背书。插件通过结构化参数直接启动项目
检查器，不执行调用方拼接的 shell。配置、依赖和实际发布入口变化后刷新
受影响评审，保留其他仍有效的业务确认。

## 替换、退役与续接

接口就绪后恢复原分支、Task 和 Plan，对比正式契约与业务约定，按低耦合边界
逐操作替换数据源并拆除独立 Mock 绑定，更新数据适配层的真实映射及异常路径，
清理/隔离缓存并补受影响真实验证；不把 Mock 拆除扩成业务层重写。
其他操作可继续 Mock，但不得宣称全部真实接入。

退役记录保留原 `MOCK-*` 身份及 `exitEvidenceRefs` 中真实替换、运行引用与
开启入口清理的证据；
`retired` 不能仅靠修改状态声明，也不能代替后续准确生产制品检查。尚未
构建时保留制品门禁待执行，不能因等待未来证据而伪造通过。技术事实补齐
不重开未变化业务结论；原授权仅含 Mock，现在新增真实接入或交付终点变化，
仍按[确定清单](execution-checklist.md)为变化补充授权，不重跑整个需求流程。
