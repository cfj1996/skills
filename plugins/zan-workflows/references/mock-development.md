# 跨项目 Mock 开发与交付门禁

本规范适用于有无 Query Contract 的项目。统一行为、记录和退出要求，
实现绑定沿用项目实际能力；不因页面任务强制安装插件、迁移请求体系或
建设全局 Mock 平台。正式记录使用[评审模型](../skills/writing-plans/references/page-review-standard.md)
的 `mockModules`，与[外部数据与依赖](external-data-dependencies.md)及原 Plan
关联；无正式 Plan 时在原执行摘要中表达，不增加台账。

## 先定契约边界，再选实现

| 条件 | 实现方式 | 证明范围 |
| --- | --- | --- |
| 业务已明确，接口机器事实未知 | 在最近的功能数据入口提供前端业务/展示模型场景数据 | UI、交互和模拟状态；不证明请求/响应或真实保存 |
| 正式契约已确认，服务暂不可调用 | 在现有请求边界按已知契约模拟响应 | 前端消费契约的路径；不证明服务、权限和真实业务链路 |
| 项目采用受管理 Draft 且机器事实已确认 | 按现有 Draft 生命周期生成类型与 Mock | 已确认 Draft 范围；保留正式契约迁移与发布限制 |

契约未知时不猜 method、URL、参数位置、DTO、类型、传输枚举、鉴权或
状态码，不为启动 HTTP Mock 随手生成 OpenAPI。Draft 必须同时满足
[契约阶段门禁](../skills/writing-plans/references/api-contract-stages.md)，包括
机器事实已确认、项目产物路径规则和可追踪关联。

先核实项目当前版本、配置、请求入口和运行能力。已接入 Query Contract
Mock 的沿用该链路；已有其他 Mock 体系的沿用现有 handler/代理；均无时
在本功能现有数据入口或 service 边界提供可替换实现。安装了 Query Adapter
或 Query Contract 依赖，不能证明 Mock 已接通。

## 明确标识与实现边界

每个 Mock 模块使用稳定 `MOCK-*` 编号及机器可识别的 `MOCK_ONLY` 标识。
在代码/配置、Plan/摘要和交接中关联同一编号；记录功能和 Task 范围、路径、
实现方式、场景、开启方式、真实请求边界、退出条件、验证局限和授权证据。
内置检查器支持以下明确声明；普通页面显示文字或检测代码中的标识字符串
不是 Mock 模块声明：

```ts
/** @mock-module MOCK-001 MOCK_ONLY */
```

JSON 配置可使用同一对象内的 `id: "MOCK-001"` 和 `marker: "MOCK_ONLY"`。
Query Contract 的 `@api-mock true` 声明还须在其源码位置关联同一稳定 Mock ID，
不能仅按目录登记。项目采用其他声明语法时，须提供受审查的识别适配和
验证；检查器未识别不能据此认定无 Mock。不得只在聊天中声明或仅靠文件名。

- 页面尽量走同一功能入口，模拟分支集中在数据提供方或 handler；不在
  各页面散落 `if (mock)`，也不为一个功能机械增加多层 service。
- 仅按明确操作启用。普通 HTTP handler 精确匹配已确认的服务、method、
  path 等；Query Contract 按其版本支持的身份选择。未匹配请求执行项目
  明确的报错/透传策略，不返回通用成功。
- 显示开发调试 Mock 标识，能够确认当前场景、命中操作及仍然真实调用的
  操作。混合模式必须说明真实 mutation 边界，不能让“页面 Mock”掩盖保存
  实际写入后端。
- 禁止真实请求失败后 `catch → fixture`，禁止把超时、鉴权失败、保存失败
  自动降级为 Mock 成功。模拟失败使用受控场景，不依赖 handler 意外异常。

## 场景、状态与验证

按本轮行为选择正常、空态、加载/延迟、分页边界、详情缺失、校验、成功/
失败、防重复提交等场景，不为不适用行为增加固定数量测试。使用固定
fixture/seed 和显式场景选择，避免结果随机变化。

两页有新建/编辑→返回列表→详情回显时，使用功能范围受控的内存状态形成
一致演示，明确刷新、重启和场景切换的重置行为，不模拟未请求的完整后端。
切换场景或数据源时清理/隔离缓存、加载、错误和分页状态，防止旧响应或
旧 Mock 数据冒充真实接口结果。

分别记录功能 Mock、HTTP Mock、契约检查和真实联调的实际结果。Mock
保存成功不等于真实保存，类型或 build 通过不等于接口已命中；验证必须
检查实际数据来源与局限。

## Query Contract 的项目绑定

以项目安装版本的 Package Contract 和真实配置为准，不复制固定 CLI 参数
或旧 Vite Recipe。当前本地 `0.7.1` 包文档采用独立 Mock 服务：契约同步、
Mock 工件同步和服务启动是独立操作，`X-Query-ID` 是 Mock 工件唯一选择键，
工件/handler/配置变更后重启读取；method/path 不选择工件。

该版本缺少工件默认可能警告后透传，handler/transformer 异常也可能透传。
声明为 Mock 的操作必须验证实际命中；版本支持时可用
`missingArtifact: 'error'` 阻止缺工件透传，但它不覆盖所有 handler 异常路径。
`@api-mock true` 自身不阻断 `release-check`；该检查通过不证明符合本规范的
生产禁令。项目能力或版本不同时，核实等价绑定，不假称支持未验证能力。

## 测试交付：默认禁止，精确确认后才允许

Mock 默认仅本地使用。普通“开发”“直接提测”和测试构建默认项不能授权
把 Mock 带到测试分支或测试环境。首次 Git 交付写入前，确定清单必须列出：

- 准确 Mock 编号、功能/路径/操作和源版本或待交付差异。
- 实际目标测试分支、测试环境及本轮交付操作。
- 是否明确允许这些 Mock 进入该测试环境；默认否。
- 测试用途、真实请求边界、尚未覆盖的验收和退出条件。

取得人类对完整当前内容的明确确认后，才可执行该含 Mock 测试交付；没有
回复、普通确认布尔值或实现通过都不能代替。已获确认且范围、版本绑定、
环境和操作仍匹配时复用授权，不按技能重复询问。实质变化刷新清单确认；
如拟携带，预览应明确写出“拟允许本次所列 Mock 测试交付，待确认”；清单仍写
“否”时的普通“确认”不能变成 ALLOW，明确拒绝也不能被默认提测覆盖。
机械派生提交/合并 SHA 必须有原已批准差异到新版本的等价/包含关系证据，
不能把所有 SHA 变化都视为自动获准。

测试环境持续显示 Mock 标识，测试记录与所选 Wiki 标注“含 Mock”、对应
范围和真实链路未覆盖项。只报告本轮获准的模拟验证，不把整条需求、Task
或真实集成登记为已验收。明确拒绝或无法核实授权时，停止含 Mock 的 Git、
构建/部署和登记，不擅自切换默认选择继续。

运行时通过共享 [Mock 安全检查](../scripts/mock-safety.mjs)核实清单、受检
路径与当前来源版本/内容，并在各写入边界重新读取；会话不能缓存旧检查
作为永久授权。输入结构和错误结果以该检查器为准，不用 Plan 中的状态或
手填 `confirmed=true` 代替实际检查与人类确认来源。

清查必须绑定项目已核实的完整运行目录 `runtimePaths`、Mock/启动配置入口、
全部待交付差异、未跟踪文件及运行目录内可能加载的忽略文件。不能只检查
本轮改动目录；内置声明扫描不是完整导入图或运行语义证明，还须提供项目
清单、入口/引用和启用路径的查证依据。无 Mock 的项目也需明确清查，缺记录
不能按空清单放行。

源版本提交/合并后若目标带有额外内容，须针对准确不可变目标 revision 重做
清查并绑定 Git 交付回执；核对已批准源码和 Mock 配置未被改变，以及目标新增
内容的依赖/Mock 影响。仅有祖先包含关系不等于内容等价或授权仍有效。

## 生产门禁：不得携带或启用 Mock

生产制品和业务运行链路禁止 Mock 模块、fixture、handler、示例数据、Mock
服务启动入口及启用机制。关闭默认开关、隐藏入口、删除标识或“开发者已
确认”不能证明清理完成；生产也不能经参数或浏览器存储重新开启 Mock。
开发工件可在仓库的明确隔离位置保留，但不得进入生产制品或运行依赖。

正式分支 MR/合并和正式发布分别检查，独立 helper 与会话入口都须执行：

1. **源码与构建路径检查**：核实当前范围的 Mock 清单、代码引用、构建配置、
   真实替换及必要验收；本轮生产范围仍有活跃 Mock、清单缺失/过期或无法
   证明开发工件已隔离时拦截。
2. **最终制品检查**：对准确构建版本的制品与运行入口验证，不得携带上述
   工件或可激活路径。只搜 `mock` 字符串不足以证明不存在 Mock。
3. **先检查后发布**：正式 Jenkins 路径须在部署/上传/发包前执行并强制消费
   制品检查结果。构建前可以核实该门禁配置和源码，不能伪造未来制品已通过；
   不能证明失败会拦截实际发布时，不触发可能先发布后检查的任务。

当前内置 Jenkins 适配必须读取并绑定实际 `CONFIG_XML`，只接受受支持的
`flow-definition > definition[class=org.jenkinsci.plugins.workflow.cps.CpsFlowDefinition]`
下唯一 `script` 的内联 Pipeline、单 stage；XML 注释、其他配置节点和 SCM
定义不提供执行证据。先 `deleteDir()` 清理 CI 工作区，再显式 GitSCM
checkout 本次准确仓库及不可变发布 SHA，随后唯一 `sh` 严格执行
`检查器完整性校验 && checkCommand && deployStep`；可选 `buildCommand` 在该校验
之前执行。完整性校验由 helper 按受审路径和指纹固定推导为：

```sh
sha256sum -- <scriptPath> | grep -Fx -- "<contentHash>  <scriptPath>"
```

指纹与路径之间固定两个空格；CI 需要 `sha256sum` 和 `grep`，缺失或检查器被构建
改写时均停止，不执行后续检查或部署。检查器同仓同 SHA 的证据不能
代替实际 checkout，浮动分支、旧工作区、缺少清理或身份不符都在触发前阻断。
普通 Job 元数据、自报 VERIFIED、可跳过的
`if/when`、额外发布路径、并行或 SCM 间接流水线均不能放行；复杂流水线
在触发前报告缺少受审查适配，不能先触发后观察。构建后还须核实与本次
源码/Job/队列/构建及制品指纹绑定的唯一 `MOCK_PRODUCTION_GATE` 检查回执。

现有 `release-check` 是补充检查，不能替代以上门禁。任何“测试确认”均不
授予生产豁免，测试环境可用或 Mock 验证成功也不能放行上线。

当前受支持的相对路径检查器必须与本次发布仓库及准确源码 SHA 一致，并现场
核实脚本内容指纹和职责评审证据；不能用旧版本的正确脚本为当前版本背书。
检查命令仅支持 `node|python3|sh|bash` 后跟准确脚本相对路径的直接调用，不带
解释器选项或额外参数。`echo`、`cat` 或 `node --check` 提到脚本路径不表示执行。
外部检查器或额外 checkout 没有显式固定版本适配时，在触发前阻断。

## 替换、退役与续接

接口就绪后恢复原分支、Task 和 Plan，对比正式契约与业务约定，逐操作
替换数据源，更新真实映射及异常路径，清理/隔离缓存并补受影响真实验证。
其他操作可继续 Mock，但不得宣称全部真实接入。

退役记录保留原 `MOCK-*` 身份及 `exitEvidenceRefs` 中真实替换、运行引用与
开启入口清理的证据；
`retired` 不能仅靠修改状态声明，也不能代替后续准确生产制品检查。尚未
构建时保留制品门禁待执行，不能因等待未来证据而伪造通过。技术事实补齐
不重开未变化业务结论；原授权仅含 Mock，现在新增真实接入或交付终点变化，
仍按[确定清单](execution-checklist.md)为变化补充授权，不重跑整个需求流程。
