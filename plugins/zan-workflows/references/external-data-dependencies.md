# 外部数据与依赖

确定清单、Plan、评审面板和实施交接共用本规范。外部依赖是同一份方案中的
事实记录，不是另一份任务台账，也不自动创建 Task、修改工时或授予执行权限。
正式结构由[评审模型](../skills/writing-plans/references/page-review-standard.md)
定义；小范围工作在原 `implementationBrief` 中表达相同事实，不强建正式 Plan。

## 分开记录业务决定、外部事实和实施依据

| 内容 | 记录位置 |
| --- | --- |
| 范围、字段业务含义、角色行为、业务规则、用户反馈和验收结果的定义 | 主表“需求待确认”及模块业务问题 |
| API method/path、请求响应字段、类型和传输枚举、凭据配置引用、环境、账号权限及外部服务 | “外部数据与依赖” |
| 组件选型、内部代码落点、状态归属及实现方案 | 原实施依据与实现阻塞 |

例如“审核状态有哪些业务含义、何时允许编辑”仍是业务决定；后端字段名和
枚举 code 是契约事实。外部事实揭示业务语义冲突时，重开对应业务问题；
不能仅按“字段”一词分类，也不能为缩小业务问题列表而隐藏真实冲突。

`module.questions` 只保留尚未解决的业务决定。外部缺口移入本模块后，仍须
关联受影响步骤及验收，并导出对应实施阻塞；业务问题为空不代表可实施。

## 一项依赖，一份可核验事实

先查项目声明的权威来源；需要真实新增或变更 API 消费时，沿用
[正式契约搜索顺序](../skills/writing-plans/references/api-contract-stages.md)。
Agent 能查证的先查，不把技术查证转交用户审批。一个来源已充分回答当前
问题即停止，不为完整性遍历所有系统。

每项依赖使用稳定 `EXT-*` 编号，记录：类别、摘要、已知事实、来源、适用
环境、状态、责任方、可核验补齐条件、阻塞阶段，以及关联功能、步骤/Task、
验收和证据。记录已就绪与未就绪事实，不能仅保存“后端未好”。

- 同一 API 供两个页面使用时，只记录一次，再关联两个消费点。正式契约
  正文保留在权威来源，本记录引用 API/证据，不复制第二套字段表。
- `unverified` 表示尚未核实；`missing` 必须有已核实缺失的依据；`ready`
  表示当前环境及用途的补齐条件已有证据；`not-applicable` 必须有不适用依据。
  检索为空、读取失败或无权限不能证明接口不存在、Key 未配置。
- 凭据只记录配置项名称、保管位置引用、环境、所需权限和访问验证状态。
  不读取无关凭据，不把 API Key、token、密码或其实际值写入 Plan、fixture、
  日志、评论或对话，不要求用户把值贴进聊天。
- 文档已出、配置已完成、服务可访问和业务链路已验收是不同事实。只按
  当前补齐条件更新状态，不能仅凭一条“已配置”解除真实调用验收阻塞。

## 按本轮步骤判断就绪

需求确认、依赖就绪和执行授权分别核对。`executionScope` 指定本轮阶段及
选定功能/任务；依赖只阻塞它实际关联且列入 `blockingStages` 的工作。
允许的阶段和字段以正式评审模型为准，不另建流程状态机。

| 条件 | 可以推进 | 保留的阻塞 |
| --- | --- | --- |
| 业务明确、契约未出，已批准 UI/Mock | 指定 UI/Mock 交互和场景 | 未知契约对应的真实接入、联调与验收 |
| 契约已确认、后端服务未部署 | 不依赖运行环境的请求适配、类型与映射 | 真实联调及其验收 |
| Key 已配置、访问验证仍失败 | 不依赖该调用的独立工作 | 相关调用和依赖它的验收/交付 |

不能把未知 method/path/Schema 写成临时事实来清空阻塞。已批准的 Mock
范围按[跨项目 Mock 规范](mock-development.md)执行；真实集成范围不得自行
降为 Mock。只停受影响步骤，独立、就绪且已授权的工作可以继续；整轮必需
工作未完成时，仍不得报告整条需求已完成或已验收。

Mock 的 `authorizationEvidenceRefs` 只能引用 `kind=human-confirmation` 的证据，
主流程还须核实真实人类原文与批准范围；普通原型/文档引用不授予 Mock 实施
或测试交付权限。技术依赖证据与授权证据分开，不互相替代。

正式模型需要 `dependencyReview` 的明确查证结论和证据。空数组、旧模型
未记录或面板未显示，不等于“没有外部依赖”；旧记录可以读取和继续评审，
进入实施前须补齐当前范围的查证。已保存的阶段 Plan 可以保留阻塞，保存
不表示就绪，也不放行提测或生产。

## 续接、变化和交付

接口补齐后，恢复原需求、分支、Task/Plan、代码及人工修改，比较正式契约
与原业务约定，更新原记录和引用。技术事实补齐只刷新受影响实施证据、
验收及保存确认，不重置未变化的业务结论。

- 原有效执行清单已涵盖接入，范围、关键方案和实际操作未变时，解除
  对应技术阻塞后继续，不因阶段切换重新拆任务或重复业务确认。
- 原清单仅授权 Mock，现在新增真实接入，或引出业务/关键方案/人员工时/
  交付操作变化时，按[清单规则](execution-checklist.md)展示完整当前内容，
  为变化补充确认。保留已完成效果，不重建原分支、Task 或 Plan。
- 依赖来源、环境、契约或代码版本变化使相关证据失效时，只刷新受影响
  检查；不能用旧环境验证、旧接口状态或人工完成标记覆盖当前事实。
- Git 合并形成不同于原源码的目标提交时，使用准确不可变 revision 检查目标
  内容、Mock 配置和依赖范围。原源码被包含只证明祖先关系，不能证明目标新增
  内容没有 Mock 或仍符合原授权；目标证据未核实前停止后续交付。
- 实施结果和提测交接继续携带同一依赖关系、真实验证及遗留条件。Wiki
  被选中时修订原页当前条目的过期说明。Mock 验证不替代真实联调，外部
  依赖记录本身也不授予测试交付或生产发布权限。
