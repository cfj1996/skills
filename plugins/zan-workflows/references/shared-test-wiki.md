# 共用提测 Wiki

## 归属与条目

同一需求或同一 Bug 涉及多个项目、多个原始分支时，默认共用一篇提测子 Wiki。
“两个项目的提测清单”、不同 Jenkins Job、服务类型、负责人、分支或子 Task
均不构成拆页理由。不能自行把共用草案改成每项目/每 Task 一篇。
只有用户明确要求拆分，才展示单独的拆分方案与相应确认；默认 helper 不提供
隐式拆分开关，不能通过改标题或改传 Task ID 绕开共用归属。

- 归属键：`workspaceId + wikiOwner.entryType + wikiOwner.entryId`。
- Story 自身为归属；Task 用精确读回的 `story_id` 找父 Story。`story_id=0`
  的独立 Task 才归属自身；缺字段、无法读取父需求或归属变化必须阻塞。
- Bug 自身为归属，即使有关联 Story，也不能把不同 Bug 自动合成一篇。
- 新页标题取归属需求/Bug 的标题 `MM-DD: 标题`，不加子 Task 的 H5/小程序前缀。
- 一篇页内在 `# 前端` 下按项目/原始分支分列规范条目，各自保留 Job、影响范围、
  人员及业务上线状态/工具版本。条目身份是 `repositoryKey(仓库 URL) + 原始分支`；
  不同仓库允许同名分支。同一仓库的不同原始分支也分别列条目。
- 每次 helper 只选当前一个项目/分支；这不是整篇 Wiki 只能有一个分支的约束。
  使用 `entryRepoUrl`（CLI `--entry-repo-url`）限定项目。已有 `entryHeading`
  可进一步限定精确条目，并保持标题与仓库成对。条目身份重复才是冲突。

## 发现与执行

`ensure-test-wiki.mjs` 的 `ensure` 模式自动执行以下归属发现：

1. 读取本次条目与完整评论；Task 再读父 Story 与其完整评论。
2. 父 Story 尚无提测链接时，按准确 `story_id` 完整分页读取其 Task，再读兄弟
   Task 的完整评论，找历史仅挂在子任务上的链接。无 count 时以短页结束；重复、
   不完整、跨父需求的结果阻塞。不是全空间 Wiki 扫描。
3. 归属与本次工作项/相关子任务的链接只允许一个 Wiki ID。已知归属链接优先复用，
   包括跨月；与当前 Task 的不同链接仍阻塞。历史已分开的多页不能自动删页、
   迁移、覆盖或再建第三页，须另行明确修复范围。
4. 没有链接才查询当前月份及归属标题。标题、仓库、原分支相同都不能证明属于
   同一需求/Bug；发现同名页却没有归属详情/评论或已核实同 Story 子 Task 的
   准确链接时阻塞，不复用、不换标题另建。创建后评论失败，保留实际创建结果，
   通过另行明确的精确目标补链接操作修复，不盲目重试自动创建。
   已有明确归属链接的页面无需预先包含新
   项目/分支，预览返回 `entryOperation=APPEND_ENTRY`、原正文及哈希；先计算并
   确认追加后的完整正文。不能无正文执行后宣称新项目已完成提测。
5. 创建/补充后，先确保归属 Story/Bug/独立 Task 的同 ID 评论并读回，再确保本次
   Task 的同 ID 评论并读回。兄弟 Task 只有实际交付后才补链接，不批量声称已完成。
   `--mode link` 仍只操作本次条目的评论，不扩大独立补链接请求的写入范围。

预览返回 `wikiOwner`、`commentOperations`（全部目标/动作）、`entryOperation`、
准确页 ID/标题/父页/原正文指纹。Task 执行复制 `wikiOwner` 到
`expectedOwnerType/expectedOwnerId`（CLI `--expected-owner-type/--expected-owner-id`），
与目标和正文绑定一起进入确认。归属、目标动作、正文发生变化仍需新计划；后一个
项目不能继续使用第一个项目写入前的旧整页哈希。失败保留实际完成动作，停止后续
Wiki/评论/登记写入，不自动重试。

## 多项目计划与交付

需求/Bug 编排器向 `submitting-for-test` 传入共同归属及参与项目/分支/Task 列表。
每个项目保留自己的 Git/部署计划，共用一个内存中的 `sharedWikiPlan`：归属、
单一目标、各条目仓库/分支/序号、完整合并正文/原指纹、全部评论目标及前置门禁。
不得为同一归属生成多个互不关联的 `CREATE_CHILD` 确认。

- 同一批次先准备所有项目的完整正文和一个共享 Wiki 操作，随全部 Git、部署、
  TAPD 动作一起展示并确认。读不到所需项目事实时先补齐，不按 Task 拆页规避。
- 执行各项目的 Git 和部署门禁后，只有共享正文中涉及的每个项目均通过门禁，
  才调用一次 helper 创建/更新共享页。随后以准确页及新正文指纹为各已交付 Task
  幂等补链接，最后逐项登记；所有项目结果保留同一 Wiki ID 及各自条目身份。
- 同归属的页面写入必须串行；并行只读允许。分轮提测时复用原页，追加新条目或
  对匹配仓库/分支追加影响范围。同一项目不能覆盖其它项目内容。追加项目的 helper 只接受保留原正文、
  在单一位置插入新条目的完整结果，拒绝以新项目正文替换整页。
- 若另一项目已把原 `CREATE_CHILD` 计划落实成页面，旧创建计划立即失效；刷新为
  `REUSE_EXISTING` 及新正文指纹后再确认，不能换标题继续创建。
- `NO_WIKI` 保持跳过；非功能性 `CONTINUE` 只有在已核实归属页及当前仓库/原分支
  条目并保留准确读回时才跳过正文写入。没有历史目标或当前条目时正常准备新建/
  追加草案，不能返回缺少上线交接目标的成功跳过。共用规则不授权
  给未交付项目写完成状态，也不代替实际包发布或 master 包含证据。

上线阶段继续用准确仓库、原分支和条目标题维护该项目状态，不能因为页内有另一个
同名分支就更新错误条目。共用页不是各项目已一起上线的证据。
