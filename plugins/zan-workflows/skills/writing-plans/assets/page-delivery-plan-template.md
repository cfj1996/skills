# 页面交付 Plan

> 一个页面或一个内聚功能模块对应一个 Plan。仅在适用项目 `AGENTS.md` 已确认产物位置规则且用户确认更新 Plan 后创建或更新此文件。

本模板仅用于正式 Plan；小范围工作可使用对话/内存执行摘要。
正式 TAPD Plan 始终遵守任务读回和现有模型校验。
写入前检查：不依赖规划聊天历史，只凭本 Plan、所选任务与引用的项目事实，
能否理解交付行为、排除项、关键选择及完成证据。补充必要内容即可，不为
独立接手检查新建文档或增加审批。

执行确认表固定为“项目｜分支｜交付范围｜实施方案｜验收标准｜待决事项”，
它是本 Plan 的摘要入口，不另存一份清单详情。范围、方案、验收、待决的长内容
在表内写“详见下方 #01”，表下详情标题只用 `### #01`，全清单连续编号、
跨项目不重置，同一详情可复用，短内容不编号。说明内可链接本 Plan 对应章节
或准确行号；首次未保存时展开拟写正文或用已有面板，不虚构链接或提前建文件。
确认说明不再重复“实施方案/验收标准/验证安排/分支安排”分组，本模板正文
仍保留下方正式 Plan 章节和稳定编号。分支格显示新建/复用、完整目标名及基准
ref；当前分支、完整 SHA、原始 payload 和人员字段核验留内部、按需披露。
内部精确校验与授权绑定不变，必要 Task/Plan 写入及人员/工时变更仍按项目说明。
有本轮 Task 时，在清单的执行内容前先展示“序号、标题、工时”三列表；
标题链接到真实 Task，后续清单按 `#F01`、`#F02` 关联，详情备注另用 `#01`。
标题前显示本轮【新建】【复用】【调整】；工时格区分任务原预估/拟预估和
本轮剩余，只展示任务列表，不追加工时汇总，沿用共享清单的未知值规则。复用 Task 未填写
时如实说明，不用剩余预测补填原预估，不因此补估时、创建任务或生成日期排期。
这些阅读序号不替代下方正式 Plan 的原 Task key/ID、F-* 或实施步骤关联，
也不为新增清单索引重写已有 Plan 或增加模型字段。
本轮终点和实际风险用中文，不显示内部交付模式码；无业务或
实施未决时写“无”，执行确认单独提出。

确认前展示确定清单，确认后同一内容称执行清单；顶部列执行项目名称（可多个）、
关联缺陷/需求和本轮交付，任务数量可简述但不重复其标题。首次及实质调整后的确定清单另列“合并与测试环境”：
合并和部署按项目分别列是/否及准确目标，是否需要提测 Wiki 统一选择，三项默认都需要。
Bug 在该区块末尾另列“TAPD 状态：待测试（提测交付完成后流转）”；仅修复验证
则显示修复中，续接已待测试时按原政策注明保持不变。不套用到 Story/Task。
需要 Wiki 时，确认前先展示包含各项目条目的 canonical 模板预览及按实际结果
补全的规则；完整执行清单确认后，准确提测计划/正文验证通过就复用原授权，
不按阶段再次询问。单独执行技能仍确认自身具体计划。明确只开发/计划/分支
或关闭某项时覆盖默认，不查询未选择的 Jenkins/Wiki。
实质调整后重新展示完整确定清单，保留原行和编号，已完成效果标明不重复。
“合并并构建”仅指实际 dev/develop 及该项目 Jenkins 测试环境，不能推成
master/生产。后续精确交付操作需与原执行清单授权逐项匹配，未覆盖才补充确认。

具体实现记录到独立接手所需深度，覆盖选择理由、复用/代码落点、适用的
联动/数据流、步骤依赖和验收证据/局限；无需逐行代码或操作流水账。
范围、分支、位置和内容门禁通过后保存并读回；实施中的实质变化按原门禁
更新同一 Plan，完成时补实际验证结果和未验证项。已保存不等于可实施。

## 功能模块与行为契约

每个模块使用以下结构，子模块沿用同一结构；父模块和子模块均使用稳定编号。
Markdown 与面板使用同一模块内容，临时规范化模型使用 `schemaVersion=3`、
`features[].module` 与独立的 `features[].reviewConclusion`，不把 JSON 写进文档。

- `F-001`：<模块名称>；父模块：`<稳定编号或无>`；模块版本：`<正整数>`；功能状态：`待实施`；需求结论：`<未评审/已确认/待修改/阻塞/不适用>`；双向关联：`<API-001, T-001>`；关联：`<UI-001, AC-001>`
  - 职责与范围：<本模块解决什么问题，包含和排除什么>
  - 输入：<触发条件、前置条件、所需数据与参数>
  - 输出：<用户可观察到的展示、事件、状态变化或业务结果>
  - 行为规则：<正常、边界与异常条件下应有的表现>
  - 验收例子：`<模块内唯一编号>`；给定 <输入>；当 <触发>；则 <约定输出>
  - 待确认问题：`<模块内唯一编号>`；问题：<需求不完整/流程不闭环/接口字段或外部条件缺口>；影响：<受影响行为>；责任方：<有依据的补齐方或待核实>；补齐条件：<可核验的解除标准>；阻塞范围：<需求确认/实现/联调/验收>；建议：<推荐选项或查证动作>
  - 本次变更：`<added/modified/removed/unchanged>`；说明：<具体差异和影响>
  - 内部实现：<对应下方 DESIGN-001；尚未知的事实如实保留缺口>

无需将布局、接口、权限重复拆成评审模块；以下技术记录作为模块的实现依据与后台检查结果。
以上缺口描述不扩展运行时模型：`questions.owner` 仍为负责推进的 `user|agent`，
实际外部补齐方、解除条件和阻塞阶段写入现有 question/impact/recommendation
文本；`implementationPlan.blockers` 仍为字符串数组。区分已确认缺失与尚未
核实，不记录授权 Key 值，也不把执行审批或计划中未完成的编码/测试记为缺口。
行为规则保留影响实现的关键选择及理由，避免“按前面讨论”等依赖聊天的
指代。业务约定与下方基于当前代码的实施导航分别表达。

变化依原增量规则处理，不自动改变已确认的业务约定。Mock 或静态检查能够
证明的结果与尚未覆盖的真实集成明确区分。
