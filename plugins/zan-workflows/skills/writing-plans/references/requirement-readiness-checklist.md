# 需求确认前检查清单

## 目的

在用户确认需求范围前，统一展示业务、交互、数据、接口、权限、状态和验收缺口，明确哪些问题必须先决定，哪些问题可以保留到 Plan 但会阻塞实施。清单属于 `SCOPE_REVIEW` 的只读产物，不写文件、不创建 Draft、不修改业务代码。

简短执行摘要与正式 Plan 复用同一判断，沿用
[执行流程](../../../references/adaptive-workflow.md)。摘要可以压缩展示，不能
省略适用检查或带着阻塞进入实施。验证深度根据实际风险确定。

尚未补齐且影响本轮交付的检查结果汇总到执行主表的“待决事项”，沿用
[待决事项定义](../../../references/execution-checklist.md#待决事项的内容与边界)：
需求不完整、流程不闭环、接口/字段缺失、外部环境/权限/授权 Key 等条件
未就绪。它不表示等待执行审批或尚未完成的常规编码/测试工作。

## 清单结构

内部按下面结构核对每个缺失、冲突或已确认事实；用户侧按六列主表和
编号备注汇总，不再强制展示第二张长表：

| 项目/模块 | 类别 | 检查项 | 状态 | 当前证据 | 责任方 | 影响 | 门禁 | 建议动作 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

- 状态：`CONFIRMED|MISSING|CONFLICT|NOT_APPLICABLE`。
- 责任方：`agent|user|product|backend|project-owner`；Agent 能查证的必须先查证，不能直接转交用户。
- 每项适用缺口在现有行或编号备注/Plan 中说明缺口、影响、责任方、可核验
  的补齐条件及阻塞范围；责任方不明如实标记，不猜测分配。此处是检查
  说明，正式模型的 `questions.owner` 仍限 `user|agent`，实际外部协作方和
  补齐条件写在现有问题/影响/建议或 blocker 文本中，不新增 schema。
- 门禁：
  - `REQUIREMENT_BLOCKER`：范围、业务行为或验收无法确定，必须先解决才能确认需求；
  - `IMPLEMENTATION_BLOCKER`：需求语义已明确，但接口字段、代码落点等实施证据不足；允许确认需求，禁止进入实施；
  - `NON_BLOCKING`：已有证据或明确不适用。

先识别决定之间的依赖，只询问前提已确定、会影响本次范围或行为的问题，
并给出推荐及影响。上游决定未定时保留下游检查，不要求用户提前猜答案；
Agent 可从源码、契约或现有事实核实的问题先自行解决，不转成额外审批。

## 适用性检查

先按用户明确的交付边界判断每类是否适用。`NOT_APPLICABLE` 只需说明本次
没有相应变更及所依据的现有页面/数据绑定，不要求为每类执行完整源码或
接口搜索。不要把后台实现、未请求的真实数据联调，或别的端的行为当成
UI/交互任务的隐含门禁。

1. 项目与范围：受影响项目、页面/模块、包含项、排除项、跨项目边界。
2. 业务行为与闭环：触发条件、规则、边界、异常、默认值、角色差异，以及
   结果反馈、失败处理、状态恢复和必要后续动作。
3. 输入输出与数据字段：字段含义、来源、必填/可空、默认值、枚举、展示与提交关系。
4. UI 与交互状态：初始、加载、空态、错误、禁用、成功、重复提交和刷新回显。
5. API 与契约：消费点是否需要 API、正式来源、method/URL、请求/响应字段、状态码和错误语义。
6. 权限与安全：角色权限、敏感字段、数据范围、越权与审计要求。
7. 路由与状态：路由参数、页面/应用/会话状态归属、跨页面联动。
8. 验收与验证：可观察结果、关键场景、项目验证命令和缺失测试能力。
9. 外部运行条件：本轮所需测试环境、账号权限、授权 Key 配置、外部服务
   和访问能力是否已核实可用；只说明状态、影响与补齐方式，不读取无关
   凭据，也不把密钥值放进对话、备注、评论或 Plan。

对关键行为先确定验证入口、预期结果及局限，再细化实施步骤。说明 Mock、
类型检查、浏览器操作或真实集成各自能证明什么；验证方式随风险选择，
不能把可运行命令本身当作业务验收，也不为无关场景增加固定测试数量。

## 门禁判定

- 需求范围、业务规则、输入输出语义、用户可观察结果、关键验收标准存在 `MISSING|CONFLICT` 时，标记 `REQUIREMENT_BLOCKER`。
- API method、URL、请求/响应字段、类型、枚举、状态码、权限实现或代码落点缺失，但业务语义已经确定时，标记 `IMPLEMENTATION_BLOCKER`；需求可以确认，正式模块的 `implementationPlan.status` 必须保持 `blocked`。简短执行摘要记录同一缺口并取消实施就绪，不为表示阻塞补造模块对象。
- 只有本次新增或改变实际网络消费时，API 是否需要仍为 `unknown`、
  `required` 消费点未完成正式来源搜索或接口事实没有来源证据才是
  `IMPLEMENTATION_BLOCKER`；若缺失同时导致业务输入输出无法确定，则升级为
  `REQUIREMENT_BLOCKER`。纯 UI/Mock 场景可在现有绑定证据下记为无新增契约。
- `none` 或 `NOT_APPLICABLE` 必须有证据，不能为了清空清单而填写。
- 不得猜测 method、URL、字段、类型、必填、可空、枚举、默认值、包装结构、状态码或 Schema。
- 本轮必需的外部条件或测试能力未就绪时，说明阻塞实现、联调还是验收，
  按现有门禁保持受影响交付未就绪；不要把技术/环境缺口重标为业务需求
  未确认，也不要悄悄减少必需验证。只做 UI/已批准 Mock 的范围仍按适用性判断。
- “未查到/读取失败/权限不足”不等于“接口不存在/Key 未配置”。先使用
  现有来源查证，仍无证据时记录“尚未核实”、查证限制和下一步动作。
- 尚未执行的计划测试和等待最终授权不计入缺口；缺少执行这些测试的必要
  环境/权限才计入。解除缺口必须有对应决定或新证据，不凭建议或完成标记清零。

只有 `requirement_blocker_count=0` 才能生成 `READY_FOR_CHECKLIST` 或 `CONFIRMED` 的范围结果。
只有 `implementation_blocker_count=0` 且其余实现门禁通过，Plan 才能标记为可实施。
简短执行摘要同样要求两个 blocker count 均为 0 且其余实施门禁通过，才能把
`implementationBrief` 交给实施；摘要不使用正式 Plan 的可实施状态。

## 展示方式

- `DIALOGUE`：用六列执行主表的“待决事项”显示缺口摘要与阻塞数量，
  较长说明关联 #01/#02 编号备注，完整检查表与计数留在内部；不额外提问。
  简短执行摘要也不省略适用检查，发现缺失/冲突时完整说明受影响内容，不能隐藏为零阻塞。
- `PANEL`：业务问题进入对应模块 `questions`；技术缺口进入折叠实现依据和 `implementationPlan.blockers`。统一提交后仍在确定清单中汇总阻塞数量和未解决行。
- 没有适用缺口时在“待决事项”写“无”；内部仍核实两类阻塞计数为零，
  不用固定的零计数口号替代检查，也不将待执行确认记为缺口。

确认后新增或变化的检查项按最早受影响阶段重开；`REQUIREMENT_BLOCKER` 使范围确认失效，`IMPLEMENTATION_BLOCKER` 保留需求结论但使 Plan/实施准备度回到 blocked。
