# 直接提测与人工检查后交付

复用 `submitting-for-test`，不新建另一套提交脚本或交接模型。
“直接提测”表示进入提交、推送、测试分支 MR/合并、所选 Wiki、测试构建和
TAPD 登记流程；不等于跳过构建，也不跳过验证、独立评审或执行确认。

## 两种开始方式

- **实现后直接提测（默认）**：需求/修复确定清单显示“直接提测：是”，内部
  沿用 `delivery_mode=SUBMIT`。先实施、验证、独立评审，随后核对准确交付
  计划与已确认清单，复用有效授权连续执行，不再增加一次提测确认。
- **先实现，人工检查后再提测**：用户明确“先完成代码，我检查后再提测”
  “先不要提交/推送”“暂不直接提测”时，清单显示“直接提测：否”，内部
  沿用 `IMPLEMENT`。本轮合并、Wiki、测试环境构建均显示否/不需要，并注明
  本轮不执行；不查询这些能力或展示 Wiki 预览。完成验证、独立评审及适用
  Bug 记录后返回结果，供开发者检查。人工检查没有回复不代表可以交付。

后一种路径停在 `REVIEWED`，不提交、推送、创建/合并 MR、写提测 Wiki、
触发 Jenkins 或执行提测登记。实施本身必需且已授权的 Bug 状态/修复记录、
Task/Plan 操作仍按原规则执行，不把所有 TAPD 写入误归为提测。

## 独立发起直接提测

用户检查代码后，可说“代码确认了，直接提测”或调用 `$submitting-for-test`。
这启动独立提测准备；实施授权或人工看过代码不能代替准确交付计划的确认。

1. 复用原 TAPD、所选范围、全部必要仓库/原分支、定义和 `ReviewedChange`，
   不重跑需求拆解、创建 Task/Plan、建分支或重新实施，不重新激活 Bug。
   跨对话缺少交接时，从准确 TAPD、原分支、现有差异、原确认及实际测试/
   评审证据只读核实；不能从“代码确认了”伪造 READY/REVIEWED。无法核实时
   报具体缺口，不要求用户创建交接文件或重新跑整套开发。
2. 刷新源/目标 refs、未提交差异和待交付提交，与原评审范围及版本比较。
   开发者没有改动时复用仍有效验证/独立评审；人工提交的相同已评审内容
   不要求重写提交。内容改变时，仅补受影响的验证，并通过现有
   [change-reviewer](../../implementing-work/agents/change-reviewer.md) 的
   `POST_CHANGE_REVIEW` 刷新独立评审；人工确认不能替代这项证据。
   Bug 同时核对原完成记录是否仍覆盖当前改动与验证事实：仍有效则复用；
   失效则按下节准备更正后的完整完成正文，交同一次评审，不先写评论或
   把旧记录继续当作有效交接。评审检查拟写正文，不要求未来评论读回。
   不把无关改动混入提交，不在直接提测中自动修复业务代码。缺少材料或
   检查失败时停止受影响交付，并说明所需证据/修复；保留已完成效果。
3. 准备准确只读 `SubmissionPlan`，核实实际 dev/develop、所选 Wiki 正文/
   最小补丁、Jenkins Job/参数及最终登记。默认合并、Wiki 和构建均需要；
   当前明确关闭某项时才跳过。先前 IMPLEMENT 的不交付选择属于上一轮，
   本次明确要求直接提测后重新解析本轮选择；本轮明确的 NO_WIKI/SKIP 仍保留。
4. 按下面模板展示一份完整的直接提测确定清单，等待一次准确确认；同一
   已展示计划已有匹配确认时复用。缺失/过期的事实先只读补齐，不伪造结果。
   收到确认后 EXECUTE，沿用既有 Git/Wiki/TAPD 验证及读回顺序。
   若 Bug 完成记录待补，先完成该已授权记录的追加/复用与准确读回，刷新
   `ReviewedChange` 后才进入 Git、构建、Wiki 和登记；失败保留实际效果并停止。
5. 已有提交、推送、MR 或 Wiki 逐项核实后复用，只完成缺少的已授权操作。
   已手动交付或明确本轮不合并时，调用 merge 的只读 `CONTAINMENT_ONLY`
   核实准确 dev/develop 包含已评审源码。其 `VERIFIED`、`containment=true`、
   `writes=0` 回执可通过提测 Git 门禁；绑定回执的 `deliveredSha` 作为本次
   测试目标版本，不虚构 MR 或合并成功。未包含或证据不明时停止，不擅自合并。
   先确认本轮已审查改动均已进入该 source SHA；仍有未提交的待交付增量时
   不能以 HEAD 已包含为由放行，也不能在“不合并”分支擅自提交或推送。
   Jenkins 采用 `TRIGGER_ACCEPTED`，确切队列回执即可继续，不等待构建完成。
   没有明确上线要求不进入 master/正式发布，删除资源仍需原有精确授权。

## 人工改动后的 Bug 完成记录

只处理当前 Bug 的记录有效性，不重开业务实现或状态流转。跨仓库先收齐
全部必要仓库的当前验证/评审及跨仓库验收，再汇总一份记录。

- 按 [修复记录规则](../../implementing-work/references/bug-repair-record.md)
  只读核实原开始/完成评论、作者、正文及当前修复范围。仅提交号变化、
  等价排版或仍真实覆盖当前修复的记录无需重写；人工改动使修复说明、
  原因/证据或验证事实失效时才准备更正，不复制过期结论。
- 完成正文沿用 HTML 字段及实际证据，包含必要更正及依据；先连同当前
  差异交 `POST_CHANGE_REVIEW`，评审通过后才可写“完成”。已有有效完成
  记录可作为记录恢复的历史依据，不倒补开始评论、不重复激活 Bug；
  核实不到必要历史则报具体缺口，不凭人工确认伪造记录。
- 仅记录待补时，允许在当前代码验证和独立评审已通过后准备只读 PLAN，
  但不能宣称 Bug 已有完整 `REVIEWED` 交接或放行任何交付写入。把准确 Bug、
  评论账号、原评论、完整拟写正文和追加/复用动作纳入同一提测清单确认；
  旧确认明确覆盖该同范围、同账号更正时可复用，缺失权限与其余交付一起
  确认，不为评论再增加一轮。范围/人员变化沿用原实质变更规则。
- EXECUTE 的第一项受控写入是这条记录：先刷新评论并按语义查重，已经有
  覆盖当前修复的完整记录就复用；否则在同一 Bug 下追加一份更正后的完成
  评论，保留历史，不覆盖/删除原评论。通过 `get_comments` 读回准确 ID、
  Bug、作者、正文和语义排版后，再更新原 `ReviewedChange` 的当前源码版本、
  差异及记录/验证/评审内容。所有必要仓库引用这一份已核实记录，才通过正常提测输入门禁。
- 写入或读回失败时，保留代码、评审和已有评论 ID，返回 BLOCKED，停止
  提交/推送/MR、Jenkins、Wiki 和 TAPD 登记。恢复先查原评论，只补缺失证据，
  不盲目重发评论、重新修复或重复已经完成的操作。Story/Task 不套用本节。

## 独立直接提测的确定清单

这是已有实现的交付清单，不重复实施方案和 Task/Plan 拟写内容。实施入口
仍用共享六列清单；其已确认的直接提测范围不因下游切换技能再展示确认。

```markdown
## 确定清单

**执行项目名称：** 〈本轮全部项目/子项目〉
**关联缺陷／关联需求：** 〈真实编号、标题及链接〉
**本轮交付：** 直接提测，复用已完成实现

### 待交付变更

| 项目 | 原始开发分支 | 交付范围与验证/评审 |
| --- | --- | --- |
| 〈项目〉 | 〈完整原分支〉 | 〈实际范围、所选 Task 真实链接（适用时）、验证/评审及人工改动核对结果〉 |

### Bug 完成记录补充

〈仅当人工改动使旧记录失效：展示准确 Bug、评论账号、旧记录差异、完整更正正文及追加/复用动作；无需写入则省略〉

### 合并与测试环境

- **直接提测：** 是；本轮只交付已核实变更。
- **合并到测试分支：** 〈逐项目是/否，完整源分支 → 实际 dev/develop；提交/推送、MR 及合并，已完成效果不重复〉
- **是否需要提测 Wiki：** 〈需要/不需要；完整正文或最小补丁、共享页面及回链〉
- **部署测试环境：** 〈逐项目是/否，准确环境、Job 链接及参数；任务已提交即继续，不等待完成〉
- **TAPD 状态：** 〈仅 Bug：待测试（提测交付完成后流转）或待测试（保持不变）〉

〈选定合并时说明准确 A → C → B 冲突处理范围和 .worktrees/ 位置；其余适用的登记字段及处理人如实展示〉

### 提测 Wiki 模板预览

〈需要时展开本轮准确完整正文或现有页最小补丁，不能只给路径；不需要则省略本节〉

是否按以上确定清单执行？
```

表中待交付提交/差异、评审、Wiki 正文及准确操作共同绑定确认，不增加
运行台账或新状态。所有必要仓库门禁通过后才做共享 Wiki 和最终登记。

“直接提测”本身不选择 SKIP。只有明确“不构建”“跳过发布”“不发测试环境”
等构建限制才选 SKIP；若同时给出直接提测和不构建，保留该明确限制。
