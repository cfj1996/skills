# 直接提测与人工检查后交付

## 含 Mock 的直接提测

普通“直接提测”、原人工检查和默认构建选择不包含 Mock 测试授权。先按
[本次变更与影响范围](../../../references/mock-development.md#清查范围)核查每个仓库的完整待交付
差异与关联入口，复用同一 Plan/brief 的 MOCK-* 清单。历史库存不自动扩大本轮范围。旧清单、缺字段或过期源码不能当成无
Mock。含 Mock 时在本节清单中显式加入“外部数据与依赖”和“Mock 范围与测试授权”，
展示准确路径/场景、真实调用边界、测试分支/环境、用途、真实验收缺口、退出条件
和本次选定操作，默认不允许。完整当前内容获人类明确确认后才执行首次交付写入。
确认可与本轮交付清单一次完成，不新增例行第二轮；范围/源码/目标变化仍须复核。

统一门禁覆盖提交/推送/MR、构建、Wiki及登记，NO_WIKI/SKIP不豁免。测试结果和
Wiki明确“含 Mock”，不能把模拟保存/权限验收报成真实通过；生产始终禁止 Mock。


复用 `submitting-for-test`，不新建另一套提交脚本或交接模型。
“直接提测”表示进入提交、推送、测试分支 MR/合并、所选 Wiki、测试构建和
TAPD 登记流程；不等于跳过构建，也不跳过验证、独立评审或执行确认。

补验沿用 [本地验证范围与资源预算](../../../references/local-verification.md)：
仅重验失效的受影响范围；提测阶段不自动重跑全仓 lint/type/build。
必要检查超时/超限仍是缺口，测试环境构建的队列回执不能补作已通过的验证。

## 两种开始方式

- **实现后直接提测（默认）**：需求/修复确定清单显示“直接提测：是”，内部
  沿用 `delivery_mode=SUBMIT`。先实施、验证、独立评审，随后核对准确交付
  计划与已确认清单，复用有效授权连续执行，不再增加一次提测确认。
- **先实现，人工检查后再提测**：用户明确“先完成代码，我检查后再提测”
  “先不要提交/推送”“暂不直接提测”时，清单显示“直接提测：否”，内部
  沿用 `IMPLEMENT`。本轮合并、Wiki、测试环境构建均显示否/不需要，并注明
  本轮不执行；不查询这些能力或展示 Wiki 预览。完成验证、独立评审及适用
  Bug 记录后返回结果，供开发者检查。人工检查没有回复不代表可以交付。

后一种路径停在 `REVIEWED`，不提交、推送、创建/合并 MR、写提测 Wiki、
触发 Jenkins 或执行提测登记。实施本身必需且已授权的 Bug 状态/修复记录、
Task/Plan 操作仍按原规则执行，不把所有 TAPD 写入误归为提测。

## 独立发起直接提测

用户检查代码后，可说“代码确认了，直接提测”或调用 `$submitting-for-test`。
这是本轮执行指令，可以引用对话中已确定的交付对象和操作。按[提测指令与结果](../SKILL.md#提测指令与结果)核实边界。只有实施结果时仍须有用户的提测指令。

1. 复用原 TAPD、所选范围、全部必要仓库/原分支、定义和 `ReviewedChange`，
   不重跑需求拆解、创建 Task/Plan、建分支或重新实施，不重新激活 Bug。
   跨会话按[续接位置](../../executing-tapd-plan/references/executing.md#新会话从哪里继续)
   核对原分支及实际回执。已保存计划先读正式页的执行记录，会话稿则读原会话的确认和回执。
   尚无可核实的开发收尾回执时，按现有代码和验收只补缺少的验证或独立评审。
2. 刷新源/目标 refs、未提交差异和待交付提交，与原评审范围及版本比较。
   按 [变更与文档一致性](../../../references/change-consistency.md) 核对完整待交付行为
   及本轮增量的依据、影响与验证。已有正式执行文档时，需求或实现方案变化先按
   [同页修订](../../executing-tapd-plan/references/executing.md#同步需求和实现变更)同步并读回新版，之后按新版准备交付。
   STANDARD 必须核对原 Wiki 当前条目并修订过期
   内容、影响范围及验证说明；已有链接或同页面名称不能证明覆盖了新增改动。
   开发者没有改动时复用仍有效验证/独立评审；人工提交的相同已评审内容
   不要求重写提交。内容改变时，仅补受影响的验证，并通过现有
   [change-reviewer](../../implementing-work/agents/change-reviewer.md) 的
   `POST_CHANGE_REVIEW` 刷新独立评审；人工确认不能替代这项证据。
   Bug 同时刷新单条修复记录草稿，与当前差异和验证事实交同一次评审；
   已有完整记录仍覆盖本轮事实则复用。评审核对拟写正文，不要求未来评论读回，
   也不在提测前复核或返工途中发表评论。
   不把无关改动混入提交，不在直接提测中自动修复业务代码。缺少材料或
   检查失败时停止受影响交付，并说明所需证据/修复；保留已完成效果。
3. 准备准确只读 `SubmissionPlan`，核实实际 dev/develop、所选 Wiki 正文/
   最小补丁、Jenkins Job/参数及最终登记。默认合并、Wiki 和构建均需要；
   当前明确关闭某项时才跳过。先前 IMPLEMENT 的不交付选择属于上一轮，
   本次明确要求直接提测后重新解析本轮选择；本轮明确的 NO_WIKI/SKIP 仍保留。
4. 在内部将实际 Git、构建、Wiki 和登记操作同用户提测指令及上下文核对。交付预检通过后当轮 EXECUTE，汇总真实结果。仅预览时返回清单。缺少必要用户选择时只说明具体缺项。
   Bug 记录沿用正常收尾顺序：Git、所选构建及适用 Wiki/独立回链通过后，
   才发表/复用唯一修复记录并准确读回，再登记 TAPD；失败保留实际效果并停止。
5. 已有提交、推送、MR 或 Wiki 逐项核实后复用，只完成缺少的已授权操作。
   已手动交付或明确本轮不合并时，调用 merge 的只读 `CONTAINMENT_ONLY`
   核实准确 dev/develop 包含已评审源码。其 `VERIFIED`、`containment=true`、
   `writes=0` 回执可通过提测 Git 门禁；绑定回执的 `deliveredSha` 作为本次
   测试目标版本，不虚构 MR 或合并成功。未包含或证据不明时停止，不擅自合并。
   先确认本轮已审查改动均已进入该 source SHA；仍有未提交的待交付增量时
   不能以 HEAD 已包含为由放行，也不能在“不合并”分支擅自提交或推送。
   Jenkins 采用 `TRIGGER_ACCEPTED`，确切队列回执即可继续，不等待构建完成。
   没有明确上线要求不进入 master/正式发布，删除资源仍需原有精确授权。

## Bug 修复记录

统一使用 [修复记录规则](../../implementing-work/references/bug-repair-record.md)。
全部必要仓库及跨仓验收通过后，ReviewedChange 携带已评审的完整草稿即可正常进入 PLAN；
没有已发表评论不是缺口。准确 Bug、评论账号、正文及最终发表/复用动作纳入同一提测清单，
写入固定在适用 Wiki/独立回链之后、TAPD 登记之前。人工修改只刷新受影响的验证、
独立评审和草稿，不重新激活 Bug。已有本轮完整记录有效就复用；事实失效则按记录规则
更正原评论，不追加另一条完整记录。记录或读回失败时保留已完成交付，停止登记，
恢复先查实际效果。Story/Task 不套用本节。

## 提测结果

按仓库列出原分支、目标分支、提交、MR 及构建回执。共享 Wiki 和 TAPD 登记各报告一次。已接受的风险标为已知问题，留下尚待测试的条件。遇到真实合并冲突、权限阻塞或未知写入，写明已完成效果和下一步所缺的具体条件。用户明确要求预览时，提供本轮操作及适用正文，停在预览。

“直接提测”本身不选择 SKIP。只有明确“不构建”“跳过发布”“不发测试环境”
等构建限制才选 SKIP；若同时给出直接提测和不构建，保留该明确限制。
