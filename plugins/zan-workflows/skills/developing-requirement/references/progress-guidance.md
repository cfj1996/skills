# 需求开发进度与下一步引导

## 判断原则

每次准备交回用户、暂停或阻塞时，先判断当前阶段的完成门禁：

- 当前阶段是 `PENDING|BLOCKED|FAILED`，或必需验证尚未通过：推荐“完善当前阶段”，禁止推荐提测、上线等下游动作。
- 当前阶段门禁已通过：推荐进入紧邻的下一阶段，同时提供“修改当前结果”和“暂停”选项。
- 用户要求修改已确认内容：重开最早受影响阶段，并明确哪些后续确认、Plan、实现或评审结论失效。
- 引导文字只是导航，不替代分支、写入、提交、MR、部署或上线所需的精确授权。
- 沿用已解析的 `workflow_profile` 和 `verification_risk`，只展示本路径实际
  经过的阶段。QUICK 的范围与 `implementationBrief` 就绪后走准备/分支确认并
  直接实施；不展示未执行的 Task/Plan 阶段为完成，也不为导航强制创建它们。

## 阶段与默认下一步

| 当前阶段 | 完成门禁 | 推荐下一步 | 可直接回复 |
| --- | --- | --- | --- |
| `DISCOVERY` | 项目、仓库、origin、`origin/master` 已唯一确认 | 收敛需求范围 | `继续分析需求范围` |
| `SCOPE_BLOCKED` | 仍有 `REQUIREMENT_BLOCKER` | 解决范围、行为或验收问题 | `解决需求确认项` |
| `SCOPE_READY` | 范围、排除项、验收、档位和评审模式已形成 | QUICK 准备 brief 与范围/分支清单；STANDARD/FULL 准备任务与统一清单（BRANCH_ONLY 仅分支） | `继续生成执行清单` |
| `AWAITING_TASK_CONFIRMATION` | 已展示完整拆分表、人员、预估工时和拟写入字段 | 确认或修改任务清单 | `确认任务清单` / `修改任务清单：...` |
| `TASKS_READY` | 所选任务均已准确读回，人员与预计工时完整 | 按已确认分支编写关联 Plan | `继续编写 Plan` |
| `TASK_WRITE_PARTIAL` | 已有成功项，失败或结果不明项尚未核实 | 核查原任务后展示剩余差异，禁止直接重试创建 | `核查任务创建结果` |
| `IMPLEMENTATION_EVIDENCE_BLOCKED` | 需求可确认，但 API/字段/代码落点等仍阻塞实施 | 补齐技术证据或改为仅编写 Plan | `继续补齐实施证据` / `改为仅编写 Plan` |
| `AWAITING_CHECKLIST_CONFIRMATION` | 等待用户确认完整清单 | 确认或修改清单 | `确认执行` / `修改清单：...` |
| `BRANCH_READY` | 分支已创建/选定且读回匹配 | QUICK 按已确认 brief 实施；STANDARD/FULL 编写 branch-bound Plan；BRANCH_ONLY 到此结束 | `开始实施` / `继续编写 Plan`（按当前路径） |
| `PLAN_READY` | Plan 已确认、写入并读回 | 开始实施时展示推荐开发周期，或仅保留 Plan | `开始实施` / `仅保留 Plan` |
| `IMPLEMENTING` | 尚有本次行为/任务未完成 | QUICK 继续当前行为并验证；STANDARD/FULL 继续当前任务，必要时刷新推荐排期 | `继续实施` |
| `REVIEW_BLOCKED` | 实现或必需验证未通过 | 解决当前阻塞并重新验证 | `解决当前阻塞后继续验证` |
| `REVIEWED` | 所有项目均 `REVIEW_PASSED` | 进入提测流程或检查当前实现 | `提交测试` / `查看当前实现` |
| `AWAITING_SUBMISSION_CONFIRMATION` | 已展示全部精确 `SubmissionPlan` | 确认提测计划或修改计划 | `确认提交测试` / `修改提测计划：...` |
| `SUBMITTED` | `TestSubmissionResult=SUBMITTED` | 按明确意图上线或暂停 | `上线` / `暂停` |
| `AWAITING_GO_LIVE_CONFIRMATION` | 已展示 source-to-master 与 Wiki 精确变更 | 确认上线计划或暂停 | `确认上线` / `暂停` |
| `AWAITING_MERGE` | 原 MR 已创建/复用，等待有权限人员合并；业务 Wiki 已读回待合并或单列 Wiki 阻塞 | 展示 `userAction.message`，主动请用户联系有权限的同事按准确 MR/目标分支合并，并展示 Wiki 结果；人工合并后只读核验同一个 MR 再继续 | `已合并，继续上线` |
| `MERGED` | master 包含性与必需 Wiki 读回通过 | 有安全候选时展示清单并询问；否则解释保留或检查阻塞原因 | `确认清理` / `保留开发环境`（仅已展示精确清单时） |
| `AWAITING_CLEANUP_CONFIRMATION` | 已简洁列出开发分支、临时分支（标明本地/远程）及工作树，远程开发分支保留 | 确认、修改或保留；包含远程临时分支时明确范围 | 本地清单：`确认清理`；组合清单：`确认清理（含远程临时分支）`；或 `保留开发环境` |
| `PAUSED` | 用户要求暂停 | 从记录的当前阶段恢复 | `继续需求开发` |
| `STOPPED` | 用户取消或工作已由他人接手 | 保留或按确认清理本地资源 | `检查并清理本地资源` |

`BRANCH_ONLY` 在 `BRANCH_READY` 结束，按已确认范围提示可以准备 brief 或 Plan，
不由分支请求推导实施授权。QUICK 没有 `PLAN_READY` 或 `TASKS_READY` 阶段；
确认的 brief 和准备门禁通过后，直接推进已授权实施。
`PLAN_ONLY` 在 `PLAN_READY` 结束，但仍提示可以开始实施。
`IMPLEMENT` 在 `REVIEWED` 结束；`SUBMIT` 在 `SUBMITTED` 结束；
`GO_LIVE` 继续进入 `going-live`，但每个下游写阶段都必须由用户明确选择
并确认该阶段刚展示的精确计划，不能由最初的模式选择隐式授权。

## 阻塞决策

阻塞时必须区分：

- `CURRENT_STAGE_FIXABLE`：代码、Plan、验证环境或缺失证据仍属于当前范围。推荐先完善当前阶段。
- `SCOPE_CHANGE_REQUIRED`：修复会改变已确认范围。推荐“修改清单/Plan”，重新确认后再实施。
- `EXTERNAL_OWNER`：已由他人开发、外部依赖未就绪或用户取消。推荐暂停/停止，不继续下游流程。
- `DOWNSTREAM_READY`：当前阶段全部通过。只有此状态才推荐下一流程。

“部分定向测试通过但必需构建失败”仍是 `REVIEW_BLOCKED`，不能推荐提交测试；应给出修复验证环境、调整必需验证规则（需重新确认）或暂停三个相关选项。
存在 `REQUIREMENT_BLOCKER` 时使用 `SCOPE_BLOCKED`；仅存在
`IMPLEMENTATION_BLOCKER` 且请求实施时使用 `IMPLEMENTATION_EVIDENCE_BLOCKED`，不能把它们混成同一种“待确认”。

## 多项目进度

多项目时在总进度下增加项目表：

| 项目 | 分支 | Plan | 实施 | 验证/评审 | 阻塞 |
| --- | --- | --- | --- | --- | --- |

总阶段取最早未通过的必需阶段。一个项目已完成、另一个项目阻塞时，推荐处理阻塞项目，不能把整体标为 `REVIEWED`。

## 最终回复模板

`AWAITING_CHECKLIST_CONFIRMATION` 必须使用
[执行主清单表格](branch-checklist.md#单次确认清单)，每个项目/仓库/分支绑定一行，
单项目也保留一行。QUICK 只简化准备和产物，不能将最终确认表降为散列项；
字段/功能表、上面的进度表和下方历史阶段清单都不能替代该执行主表。
先给共同背景，再展示项目主表及必要的项目关联补充表，最后汇总本轮操作
与授权边界，只问一次 `是否按此清单执行？`。不为改变展示形式重启评审或新增确认。

普通阶段推进或小修正只需说明实际结果、验证、当前阶段和一个
“推荐下一步”；不要每次重印全部历史阶段。只有阻塞、跨项目交接或用户要求
完整进度时才使用下面的展开模板，并只列本次相关阶段。`你可以选择`
和`可直接复制的短句`仅在确有多个可行决策时展示：

QUICK 的实施结果使用行为完成/验证摘要；最终执行确认仍使用上述主表。
下方完整模板只列实际适用项，不能为了填表
增加任务、正式 Plan 或排期。升级档位时只补受影响步骤，复用仍有效的证据。

```markdown
## 流程进度
- [x] 项目定位
- [x] 需求范围
- [ ] 分支准备
- [ ] Plan
- [ ] 实施
- [ ] 验证与评审
- [ ] 提测（仅 `SUBMIT|GO_LIVE`）
- [ ] 合并 master / Wiki（仅 `GO_LIVE`）
- [ ] 本地开发环境清理（仅存在已确认候选时）

当前阶段：`<stage>`
当前状态：`<READY|PENDING|BLOCKED|PAUSED|COMPLETE>`

## 推荐下一步
<一个明确推荐动作，以及为什么现在应做它>

## 你可以选择
1. `<相关动作>` — 回复：`<可直接复制的短句>`
2. `<修改当前结果>` — 回复：`修改范围/清单/Plan：...`
3. `<暂停或结束>` — 回复：`暂停`
```

不要列出当前不具备输入门禁的动作；不要只报告“成功”“完成”或“阻塞”而不给下一步。

上线完成后的清理引导必须出现在最终回复：有安全候选时展示精确的本地
分支/worktree 清单，以 `是否删除以上本地开发环境？` 收尾，并提供
`确认清理` / `保留开发环境`。若同时列出已核实的远程临时分支，则改问
`是否清理以上资源（含远程临时分支）？`，提供
`确认清理（含远程临时分支）` / `保留开发环境`；远程开发分支保持保留。
使用开发分支、临时合并分支、工作树三类简表，逐个列出准确名称；SHA/MR 等
技术证据保留在内存计划中。没有安全候选或证据不足时说明原因，不空问
是否清理。用户选择保留后结束流程，除非再次明确要求，否则不重复询问。
