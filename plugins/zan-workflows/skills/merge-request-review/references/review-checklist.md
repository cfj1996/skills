# 检查范围与意见判定

主代理和两个 reviewer 共用本清单。先确认当前 source/target SHA、完整 diff、修改依据、
项目约束和验证证据，再追踪受影响入口及消费者。只读实际需要的上下文，不做全项目重构审计。

## 通用检查

| 维度 | 需要回答的问题 |
| --- | --- |
| 修改依据与行为 | 当前目标和验收是什么？新增、改变、移除的行为是否符合依据？应保留的行为是否仍可达？ |
| 正确性与安全 | 正常、边界、异常路径是否成立？是否存在权限绕过、租户串用、敏感信息泄露、数据污染或错误计算？ |
| 工程设计 | 职责、依赖方向、状态所有权和生命周期是否清晰？复用是否有真实消费者？新增抽象、全局影响或重复状态是否必要？ |
| 兼容与影响 | API、类型、事件、持久化数据、配置及公共能力的消费者是否仍兼容？迁移、回滚和失败恢复是否满足本次交付条件？ |
| 验证 | 测试是否观察真实行为，覆盖关键失败路径和受影响旧行为？证据是否对应当前版本？未执行或失败项有什么实际影响？ |
| 适用约束 | 项目声明的规范、CI、交付文档及例外是否适用且满足？没有采用某体系本身不构成问题。 |
| Mock 生产禁令 | 当前完整源码/差异及运行入口是否经过统一 Mock 清查？MOCK-* / MOCK_ONLY 是否有真实替换/退出和构建排除依据？隔离开发工件是否确实不进入生产链路？ |

类型检查或构建通过不能代替行为审核；实现摘要、测试存在或新增 Guard 不能证明调用链真的到达它。
已有问题和本次新增/加剧的问题分开，主要意见聚焦本次可操作影响。必要的技术调整不因需求未列出
具体文件而自动判超范围；反之，目录相近、diff 小也不能证明没有影响。

## 按变更选择专项

从改动行为、项目规则和平台证据选择下列适用项。一个 MR 可选多项；无法识别项目类型时，
先做通用检查并补查影响关键判断的事实，不凭项目名或技术栈强行套用模板。

| 受影响类型 | 专项关注 |
| --- | --- |
| B 端/管理界面 | 菜单与操作权限一致性、站点上下文、批量操作部分失败、筛选分页、表单草稿与提交/刷新一致性 |
| C 端/Web/H5 | 会话变化、返回与页面恢复、弱网/重复操作、移动交互、可访问性；性能变化须有实际路径与成本依据 |
| 小程序/原生端 | 页面与应用生命周期、授权及平台 API 限制、前后台切换、平台存储、导航、分包或桥接兼容性 |
| 后端/服务 | 服务端鉴权、事务与一致性、幂等/并发/重试、超时与错误契约、数据迁移、资源释放及必要可观测性 |
| 工具包/SDK/组件库 | 公开 API/导出/类型及运行时兼容、依赖与副作用、真实消费者、破坏性变化和迁移说明；不因名称像公共库就假定使用方 |
| 构建/CI/工程配置 | 环境边界、密钥暴露、依赖/锁文件与产物一致性、构建和发布参数、回滚条件；审核中不运行部署或发布 |

项目采用的具体规范从项目声明加载。Zan 仅在正式采用且对应规则生效的范围追加检查；
monorepo 依据受影响子项目和采用范围判断，不把某个子项目规则扩展到整个仓库。
既有 master/main 目标、develop/dev 来源及历史、HEAD、CI、审批、讨论和 mergeability
门禁继续由主流程核实，项目专项不替代它们。

Mock 门禁适用于所有项目，独立于是否采用 Zan。按
[共享规范](../../../references/mock-development.md)和统一 `mock-safety.mjs` 检查；
代码结论、Mock 缺证/禁令及其他合并条件分别报告。不能因依赖版本、关闭开关、
删标识、状态 retired 或普通 pipeline 成功推断生产安全。仅源码检查通过不证明
未来制品已通过；实际发布还需 Jenkins 先检后发的制品证据。

## 工程设计与整改程度

设计意见需要指出实际责任、数据流或消费者问题。文件长度、目录偏好、封装层数和代码相似
只能作为线索，不能单独证明设计缺陷。优先提出满足当前需求的最小合理调整。

| 意见类型 | 依据与处理 |
| --- | --- |
| 必须修复 | 已确认的行为/安全/兼容缺陷，或违反实际适用的强制规则。给出成立条件、位置、影响和最小整改；代码缺陷与治理阻断分别归类。 |
| 优化建议 | 有具体收益和成本，但当前行为与强制要求成立。通常不阻断，不借个人风格偏好强推重构。 |
| 需要重新设计 | 当前方案无法满足已确认需求或关键约束，局部修复仍无法消除明确风险。说明失败原因、局部修复的不足、替代方向与调整边界；阻断依据仍是具体缺陷或适用规则。 |
| 证据不足 | 必要源码、契约、调用链或验证不可得。列出缺口及影响；关键正确性未能判断时为代码未完成，仅合并门禁缺证时保留独立代码结论。 |

每条意见附审核版本的文件行号/diff hunk、必要调用链或规则/执行证据，说明是否阻断及其原因。
同根因合并报告；不要求每类都有意见。整改后只刷新受影响的验证和评审，不能把旧版本通过直接迁移。
