# 收集需求与缺陷

[需求开发](../developing-requirement/SKILL.md)和 [Bug 修复](../fixing-bug/SKILL.md)共用本技能。按[模型路由](../../references/model-routing.md)处理只读调查和已授权的 Wiki 写入。

| 情形 | 输出模式及终点 |
| --- | --- |
| “先给我看”“只在会话评审”“不落盘”，或仅提供文字/原型供收集 | `SESSION`，在当前对话展示评审稿与待定事项 |
| 普通「开发需求／修复 Bug」、明确要求保存或从会话稿转存 | `TAPD_PLAN`，先评审，确认准确版本后保存并回链原条目，默认手动执行，返回链接即结束 |
| 明确要求按已保存的 TAPD Plan 开工 | 转交[执行 TAPD Plan](../executing-tapd-plan/SKILL.md)，使用正式页面 |

执行时机独立于输出方式，默认手动执行。用户明确立即执行时，把保存、开工以及各项目 Git/MR、提测、构建范围合并为本轮一次确认。两种启动时机遵循[执行上下文](../executing-tapd-plan/references/execution-context.md)。

两个输出模式共用按项目排列的实施正文。正式 Wiki 保存当前方案和验收，页首链接子 Wiki「执行与变更记录」。启动方式和本轮交付在会话中确认。用户指定的模式优先。收集阶段只读业务系统和源码。历史 Task、仓库里的旧计划可作为范围证据，项目编号 P 和功能编号 F 都是页内索引。分支创建、源码修改和交付留给执行阶段。

## 一、先确定做什么、在哪做、怎么做

1. 有工作项时用 TAPD MCP 按空间和完整 ID 读取准确的 Story 或 Bug，核对正文、相关附件、PRD、评论和必要原型。Bug 取复现入口、触发条件、实际和期望行为，核对既有修复、测试反馈及原始分支。按[工具路由](../../references/tool-routing.md)复用原型页面。
2. 用 [workspace-project-knowledge](../workspace-project-knowledge/SKILL.md) 核对真实项目、子目录、仓库与项目规范。读绑定基线下的相关代码、接口契约和同类实现。为每个必要仓库确认工作位置、分支动作、基准 ref 与提交。一个 Bug 跨仓时保留完整范围。多个 Bug 按用户顺序分别确定归属和修复面，共用分支的每页都列前置 Bug ID/链接、放行条件、首次创建者和后项的复用动作。
3. **确定本轮各项目要交付的改动。** 以前端为实施方时，从现有页面、组件、权限入口和请求消费差异提取 P、M、F。按前端需要保留服务端可观察的契约、权限与数据结果，并在联调验收中核对。服务端代码、数据处理和部署只有在本轮明确负责时才按独立项目编写。前端仅需回归时给出影响和联调结论。
4. **先查齐功能依赖的接口。** 在项目说明后、模块实施前按消费模块排列「接口清单」。已接入可复用、新接入、拟 Mock、缺字段或契约待核实的调用均按用途登记。每条 API 使用一个项目级 D 编号，跨项目共用时引用同一编号。其他外部配置用独立 D，路由参数和组件 props 写在 F 的输入输出。按[外部依赖规则](../../references/external-data-dependencies.md)区分契约对齐、环境就绪与实际联调。Mock 按[现有批准和实施规则](../../references/mock-development.md)处理。
5. **按 P → M → F 展开实现。** 每个 F 引用接口编号，写何时调用、如何传值和消费、修改位置、有序实现及验收。能由源码或契约查证的先查。业务分歧给出取舍与影响。接口有缺口时写受阻的步骤或验收及补齐条件，让独立的就绪工作可以继续。

有用户可见布局或样式变化时，按[视觉对齐用例](references/plan-format.md#视觉对齐用例)在对应 F 的 UI 和 TC 写可回读的确认依据、对齐点和实际页面通过条件。明确图或原型用于对照哪些界面。共享组件影响多个入口时，逐个写适用的用例。

多个页面或页签共用选中值、筛选或权限时，可选[按跨页路径验收](references/cross-page-acceptance.md)。先从原型盘齐本轮入口和状态，再把一条容易跑偏的连续操作写入原有 TC，按同一用例开发和复核。

## 二、生成同一份确认稿和正式计划

按[执行计划格式](references/plan-format.md)、[前端需求示例](assets/example-frontend-plan.md)和[缺陷示例](assets/example-bug-plan.md)准备正文。分支、证据链接、契约和测试命令以本次核实结果填写。正式 Plan 使用 Story/Bug、项目与功能点绑定，范围、验证和交付都沿用这些编号。

- **项目 P** 给出准确仓库、原分支、基线、实现边界、项目规则和验证命令。项目头列数据对齐结论和受影响 F。
- **数据 D** 接口清单的每一行就是一个 D。凭据等外部配置按对应 D 写配置引用、环境与访问验证，实际凭据留在原系统。
- **模块 M、功能 F** 给出职责、已确认规则、前置功能、输入／输出、关联 D、现有文件和符号。按顺序写清新增或修改的位置、如何处理数据、哪里更新状态及可观察产出。关键选择注明实际依据。新建文件标为拟新增。
- **交互 UI、测试 TC** 按功能展开适用的入口、触发、展示、失败反馈和回显。每个本轮功能有可独立检查的 TC，写固定输入、操作或真实命令、预期输出和通过条件。接口及纯后台功能直接验证调用或数据结果。
- **Bug 增量** 在对应 F 中写复现、故障定位、原因证据、修复位置和防回归场景。写前明确后续修复状态／处理人及唯一修复记录的时机。一个 Bug 只有一份覆盖各必要仓库的计划。

保存时展示实施范围和启动方式。用户要接着开工时，按当前指令确认仅开发验证、提测、提测并构建或仅构建。明确提测时核实目标分支及提测 Wiki，明确构建时核实环境、Job 与参数，同一次确认覆盖本轮选择。明确启用子智能体开发时在该次开工指令中确认。

## 三、按选择输出

**会话模式 SESSION**　直接在对话输出完整评审稿、数据对齐结论、缺口和待决定事项。简要说明按本稿开工或保存后使用链接开工的方式。按已确认会话稿就地执行时，实际进度在会话中报告。用户随后指定保存时，复用实施正文并补齐工作项身份，再给出准确保存预览。纯文字或 PRD 也能在此模式收集，未知的项目、入口或外部条件如实标明。

**TAPD Plan 模式 TAPD_PLAN**　输出一个工作项的一份正式执行 Wiki。

目的地使用条目所在空间的执行文档父 Wiki。优先使用用户给定的目录链接或已验证的空间映射，按 ID 读回实际父页。输入只有工作项链接时可按准确名称「需求执行文档」只读定位并核实；有多个候选时让用户选定准确目标。目录配置按空间使用。

按 [Wiki 存取契约](references/wiki-storage.md) 运行只读 `PLAN`，新版传 `schema=4`。向用户展示**实施范围、实现方向、拟写正文、保存位置和工作项回链**，修订时展示准确差异。手动模式确认「按这版保存，稍后手动执行」。立即模式在同一确认中另外列出本次开工动作。批量 Bug 合并展示一次，逐个绑定各自预览。已有旧式草稿时展示原页归档、原位转正及版本差异。已有准确稿和目标的有效确认直接复用。

收到对该版的明确确认后调用 `SAVE`。确认后有实质变化时重新展示当前范围。SAVE 写已确认的主计划、子 Wiki 和关联评论。读回后返回主计划与记录页链接、版本及 `startCommand`，提示开工前确定本轮动作。手动执行到此结束。立即执行把读回的版本和当前已确认的启动选择交给执行技能，从 `START` 进入本次实施和交付。写入结果不明时用 `CHECK` 或 `READ` 核实后续接。

实施中出现后续需求、实际接口、落点或关键实现步骤变化时，按[同步实施正文](references/wiki-storage.md#同步实施正文)提交变更。授权回填时可先写待确认项，确认后修订原主计划，生效版本回填到原变更条目。仍有效的编号和执行回执继续沿用。
