# 收集需求与缺陷

[需求开发](../developing-requirement/SKILL.md)和 [Bug 修复](../fixing-bug/SKILL.md)共用本技能。按[模型路由](../../references/model-routing.md)处理只读调查和已授权的 Wiki 写入。

| 情形 | 输出模式及终点 |
| --- | --- |
| “先给我看”“只在会话评审”“不落盘”，或仅提供文字/原型供收集 | `SESSION`，在当前对话展示评审稿与待定事项 |
| 普通「开发需求／修复 Bug」、明确要求保存或从会话稿转存 | `TAPD_PLAN`，先评审，确认准确版本后保存并回链原条目，默认手动执行，返回链接即结束 |
| 明确要求按已保存的 TAPD Plan 开工 | 转交[执行 TAPD Plan](../executing-tapd-plan/SKILL.md)，使用正式页面 |

执行时机独立于输出方式，默认手动执行。用户明确立即执行时，把保存、开工以及各项目 Git/MR、提测、构建范围合并为本轮一次确认。两种启动时机遵循[执行上下文](../executing-tapd-plan/references/execution-context.md)。

两个输出模式使用同一份按项目排列的 Markdown。用户指定的模式优先。收集阶段只读业务系统和源码。历史 Task、仓库里的旧计划可作为范围证据，项目编号 P 和功能编号 F 都是页内索引。开发分支的创建、源码修改及交付留给执行阶段。

## 一、先确定做什么、在哪做、怎么做

1. 有工作项时用 TAPD MCP 按空间和完整 ID 读取准确的 Story 或 Bug，核对正文、相关附件、PRD、评论和必要原型。Bug 取复现入口、触发条件、实际和期望行为，核对既有修复、测试反馈及原始分支。按[工具路由](../../references/tool-routing.md)复用原型页面。
2. 用 [workspace-project-knowledge](../workspace-project-knowledge/SKILL.md) 核对真实项目、子目录、仓库与项目规范。读绑定基线下的相关代码、接口契约和同类实现。为每个必要仓库确认工作位置、分支动作、基准 ref 与提交。一个 Bug 跨仓时保留完整范围。多个 Bug 按用户顺序分别确定归属和修复面，共用分支的每页都列前置 Bug ID/链接、放行条件、首次创建者和后项的复用动作。
3. **把实现方向放进确定清单。** 按 P → M → F 逐项展示需求／复现依据、已观察到的现状、本轮要改的行为、代码入口、方案与理由、排除项和验收。标明谁先提供数据，谁负责消费。对尚未决定的业务问题写清取舍与影响，能由代码或契约查证的由 Agent 先查。让用户能在写入前改范围、改方案、改交付终点。
4. 在每个 P 下登记 D。API 写 method/path、输入、返回映射和业务口径。API Key 等配置写配置项、环境、注入位置和访问验证情况，密钥值保留在原凭据系统。路由参数和组件 props 在 F 的输入输出里定位到提供方。跨项目共用一条 D，所有消费点引用同一编号。按[外部依赖规则](../../references/external-data-dependencies.md)区分契约对齐、环境就绪与实际联调。已批准的 Mock 另遵循 [Mock 规范](../../references/mock-development.md)。
5. 完成每个所选 F 的可独立执行正文，使用下节格式。若当前目标所需的业务行为仍有分歧，先给出待决定事项。技术条件缺失时标出具体 D、受阻步骤和解除条件，可明确本轮可实施范围，保留后续依赖。

## 二、生成同一份确认稿和正式计划

按[执行计划格式](references/plan-format.md)、[需求示例](assets/example-plan.md)和[缺陷示例](assets/example-bug-plan.md)准备正文。分支、证据链接、契约和测试命令以本次核实结果填写。正式 Plan 使用 Story/Bug、项目与功能点绑定，范围、验证和交付都沿用这些编号。

- **项目 P** 给出准确仓库、原分支、基线、实现边界、适用的项目规则、验证命令和交付选择。项目头列数据对齐结论和受影响 F；团队能从这里定位每个缺口。
- **数据 D** 明确提供方、消费方、来源、字段或配置、口径、环境证据、缺口和补齐条件。
- **模块 M、功能 F** 给出职责、已确认规则、前置功能、输入／输出、关联 D、现有文件和符号。按顺序写清新增或修改的位置、如何处理数据、哪里更新状态及可观察产出。关键选择注明实际依据。新建文件标为拟新增。
- **交互 UI、测试 TC** 按功能展开适用的入口、触发、展示、失败反馈和回显。每个本轮功能有可独立检查的 TC，写固定输入、操作或真实命令、预期输出和通过条件。接口及纯后台功能直接验证调用或数据结果。
- **Bug 增量** 在对应 F 中写复现、故障定位、原因证据、修复位置和防回归场景。写前明确后续修复状态／处理人及唯一修复记录的时机。一个 Bug 只有一份覆盖各必要仓库的计划。

确认稿按用户已有指令、工作项及适用项目规则填好提测、构建、子智能体开发三项及其适用范围。普通开发/修复沿用测试交付的现有默认值，用户已给的仅开发、跳过构建或仅构建优先。开发者一次核对这些选择和准确目标。选择提测时明确目标分支和适用的提测 Wiki，选择构建时核实环境和具体 Job；实际发布或上线按相应阶段的授权推进。执行状态按「待执行、开发中、已上线」记录，初次保存为待执行。

## 三、按选择输出

**会话模式 SESSION**　直接在对话输出完整评审稿、各项目数据对齐结论、缺口和待决定事项，到此结束。用户可以继续修改并重新查看。纯文字或 PRD 也能在此模式收集，缺少工作项、目录、分支或凭据时如实标明。仅为在会话展示而收集时无需 Wiki 操作者、父目录或保存确认。用户随后指定保存时，复用同一稿，补齐正式页所需事实，按下面的流程给出准确保存预览。

**TAPD Plan 模式 TAPD_PLAN**　输出一个工作项的一份正式执行 Wiki。

目的地使用条目所在空间的执行文档父 Wiki。优先使用用户给定的目录链接或已验证的空间映射，按 ID 读回实际父页。输入只有工作项链接时可按准确名称「需求执行文档」只读定位并核实；有多个候选时让用户选定准确目标。目录配置按空间使用。

按 [Wiki 存取契约](references/wiki-storage.md) 运行只读 `PLAN`，校验拟写正文并取得准确的父页、版本、回链和指纹。向用户展示**本轮项目实现范围、实现方向、完整拟写正文（修订时可读回原版并展示准确差异）、保存位置和原工作项回链**，最后一次确认按用户所选时机表达。手动模式确认「按这版保存，稍后手动执行」，立即模式确认「按这版保存并立即执行上列实施和交付」。用户已经对这份准确稿发出相同指令时直接采用。批量 Bug 合并展示一次，逐个绑定各自预览。同一条目已有旧式草稿时，展示原页归档、原位转正及版本差异。已有同一份内容与目标的有效确认直接复用。

收到对该版的明确确认后才调用 `SAVE`。确认后有实质变化时重新展示受影响内容和完整当前范围。SAVE 只写本次确认的执行 Wiki 和关联评论。读回正式页、完整正文及原条目回链后返回链接和版本，给出带正式链接及版本的 startCommand，供新会话直接使用。手动执行到此结束。已明确确认并立即执行时，直接把读回的版本与当前指令交给执行技能，从 START 进入实施和所选交付。写入结果不明时用 `CHECK` 或 `READ` 核实已有结果再续接。
