# 按跨页路径验收

适用于下钻、返回、筛选回填、跨页权限或导出等连续操作。收集时逐页核对入口、角色、关键状态与现有实现，只有本轮需要改变或验收的行为进入原工作项的 P/M/F/UI/TC。优先选择一条会把错误带到其他页面的路径，例如「按服务商下钻 → 导出当前店铺 → 查看下载记录 → 返回重置」。[完整示例](../assets/example-report-flow.md)

## 开发前写出预期

在负责这条路径的 F 下使用已有 TC 编号。`验收前提` 写进入角色、初始数据和必要环境。`对照依据` 指到原型的具体页签或状态以及实际适用的项目规范、配方或同类实现。`跨页步骤` 用以下三列，每个动作引用一个已登记的 UI。返回、重置等动作可以重复引用相同 UI。接口契约沿用对应 F 的 D。

| 交互编号 | 操作 | 可观察结果 |
| --- | --- | --- |
| P1-M1-F1-UI1 | 点击服务商 A 的管辖门店数 | 切到店铺页签，筛选回填 A，从第一页读取 A 的门店 |
| P1-M1-F1-UI2 | 点击导出列表 | 导出请求使用刚才提交的日期、排序和 A 的 ID |

正式页 `PLAN` 或本地 `validate-plan.mjs` 的 JSON 输入可以传 `checkAcceptancePaths: true`。`acceptanceReview.paths` 给出每条路径的用例、前提、依据、功能点和有序步骤。`standaloneTestIds` 列出同范围内其余普通 TC 的编号，沿用文中的验收条件。工具检查表格、交互引用和步骤完整性。

## 按路径实施和复核

1. 开工前沿用收集阶段已核实的原型页面、角色和状态。缺少传值、返回效果等依据或原型有修订时，再看对应入口。已确认的差异写进原 UI、D 或 TC。
2. `START` 传 `checkAcceptancePaths: true`。选中路径起点或途经的功能点都能看到这条路径。`outsideSelection` 列出还需配合的未选功能点。本轮只实施已选功能，整条验收留待范围齐备。会话稿就地执行也可照步骤复核。
3. 先做通一条已就绪路径，再实现采用同一模式的其余页面。保留切换前的筛选与身份，在同一浏览器会话连续操作。UI 用同角色、同视口和同状态的原型与实页对照。功能用实际请求、响应或状态断言。采用 Zan 的项目再按生效版本和规则核对改动位置、状态所有者及事件流。
4. 把同一次操作的证据用于实际覆盖的 TC。例如路径已观察成功任务的文件地址，普通下载用例只需补验「生成中」行。开发者把实测交给同一位独立评审者，按原 TC 注明真实环境、模拟范围和缺口。

续修按[实现评审复用](../../../references/change-consistency.md#实现评审复用)处理。只改导出参数时，复核对应请求和实际受影响的下游结果，沿用仍适用的首屏截图。共用布局组件有变化时，沿引用查到实际受影响的页面，按各自的布局、角色和视口补验。
