# 执行计划正文

[需求示例](../assets/example-plan.md)与[Bug 示例](../assets/example-bug-plan.md)展示正式页的完整语法。会话稿沿用相同顺序，尚未决定的内容可以保留待确认。一个工作项保存一份可独立阅读的 Markdown。新会话拿到这份正文和授权的仓库访问即可确认第一步、输入、受阻点、验收与恢复位置。Wiki 中的代码链接指向实际 Git 仓库和研究时的提交，命令的工作目录相对仓库根说明。

## 工作项及执行选项

一级标题写准确标题。Story 用 `## 需求信息` 和八行字段表：需求链接、需求 ID、TAPD 需求状态、创建时间、执行状态、是否提测、是否构建、是否开启子智能体开发模式。Bug 用 `## 缺陷信息`，前三行对应缺陷链接、缺陷 ID、TAPD 缺陷状态。保留 TAPD 全长 ID 和可打开的条目链接。执行状态使用待执行、开发中、已上线。三个执行选项写本轮已确定的“是”或“否”；待决定项先在只读确认稿中解决。子智能体开发模式默认否，用户选择启用时展示可分工的功能及共享边界。

在表下写用户会观察到的交付结果、本轮范围、排除项、实现顺序及验收环境。外部依赖从所选功能的 D 引用去重汇总，并在这里指出影响本轮的具体数据、功能和阶段。需要的测试数据与验证步骤给出确定输入和预期值。Bug 在信息表下用加粗字段「复现与实际结果」「预期结果」「定位依据或调查步骤」「修复方向」「回归验收」记录故障。回归验收引用本轮 F 的完整 TC 编号。

## 项目、数据、模块、功能、交互和测试

标题遵循示例的 Markdown 层级和空格。一个项目命名空间内的 D 与 M 同级。完整编号用于跨项目及跨会话引用。增量修订保留同一条目的编号，增加内容使用新编号，移除或调序时保留可追溯性。

| 标题形式 | 应写内容 |
| --- | --- |
| `## P1 项目名` | 用「实施范围」概括本轮功能和边界，给出仓库／子项目、核实的新建或复用分支、工作位置、基准 ref 与 SHA、项目开发规范与参考代码、验证命令。选定交付时给出真实测试目标和 Job。项目头按本轮选中 F 的数据列出外部数据对齐结论及缺口、真实联调结果。 |
| `### P1-D1 数据或配置` | 哪个服务或模块提供、哪些模块消费、契约或配置依据。接口写方法、路径、使用字段的类型/映射、权限、时间和其他实际口径。配置写名称、环境、注入位置及验证状态。缺口给出阻塞阶段、受影响功能和可核实的补齐条件。 |
| `### P1-M1 业务模块` | 用「职责与依赖」写明模块职责和上下游，指出路由参数、组件 props 或调用所需的 D，并组织下属功能。 |
| `#### P1-M1-F1 功能名` | 每个 F 可独立验证。写范围依据、已存在行为、本轮增量和取舍、输入与输出、引用的 D 和前置 F、文件／方法、实施步骤。路由参数及 props 写明提供方、契约及消费方式；界面字段说明何时从哪里取数据。按本轮选定阶段判断能做哪些步骤。 |
| `##### P1-M1-F1-UI1 交互名` | 面向用户的入口、触发、状态切换、展示文案和数据效果，覆盖本轮实际涉及的加载、空态、失败、恢复等情形。纯服务功能在 F 中写调用方和返回行为。 |
| `##### P1-M1-F1-TC1 用例名` | 给定固定数据和环境、执行具体动作或仓库已有命令、预期得到什么结果。跨端用例注明需要的提供方产出、消费方版本及证据。 |

每个 P/D/F 的加粗字段名及格式见示例。F 的「本轮」填“纳入”或“后续”，数据依赖和前置功能用完整编号或“无”；无依赖的查证依据写在范围或输入输出。每条数据只定义一次，消费点保留自己的映射。对齐字段用“已对齐／未对齐／待核实／不适用”。本轮依赖未完成普查时保留待核实；有确切差异显示未全部对齐。所有适用依赖已有来源、字段及口径依据时显示全部对齐。全部经过审查且本轮无适用外部数据时如实说明原因。环境可用与实际联调另记，引用同一 D 的阻塞只影响它关联的步骤。

## 已选交付的项目字段

由收集者查项目规则、Git 与冻结的 Jenkins 配置，补到项目 P 头。保持顶部八行。仅本地实施时无需补测试交付字段。提测时在信息表下写 `- **提测 Wiki** 需要` 或「跳过」。只有确实要写入 TAPD 测试版本时才在同处写「登记测试版本」及其确切值。

| P 字段 | 填写方式 |
| --- | --- |
| 开发分支、交付目的 | 选中交付的 P 使用准确 feature/fixbug 原分支名，创建/复用、基准及工作位置另写。写明这次 Git 和构建服务于哪一项工作。 |
| 提测合并、提测目标分支 | 顶部选提测时，每个在范围内的 P 选择「提交推送并合并 MR」「仅推送并合并 MR」「创建或复用并合并 MR」「仅合并已有 MR」「仅核验已交付」或「跳过」。目标使用已核实的 dev/develop。操作文案覆盖提交/推送或创建及合并的具体范围。仅合并已有 MR 须核实对应 IID，CI/必需审批仍须通过。 |
| 冲突中转分支、冲突工作树 | 需要 MR 且允许自动处理冲突时，写出准确的 merge/* 分支和仓库内 .worktrees/ 下的相对路径，先展示 A→C→B 操作与目的。用户限定冲突交人工时中转分支填「未授权」。 |
| 测试构建 Job、构建项目、构建对象、构建来源、构建参数指纹 | 顶部选构建时，各 P 填准确 Job URL 或「跳过」。所选 Job 写实际项目/模块、发布对象、测试 ref 及冻结参数的 jenkinsParametersValueHash。注明测试环境、canary 通道及经验证的源码 SHA/版本策略，展示实际非敏感选项。凭据只记录配置引用。 |

[缺陷示例](../assets/example-bug-plan.md)包含一组可执行的测试交付选择。应用服务以测试部署执行；金丝雀发包需写 `构建类型=金丝雀发包`、包名、通道、计算版本和对应 Job，使用原有发布流程。同仓多 Job 复用 Git 回执，每个所选 Job 各自取得回执。跨项目总开关表示本轮至少一个项目选中，个别跳过的项目不触发该操作。若用户要先定范围而交付目标尚待核实，在信息表后用「交付待核实」写具体缺项、影响项目与解除条件，可先保存和实施就绪功能。

## 执行与证据

在最后一节 `## 执行记录` 前写明跨项目验收路径、命令、完成条件和中断恢复方法。当前用户确认的是哪些项目、分支、功能、拟写的 Wiki 及评论，应在确认时可见。用稳定输入、代码基线、契约和同一套断言判断重复运行的业务结果。切换会话或遇到不确定的写入时，先读回已发生的结果，核对版本与适用范围，再续接第一个未完成的就绪步骤。

最后一节用于追加真实进度、验收与交付证据。首次保存时留空。执行者按 [Wiki 存取](wiki-storage.md) 绑定工作项、确认版本、当前页面和事件标识写回。功能开发状态按实际回执展示待实施、开发中、已完成或已验证。阻塞说明具体依赖及解除条件。提测构建取得 Jenkins 队列回执时记录“构建任务已提交”及 Job 链接。
