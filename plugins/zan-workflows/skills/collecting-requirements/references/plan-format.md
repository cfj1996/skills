# 执行计划正文

[前端需求示例](../assets/example-frontend-plan.md)与[Bug 示例](../assets/example-bug-plan.md)展示正式页的完整语法。会话稿复用相同的实施正文和索引。一个工作项保存一份可独立阅读的 Markdown。新会话拿到这份正文和授权的仓库访问即可确认第一步、输入、受阻点、验收与恢复位置。Wiki 中的代码链接指向实际 Git 仓库和研究时的提交，命令的工作目录相对仓库根说明。

## 工作项信息

新版正式 Story Wiki 用 `## 需求信息`，表格保存需求链接、需求 ID 和创建时间。Bug 用 `## 缺陷信息`，对应保存缺陷链接、缺陷 ID 和创建时间。用准确标题、完整 TAPD ID 及可打开的条目链接。需要工作项当前状态时读取 TAPD，实施进展以文末真实回执为准。

开工会话确认交付与子智能体选择。会话稿可提示「确认后按本稿开工」或「保存到 TAPD 后用正式链接开工」。正式正文保存实施方案、依赖和验收。

在表下写用户会观察到的交付结果、本轮范围、排除项、实现顺序及验收环境。外部依赖从所选功能的 D 引用去重汇总，并在这里指出影响本轮的具体数据、功能和阶段。需要的测试数据与验证步骤给出确定输入和预期值。Bug 在信息表下用加粗字段「复现与实际结果」「预期结果」「定位依据或调查步骤」「修复方向」「回归验收」记录故障。回归验收引用本轮 F 的完整 TC 编号。

## 项目、数据、模块、功能、交互和测试

按项目、接口清单、其他外部依赖、模块与功能的顺序写。完整编号用于跨项目及跨会话引用。修订保留既有条目的编号，新增内容使用新编号。

| 标题形式 | 应写内容 |
| --- | --- |
| `## P1 项目名` | 用「实施范围」概括功能和边界，给出仓库／子项目、核实的新建或复用分支、工作位置、基准 ref 与 SHA、项目开发规范、验证命令与真实联调情况。`开发分支` 填完整分支名，分支动作和工作位置另写。 |
| `### 接口清单` | 用一张表定义本轮模块会使用的 API，每行一个项目级 D。 |
| `### P1-D1 外部配置` | 接口之外的外部依赖。给出提供方、配置项、环境、注入位置和访问验证，缺口关联受影响的功能与阶段。 |
| `### P1-M1 业务模块` | 用「职责与依赖」写明模块职责和上下游，指出路由参数、组件 props 或调用所需的 D，并组织下属功能。 |
| `#### P1-M1-F1 功能名` | 每个 F 可独立验证。写范围依据、现状、本轮改动、输入输出、文件／方法和步骤。`数据依赖` 填完整 D 编号，`前置功能` 填依赖的 F。步骤写调用触发、传值、映射和反馈。路由参数及 props 就近注明来源和值。 |
| `##### P1-M1-F1-UI1 交互名` | 面向用户的入口、触发、状态切换、展示文案和数据效果，覆盖本轮实际涉及的加载、空态、失败、恢复等情形。纯服务功能在 F 中写调用方和返回行为。 |
| `##### P1-M1-F1-TC1 用例名` | 给定固定数据和环境、执行具体动作或仓库已有命令、预期得到什么结果。跨端用例注明需要的提供方产出、消费方版本及证据。 |

每个 P/D/F 的加粗字段名及格式见示例。F 的「本轮」填「纳入」或「后续」，数据依赖和前置功能用完整编号或「无」。无依赖的查证依据写在范围或输入输出。项目对齐结论根据本轮 F 引用的 D 计算，全部完成审查且本轮无适用依赖时写「本轮无适用项」。已保存的[旧版跨项目计划](../assets/example-plan.md)可继续用原 D 标题读取和执行。

需要沿同一上下文验证多处交互时，TC 可采用[跨页步骤表](cross-page-acceptance.md)。表中的 UI 编号可以跨 F、跨模块，也可以多次回到同一个 UI。

## 接口清单写法

项目需要登记 API 时，在 M 之前放一张表。按消费模块顺序列出本轮所需调用，包括复用现有请求、接入新请求、拟 Mock、缺少字段或路径待核实的接口。只消费其他项目已登记的接口时，模块和功能直接引用原编号。

| 编号 | 接口 | 前端传 / 读 | 对齐 | 就绪与验证 | 本轮接入及缺口 | 依据 |
| --- | --- | --- | --- | --- | --- | --- |
| P1-D1 | 门店目录 · 查询候选 · `GET /api/stores` | 传 `regionId`，读 `id/name` | 已对齐 | 测试环境可用，联调待验 | 复用现有查询 | [契约示例](https://api.example.test/stores) |

- 接口列用「提供方 · 用途 · `METHOD /path`」。方法与路径尚无可核实依据时，第三项写「待确认」，对齐写「待核实」或已有缺失证据的「未对齐」。同一提供方、方法和路径登记一次，由所有消费 F 共用编号。
- 前端传 / 读只列实际消费的字段、必要类型和业务口径。非前端调用按实际消费方填。依据列链接正式契约、现有调用或缺失证据。请求、响应或枚举有差异时，精确到字段路径，写清受影响的 F 步骤或 TC、提供方和补齐条件。
- 对齐填「已对齐／未对齐／待核实／不适用」。环境、实际联调和本轮接入方式各自记录。契约齐全、服务未部署时可先接入已确认的请求和映射。拟 Mock 写待确认的场景，已批准时写模拟范围和真实接入条件，沿用[外部依赖](../../../references/external-data-dependencies.md)和 [Mock 规则](../../../references/mock-development.md)。
- 每个接口由消费功能引用。步骤只展开该功能实际调用时机、值的来源和界面消费。缺口只影响与之相连的步骤和验收。

## 启动前确认的交付信息

由启动会话按当前指令和项目规则核实 Git 及冻结的 Jenkins 配置。选中的操作随 `startup` 传入 [START](wiki-storage.md#立即和手动开工)。提测时明确提测 Wiki 是否需要，实际选择登记测试版本时传具体值。

| 本轮项目字段 | 确认内容 |
| --- | --- |
| 交付目的 | 仓库与原分支沿用正式计划，说明本次 Git 和构建要交付的工作。 |
| 提测合并、提测目标分支 | 对选中的 P 选择「提交推送并合并 MR」「仅推送并合并 MR」「创建或复用并合并 MR」「仅合并已有 MR」「仅核验已交付」或「跳过」。目标使用已核实的 dev/develop。仅合并已有 MR 时核实对应 IID、CI 和必需审批。 |
| 冲突中转分支、冲突工作树 | 需要 MR 且允许自动处理冲突时，写出准确的 merge/* 分支和仓库内 .worktrees/ 下的相对路径，先展示 A→C→B 操作与目的。用户限定冲突交人工时中转分支填「未授权」。 |
| 测试构建 Job、构建项目、构建对象、构建来源、构建参数指纹 | 对选中的 P 确认准确 Job URL、项目/模块、发布对象、测试 ref 及冻结参数的 jenkinsParametersValueHash。注明测试环境、canary 通道及源码版本策略。凭据沿用配置引用。 |

应用服务以测试部署执行。金丝雀发包明确 `构建类型=金丝雀发包`、包名、通道、计算版本和 Job。每个选中 Job 取得独立回执，同仓可复用已核实的 Git 回执。尚缺交付目标时，在会话说明缺项并按已确认的就绪范围推进。

## 执行与证据

在最后一节 `## 执行记录` 前写明跨项目验收路径、命令、完成条件和中断恢复方法。当前用户确认的是哪些项目、分支、功能、拟写的 Wiki 及评论，应在确认时可见。用稳定输入、代码基线、契约和同一套断言判断重复运行的业务结果。切换会话或遇到不确定的写入时，先读回已发生的结果，核对版本与适用范围，再续接第一个未完成的就绪步骤。

最后一节追加真实进度、验收与交付证据，首次保存时留空。执行者按[进度回填](wiki-storage.md#进度回填)记录本轮完成的功能、对应源码和验证来源。部分完成时写明仍需的步骤、具体阻塞及解除条件。提测构建取得 Jenkins 队列回执时记录“构建任务已提交”、Job 和可核验的队列身份。
