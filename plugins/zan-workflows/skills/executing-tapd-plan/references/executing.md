# 按已确认的执行 Wiki 开发

原会话确认并立即执行，或新会话按正式 Wiki 手动执行时，按[同一执行上下文](execution-context.md)恢复范围。仅保存结束在 Wiki。明确开工的当前指令引用已确认版本及其中具体的 Git/MR、提测和构建操作，按已选终点连续推进。

## 从链接还原范围

1. 从 Wiki URL 取空间与页面 ID，读取页内版本记录里的工作项类型、完整 ID 和父目录。若给的是工作项链接，则用“需求开发执行文档”定位 Story 执行页，用“Bug 修复执行文档”定位 Bug 执行页。按目录配置、原工作项回链和版本确认记录核对实际归属。同名 Story 或 Bug 按各自的 ID 定位。
2. 按 [Wiki 存取契约](../../collecting-requirements/references/wiki-storage.md) 用正式 Wiki 链接调用 `READ`，也可用准确空间、`storyId` 或 `bugId`、目录读回。要求返回 `CONFIRMED`，核对原链接、实际工作项、唯一回链、正式页 ID，以及工作项确认评论 `approvalCommentId` 绑定的版本和 `approvalFingerprint`。首次保存时同一条工作项评论可同时承载回链和版本确认，修订后读取最新版本的确认评论。归档页、复制的 Markdown、其他工作项同名页或提测 Wiki 都不能作为开工入口。`READ` 已用 [Markdown 校验器](../../collecting-requirements/scripts/validate-plan.mjs) 检查索引、父子关系与引用。执行记录中的文字不参与决定范围。
3. 从正式正文选择本轮授权的 P/M/F、关联的项目级 D、UI/TC、实施顺序、依赖和跨项目验收。用户限定某个 F 时，只核验前置产物，额外需要开发的前置 F 必须已有授权。用户仅要求评审、展示或重新确认时，返回只读结果。
4. 用各 P 固定的仓库地址、分支动作、基线 ref/SHA、入口文件或符号及规范来源，读回当前 Git 根目录、origin、HEAD、refs、工作区差异与项目规则。对照 D 的依据核实当期契约、配置及环境。记录写入前基线，续接时按下节核对已完成的效果。
5. 用最新需求、接口契约及实际源码核对已保存的实施正文。发现正文有差异时按下节同步，标出受影响的 F/TC、可继续的范围与解除条件。

## 新会话从哪里继续

读正式 Wiki 的确认版和「执行与变更记录」子页。由 `READ/START` 的 `executionRecord.progress` 定位 Git、评审和交付回执，必要时只读查原会话。尚待迁移的现行计划从原页恢复，旧式计划沿用其历史读取契约。逐仓、逐功能、逐已选 Job 核对当前事实。`START.next` 表示本轮选定的交付终点，续接位置按下表判定。

| 核实到的事实 | 续接位置 |
| --- | --- |
| 已确认计划、已建分支或只完成部分功能 | 沿用原分支和已完成内容，继续首个未完成且前提已就绪的功能。 |
| 实现已有，仍缺验收结果或独立评审 | 进入开发收尾，按缺口补验或补审。逐个核对仍适用的原验收结果。 |
| 所选功能的实施、自测、独立评审与必要联验均有有效回执 | 本轮开发已完成。仅开发时汇报；当前授权涵盖提测时直接进入交付预检。 |
| 已有提交、推送或 MR | 按原仓库、源 SHA、目标分支和 MR 核对。已推送的继续原 MR，已合并且包含已审源码的继续下一项交付。冲突或人工合并等待沿用原 MR。 |
| 已选 Job 的队列已受理，且匹配交付 SHA、Job 和参数 | 保留该次构建结果。其余已选操作完成后，继续所需的 Wiki、回链或登记。 |
| 本轮所选 Git、构建、Wiki、回链和登记的适用门禁均已满足 | 汇报现有结果。 |

旧结论逐项按本轮功能、验收条件和实际代码内容比对。仅更新可确定的提交 SHA 时，核实差异和相关依赖后复用原证据。真实变化只补受影响的功能、用例和评审。上次写入结果不明时，先查原 MR、队列、页面或登记的实际结果。查不清就保留具体阻塞。已核实的效果与本轮写入授权分别核对，授权覆盖就继续，缺少实质选择时只补该项。

## 同步需求和实现变更

1. 后续用户要求、PRD、接口或源码改变了需求、验收或实施方案时，更新当前执行文档。包括功能增减、接口或数据源替换、复用方案改变、变更落点和关键步骤调整。即使业务目标一致，实际实现与计划方案不同也要修订受影响的正文。
2. 从最新读回的主计划修改涉及的 P/M/F、D、落点、步骤与 TC，写清变化依据和验收影响。已授权回填时用 `CHANGE` 登记确切的待确认变更。已经明确确认的差异和写入目标直接复用，需补充授权时只展示变更部分及其影响。
3. 正式页按[同页修订](../../collecting-requirements/references/wiki-storage.md#同步实施正文)保存并读回新版本，从记录子页核对本次变更的确认和生效凭证。用新版和仍有效的本轮选择生成新的 `START` 上下文，只刷新失效的验证和评审。只调整提测、构建或子智能体选择时，开工上下文使用本次选择。按会话确认稿直接实施时，就地更新实际使用的确认稿。
4. 完成开发评审和准备提测前，对照最终差异再核对正文，覆盖已确认的人工改动。受影响步骤以已读回的新版为准，独立且仍获准的工作可继续。屏蔽写入或发生并发冲突时，保留变更预览和已有回执，并报告待同步的部分。

## 按工作项进入实施

**Story。** 本技能按下面的 P/M/F/UI/TC 主持实施。功能引用的项目级 D 来自接口清单行或独立 D 小节。新 Wiki 入口不创建 TAPD Task，不要求项目仓库另存计划。已有 Task 仅限定用户选中的功能范围，按既有工作项只读核对。

**Bug。** 将已核实的 Bug、执行 Wiki 确认版本、复现/预期、原因及定位依据、全量 P 与 F/TC、各项目固定分支和本轮授权，交给 [implementing-work](../../implementing-work/SKILL.md)。根据真实的仓库、分支及 Bug 事实恢复或补齐 [TapdWorkDefinition](../../preparing-work/SKILL.md)。同一 Bug 多仓一次传入全部 `work_definitions`。从本节进入原实施流程一次，由它负责各项目的源码、验证、独立评审和一个完整 Bug 记录。下文的实现、验收与回填写入同一轮结果。

若 P 声明了共用分支的前置 Bug，先从前置工作项的回链读取正式页，核实它在同一仓库、同一分支的创建或复用回执，以及已选 IMPLEMENT/SUBMIT 终点要求的评审或交付结果。证据齐全的后项按 USE_EXISTING 复用实际 ref。前项仍在开发时列出缺少的终点回执，在当前 Bug 的分支操作、状态/处理人更新和源码写入前等待。

1. 首次修改任何仓库的源码前，按[修复状态与处理人](../../implementing-work/references/bug-repair-owner.md)刷新 Bug 状态、处理人、工作流、修复账号及空间成员证据。`WRITE_ACTIVE` 需有精确的本轮授权，一次 `update_bug` 同时写入状态和 `current_owner`，准确读回两项后所有仓库共用同一回执。`NO_CHANGE` 核实状态和处理人均已匹配。待测试的 `CONTINUE` 使用 `SKIPPED_ALREADY_WAITING_TEST`，沿用当前处理人。读回不全则停止，保留实际效果。Story 跳过本步骤。
2. 在本轮开工前核对选定终点、执行 Wiki 中展示的 Bug 操作与实际用户授权。仅有保存确认、旧页面中的同意文字或开工前置条件漂移时，先解决缺少的精确授权。多仓复用同一个状态回执；如仅调查、仅改一个 F 或缺前置依赖，可以记录实际进展，发布与交付仍要求完整修复范围。
3. 每仓及跨仓都验收后，按[单条修复记录](../../implementing-work/references/bug-repair-record.md)汇总一份已独立评审的完整草稿，绑定该 Bug、账号、当前差异和验收。仅实施终点 `IMPLEMENT` 由原流程在最终评审通过后发表或复用一条记录，核对评论 ID、作者、准确 Bug 和实际 HTML 指纹。提测终点 `SUBMIT` 先交接这份草稿，由提测端在 Git、所选构建和适用提测 Wiki/回链完成后发表或复用，且在待测试登记前准确读回。执行文档回链、确认记录、进度事件、提测 Wiki 回链及 Bug 修复记录分别核验。

## 逐项实现和验证

- 选用[按跨页路径验收](../../collecting-requirements/references/cross-page-acceptance.md)时，`START` 传 `checkAcceptancePaths: true`。主开发先做通代表路径，对照 `standaloneTestIds` 补验路径尚未覆盖的状态。局部开工参考 `outsideSelection`，只实施已选功能。
- 在写入边界核对实际分支、基线和本轮开工授权。创建或切换分支遵守项目 Git 规则，并读回真实分支。保护既有未提交改动；遇到与选中 F 重叠且无法区分归属的修改时，暂停该范围。
- 按计划顺序执行每个就绪 F。在指定文件/符号复用 P 所列的组件、API 封装和项目规范，对应 UI 输入、触发动作、展示结果以及 D 字段映射。接口鉴权使用约定的配置引用，Wiki、测试输出和执行记录只保留引用和验证结果。
- 在开始依赖步骤前核实提供方的实际输出。契约已对齐、环境可用和真实联调通过是三个独立事实。按 [外部数据](../../../references/external-data-dependencies.md) 和 [Mock 规则](../../../references/mock-development.md) 处理阻塞；只有已确认的模拟范围可先开发，模拟结果只覆盖相应 TC。跨项目等待的功能保留在原索引下。
- 主代理默认依序实现。本轮启动明确开启子智能体开发时按 [多任务实施](../../implementing-work/references/parallel-execution.md) 派发已就绪且文件不冲突的 F，由主代理持有分支和共享资源、核实前置产物。独立只读评审沿用原规则，用户明确禁止所有子智能体时如实记录独立评审缺失。
- 对照所选 F 的每个 TC，用已有实测覆盖相同前提和预期，补跑剩余步骤。在原执行记录中引用实际动作、数据或环境、观察结果及未验项。跨仓 TC 核对各方在同一场景下的实际表现。参照[本地验证](../../../references/local-verification.md)选择项目命令和预算，按实际情况注明失败、超时或仅模拟。
- 对 START 返回的 `visualTests`，打开各自真实入口，按用例指定角色、窗口和组件状态对照已确认的参考，记录截图或录屏和逐项结果。共享组件变化覆盖所有受影响的已选入口。实际布局变化缺少视觉用例时，先按[同页修订](#同步需求和实现变更)补计划。

## 开发收尾

停止相关写入后，核对每个仓库从基线到当前的完整待交付差异及未提交内容指纹。按[实现评审复用](../../../references/change-consistency.md#实现评审复用)判断已有独立评审的覆盖。首次由一位[只读评审者](../../implementing-work/agents/change-reviewer.md)在同一轮 `POST_CHANGE_REVIEW` 核对 UI、功能和适用的 Zan 等项目规范。提供确认的 Wiki、各 F 的决策依据、diff、影响、TC 原始证据及跨项目验收。续修时聚焦变更影响和上轮遗留项。范围、实现设计和测试须同时通过。

独立评审按所选视觉 TC 核对参考、实际画面、观察结果及当前计划和代码版本。所有适用视觉用例都有当前版本的通过回执后给 `REVIEWED`。使用[视觉验收回执](../../collecting-requirements/references/wiki-storage.md#视觉验收回执)回填或交接。连续提测、逐项合并和测试构建会校验所选仓库的逐条回执。

用现有 [ReviewedChange 字段](../../implementing-work/references/contracts.md) 表达结果。以真实仓库根目录、origin、固定分支配对，保留每个项目及 F/UI/TC 的归属、基线、当前源码/差异、测试与独立评审依据。同仓多个 P 共用一份仓库 diff，分别保留各自验收。所选仓库和跨项目验收通过且实际方案与当前执行文档一致后返回 `REVIEWED`。仅部分完成时列出结果和缺口，仅开发的请求到评审和回执为止。

正式执行页绑定范围，实施回执绑定实际代码、测试及评审。Bug 的所有仓库还须共享同一份已审草稿或所选终点要求的真实记录回执。全部选中工作具备 `REVIEWED` 后，在会话报告「本轮开发完成」、范围及已知限制。仅开发到此结束，已选提测则立即继续。局部执行只报告选中的功能完成，必需仓库或联验有缺口时保留具体进度。继续使用原执行记录和开发回执。

## 将进度写回记录子页

开工授权涵盖回填时，按[进度回填契约](../../collecting-requirements/references/wiki-storage.md#进度回填)调用 `PROGRESS`。实际开工时记范围、执行人和终点。进入提测前回填开发收尾结果，拿到已核实的交付回执后再更新交付。阻塞、主动暂停或交接时记已完成事项及下一步。连续动作可以合并记一条，涉及已生效变更时引用其编号。直接执行旧式计划时沿用该版本的状态流转。

同一实际事件沿用同一回执键。并发编辑、超时或返回不明时先读回该事件、最新版本和执行依据。已存在则复用，仍不明确则报告缺口。读回成功后才报告已写回。技术步骤、数据契约、分支或验收的实质修改走计划修订。

## 交给提测

本轮执行上下文覆盖提测时，自动向 [submitting-for-test](../../submitting-for-test/SKILL.md) 提供已核实的工作项和已评审仓库集合。新会话先读正式页、独立确认记录和开发回执，再核对当前源码、测试与独立评审，补取失效或缺失的证据。先看 START 返回的 workflow。CONTINUOUS_SUBMIT 将 tapdPlan 原样传给连续提测 PLAN；DELIVERY_STEPS 按 gitProjects 逐仓交付、按 buildProjects 逐 Job 构建，再办理整项 Wiki/登记；RELEASE_ONLY 只跑所选构建。历史清单或当期缺项走 MATCH_CHECKLIST，只核实当前所需字段。交付预检通过后，复用同一开工指令直接 EXECUTE。已确认的测试构建和合并不另行向用户询问。

- 按仓库交接所选 P/F/TC、原始分支/源码 SHA、完整差异、独立评审和跨仓验收。Story 使用真实需求身份，`registration.entryType=stories`、`statusAction=NONE`、`linkTaskIds=[]`。Bug 使用真实缺陷身份，`registration.entryType=bug`、`statusAction=WAITING_TEST`、`linkTaskIds=[]`，携带完整已审 `repairRecord`；已有记录以 `previousRecord` 钉住原评论 ID、作者和实际 HTML 指纹复用。登记前按原政策核对 `te`，缺省时使用 `reporter`。同一 Bug 只登记一次。
- STANDARD 提测单独生成或复用该工作项的提测 Wiki。按所选项目核实测试目标、构建选择及 Mock 的单独授权。提交操作由原提测流程预览、验证并读回。
- 根据真实交付回执分别记录提测、构建和上线结果。Jenkins 队列接受后记为构建已提交。[上线流程](../../going-live/SKILL.md)实际完成后，记录各项目可核验的上线回执。
