# 一次确认覆盖选定的执行终点

「立即执行」和「手动执行」只决定何时开工。两者都按本轮指令引用的同一份已确认计划，实施、验收、评审并自动推进已选操作。

| 当前指令 | 行为 |
| --- | --- |
| 只看、仅保存、单独贴链接 | 展示或保存后结束。默认手动执行。 |
| 确认这版并立即执行 | 在一次确认中展示并绑定保存、实施和所选交付。保存并读回后在本会话开工。已经确认的会话稿且用户明确就地执行时，两个主入口可直接消费同一稿及其具体操作，不强制转存。 |
| 在新会话手动「执行／继续这份 Plan」 | 按[续接位置](executing.md#新会话从哪里继续)恢复已完成效果。用当前指令及它引用的明确操作确定本次终点，从最早未完成且就绪的动作继续。 |
| 本次仅开发、先让我检查、提测不构建、只构建 | 按本轮指令选择终点。仅开发停在验证和评审。只构建使用本次确认的 Job 和 ref。目标变化时展示实际差异。 |

## 开工时如何衔接

正式稿固定仓库、工作位置、分支动作、基准和原开发分支。启动前确认本轮 Git 操作、实际测试分支、Job、目的及适用的提测 Wiki。Bug 同时核实修复账号、状态和单条记录的发表时机。此处确认的选择随本次上下文交给执行器。

明确动作后调用只读 `START`。立即执行传 `startMode=IMMEDIATE` 及 SAVE/READ 取得的 revision、approvalFingerprint。手动执行传 `startMode=MANUAL` 和 Wiki 链接，用户指定版本时固定预期版本。两者都使用当前开工指令确认的 `startup`，并返回交付执行器所需的 `tapdPlan`。当前会话里的明确指令和准确目标仍是执行授权的依据。

`startup` 必填 `submit` 与 `build` 两个布尔值。提测时使用 `testWiki: "需要"` 或 `"跳过"`，选中登记时传 `testVersion`。`projects` 用已选的 P 编号作键，值填写[实际交付字段](../../collecting-requirements/references/plan-format.md#启动前确认的交付信息)。确切仓库与开发分支从正式页读取。仅指定少数项目作为交付目标时只传那些项目。明确启用子智能体时传 `parallelDevelopment: true`。

```json
{
  "submit": true,
  "build": false,
  "testWiki": "跳过",
  "projects": {
    "P1": {
      "交付目的": "将门店筛选修复交付测试",
      "提测合并": "提交推送并合并 MR",
      "提测目标分支": "develop"
    }
  }
}
```

选构建时在相应 P 中提供 Job URL、构建项目、构建对象、构建来源和构建参数指纹。明确「仅构建」用 `limit=BUILD_ONLY`，`IMPLEMENT_ONLY` 和 `NO_BUILD` 可收窄已选动作。后续读回使用 START 返回的完整 `tapdPlan` 和启动指纹。

开工参数支持 `selectedProjects`、`selectedModules`、`selectedFeatures`，值均为准确编号的非空数组。例如「只做 P2」传 `{"selectedProjects":["P2"]}`，「只做 P2 中的这项功能」传 `{"selectedFeatures":["P2-M1-F1"]}`。同时传入时取交集，只能选择本版纳入的功能。START 把实际所选 F 固定进 `tapdPlan`，其余项目的分支、Job、数据缺口都不进入本轮交付。局部执行采用逐项 Git/Job 并回填所选功能；整项提测 Wiki、最终修复记录和待测试登记须恢复完整授权与全量证据。如果所选分支还承载未选功能，交付前必须验证当前差异仅含本轮选项，在 merge/release 的 `reviewedFeatures` 传入这些确切功能。无法隔离时仅开发已选项。

已选构建但缺少具体 Job 或必要参数时，先复核目标与授权。`next=NO_ACTION` 表示选定范围内没有对应动作。

`START.next` 指开发收尾后的交付动作。开发完成以已选范围的 `REVIEWED` 和必要联验为据。

| 提测 | 构建 | 开发验证、独立评审通过后的终点 |
| --- | --- | --- |
| 否 | 否 | 返回代码、验证和评审结果 |
| 是 | 否 | 按已选仓库合并或验证已交付，处理选定 Wiki 和 TAPD 登记，跳过 Jenkins |
| 是 | 是 | 自动推进已选 Git/MR、测试构建、Wiki 与登记，各项目沿用自己的目标和 Job。START 返回的 separateBuilds 由 release 单独办理，整体完成需全部所选构建的回执 |
| 否 | 是 | 仅在已审源码和所选测试 ref 核实一致后走 release，保留实际构建回执 |

立即执行与新会话手动开工均属于 Plan 编排。向下游传当前开工指令、核准版本和已选操作。提测在内部核对只读 PLAN 和已有实现评审，匹配后直接 EXECUTE，按实际结果汇总。连续提测返回的 PREPARED 表示交付预检已就绪。测试构建以所选 Job 接受为已提交。单纯保存只授予保存操作。

项目、分支、目的、操作、Wiki 语义、环境、Job、通道及参数含义一致时，只读刷新当期证据。提交 SHA、经批准的合并结果、MR IID、实际构建队列及模板的确定性补全均按原约定派生。新风险或范围变化只展示差异，明确授权未覆盖时仅补该项。旧版 Wiki 先读原文及当前指令，已有准确字段可走原完整清单复用路径，缺项先自行查证。交付待核实按操作计算，唯独 Jenkins 参数待核实而本次明确不构建时，已核准的 Git、Wiki 和提测照常推进。手动接续固定当前版本和进度，已知写入结果不明时先查证。

## Git 分支与冲突

在当前会话把准确的仓库、A → B、目的、工作位置、提交/推送、创建或复用 MR 及合并意图作为执行摘要展示并核验。明确批准的启动动作直接推进。仅授权创建 MR 时停在创建。GitLab 的权限、CI、独立审批和保护分支规则仍按实际项目检查，缺合并权限时交给有权限人员并等待读回原 MR。

若初次确认包含条件式 A → C → B，要预先列出准确 C 名、本仓库相对工作树、从 B 建 C、仅在 C 解决冲突、推送 C、创建与合并 C → B 的 MR、必要验证及目的。真实冲突出现时复读原 MR、作者和 A/B，核实条件后直接走[冲突处理](../../../references/conflict-merge.md)。保留 A 作为业务分支，验证 A 和已评审的 C 均已包含在实际交付结果中，继续原提测与构建。业务取舍、新中转分支、其它仓库或他人的 MR 要按实际权限和差异处理。关闭旧 MR、清理分支及生产发布各自只在明确授权的范围内办理。

测试交付使用仓库实际提测分支，Git 交付时核对它与远端默认分支的角色。需要上线时，当前执行指令须明确覆盖原始 feature/fixbug → 实际默认分支、操作与目的及所选正式发布目标，满足[上线规则](../../going-live/SKILL.md)后复用该项授权。禁止从提测分支合入默认分支、直推保护分支或在 A 上改写历史消冲突。
