# Bug 溯源与修复记录

同一 Bug 的同一轮修复只发表一条完整记录，标题为 `【Bug 溯源与修复记录】`。
由 `fixing-bug` 的确定清单预览准确 Bug、评论账号、正文规则与写入时点并取得授权；
独立实施或提测时纳入该能力的同一份清单。Story/Task 不写此记录。
修复记录与提测 Wiki 链接是两条独立评论，不合并正文，也不相互替代。

## 内容与证据

保持以下格式，不增加项目分段、项目字段、修复人员或工时统计字段。
同一 Bug 涉及多个项目时，也只汇总一份原因、引入证据与修复方式；
必要时在现有字段的正文中说明因果关系或列出多个提交链接。
按该 Bug 的完整已确认修复范围记录，不把每个仓库当作独立修复轮次。

实际提交给 `create_comments` 的 `description` 使用 HTML 富文本：

```html
<p><strong>【Bug 溯源与修复记录】</strong></p>
<p><strong>产生原因：</strong>哪个改动或遗漏，在什么条件下导致了什么问题。</p>
<p><strong>引入人：</strong>有证据支持的原改动作者；无法确认则注明暂未确认。</p>
<p><strong>引入时间：</strong>原改动提交时间及其时区；无法确认则注明暂未确认。</p>
<p><strong>引入提交／MR：</strong>可核验的链接；无法确认则注明暂未确认。</p>
<p><strong>关联需求：</strong>已核实的需求链接；没有关联需求时删除整个段落。</p>
<p><strong>依据：</strong>原改动与故障之间的关系。</p>
<p><strong>修复方式：</strong></p>
<ul>
  <li><strong>改动：</strong>实际修复内容。</li>
  <li><strong>验证：</strong>已执行的验证及实际结果。</li>
  <li><strong>未验证项：</strong>尚未执行的检查及其局限；没有时省略本项。</li>
</ul>
```

TAPD 评论会折叠普通换行；不要把整份记录放进一个 `<p>` 后靠 `\n`
分行，也不要把 Markdown 的 `**字段名**` 或列表源码直接交给评论接口。
每个字段使用独立 `<p>`，标题和字段名使用 `<strong>`。字段内多项内容用
`<ul><li>…</li></ul>`；列表放在段落外，不在 `<p>` 内嵌套列表。
正文中的 `&`、`<`、`>` 等按文本转义，不能把代码片段当作 HTML；已核验的
HTTP(S) 提交、MR 和需求链接用 `<a href="…">…</a>`，属性值也须转义。

正式发表前，所有适用字段都须覆盖最终已评审代码和实际验证事实。
清单中的执行前预览可说明哪些事实待实施后填充，不能把该预览当作已发表记录。

- 查阅相关代码历史、原始 diff、MR、需求和复现结果，验证引入改动与
  故障之间的因果关系。`git blame` 只提供线索，最后修改人、合并人、
  当前处理人、本次修复人都不能直接等同于引入人。
- 引入时间记录原始改动的提交时间，并注明时区；不要使用本次修复时间
  或假定首次上线时间。记录中的链接必须经过核验，不猜测提交或 MR URL。
- 多人共同引入时据实列出各自证据；需求遗漏、历史逻辑或外部变化导致的
  问题按实际原因描述。证据不足的字段写“暂未确认”及缺口，不为归责
  猜测人员，也不因无法确认历史责任而阻止已明确范围的修复。
- 没有关联需求时删除整行，不写“无”或空占位；未核实的候选需求不作为
  已有关联写入。执行前预览无法定位原因时，明确写“待定位”；正式发表时
  按最终证据填充，仍未知则保留“暂未确认”及原因。

## 授权、草稿与写入时机

按 [确定与执行清单规范](../../../references/execution-checklist.md) 在一个
“TAPD 更新与修复记录”区块展示状态/处理人、评论账号、单条正文预览和实际终点。
记录标题下平铺字段，未知历史如实说明；原完整清单确认覆盖按最终证据填充这些字段，
不因换技能、技术事实补齐或派生 ID 再增加常规确认。缺少评论权限与其余本轮操作一并补齐。

源码修改前只处理已授权的 Bug 状态/处理人，不发表阶段评论。调查、修复、同范围返工和
补验期间，在内存中更新本轮记录草稿。评审次数、阶段切换或补验不构成新的修复轮次。
全部必要仓库及约定跨仓库验收的验证、独立评审通过后，统一核对草稿与当前源码/差异：

- `SUBMIT|GO_LIVE`：`implementing-work` 返回 `REVIEWED` 代码结果和已评审草稿，
  不发表修复记录，不要求未来评论 ID/读回。`submitting-for-test` 完成全部必要仓库的
  Git 包含关系和所选部署门禁、以及适用的 Wiki/独立回链门禁后，才写入或复用该记录并
  读回；记录核实后才能登记状态、处理人和测试版本。新测试构建沿用 `TRIGGER_ACCEPTED`，
  不等待构建完成。提测前复核发现问题时先返工、补验和刷新评审/草稿，不提前发表评论。
- `IMPLEMENT`：仅修复且本轮不提测，由 `implementing-work` 在全部验证/评审通过、
  确认本轮实施最终结束后，写入或复用这一条记录并读回，再返回最终结果。
  独立调用实施能力沿用此终点；本次明确要提测时须传递同一清单的 `delivery_mode`。

一个 Bug 跨仓库仍只汇总一份草稿/记录，全部结果共同引用；任何必要仓库未就绪都不发表。
后续只交付已结束实施的相同修复时，先核实已有记录是否仍完整覆盖当前事实，有效即复用。
已发表的本轮记录事实失效时，须通过已授权且可用的评论编辑能力更正并读回；能力缺失就
报告具体缺口并停止登记，不能追加第二条完整记录代替更正。新一轮记录须有明确的新修复
范围依据，不能从同一轮的返工或补验推导。月底统计仍按 Bug ID 归并。

## MCP 写入、查重与读回

1. 到达上述写入时点后，刷新当前源码/差异、验证和评审绑定；失效则返回相应检查，
   保留尚未发表的草稿。分页读取准确 `workspace_id`、`entry_id` 下 `entry_type=bug`
   的全部相关评论，核对账号、正文、时间及当前已确认修复范围，按语义查重。
   已有本轮完整记录且覆盖最终事实就复用准确 ID/读回；仅标题相同不足以复用。
2. 确认本轮记录尚未写入后，使用 `tapd-mcp.create_comments`，参数为准确
   `workspace_id` 和 `options={entry_type: "bug", entry_id, author, description}`。
   `author` 必须是已核实并获准的评论账号，正文仅为上述完整修复记录，不含 Wiki 回链。
   不使用 `bug_remark`，也不借此修改状态、人员或版本。
3. 立即通过 `get_comments` 读回准确 ID、所属 Bug、作者、完整正文和语义排版。
   忽略等价 HTML 标签/实体差异，核对字段分段、列表与链接目标；只收到创建成功响应
   不能宣称记录已核实。读回失败或格式不符时保留已知 ID 和实际效果，不自动重发。
   提测登记的执行输入携带 `prerequisites.repairRecord={commentId, author, bodySha256}`：
   ID 使用准确字符串，`bodySha256` 用共享 `sha256` 对这次读回的原始 `description`
   UTF-8 内容计算，不能用写入前草稿代替。登记执行器会再次按 ID 读取当前评论，核对
   空间、Bug、类型、账号、标题和正文指纹，再刷新 Bug 状态/人员并执行登记。
   只读登记 PLAN 不要求未来评论，实际读回后再为 EXECUTE 填入此证据。
4. 读取、创建或读回失败/未知时返回 `BLOCKED`，保留代码、评审及已完成交付结果，
   停止后续 TAPD 登记。续接先只读核实原评论，只补缺少的授权操作或读回，不重跑
   有效修复、交付或 Wiki 操作，也不盲目重复创建。评论 ID/读回只留在当前会话，
   不建立本地记录或额外编号。
