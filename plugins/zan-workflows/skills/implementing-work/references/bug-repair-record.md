# Bug 溯源与修复记录

由 `fixing-bug` 在确定清单中预览并取得授权，确认后的执行清单交 `implementing-work`
在原 Bug 评论下写入。独立调用 `implementing-work` 时复用同一规则。
只适用于 Bug；Story/Task 不写此记录。记录属于修复阶段，不依赖提测、
Wiki 或部署，不能由提测 Wiki 链接评论替代。

## 内容与证据

保持以下格式，不增加项目分段、项目字段、修复人员或工时统计字段。
同一 Bug 涉及多个项目时，也只汇总一份原因、引入证据与修复方式；
必要时在现有字段的正文中说明因果关系或列出多个提交链接。
按该 Bug 的完整已确认修复范围记录，不把每个仓库当作独立修复轮次。

实际提交给 `create_comments` 的 `description` 使用 HTML 富文本：

```html
<p><strong>【Bug 溯源与修复记录｜开始】</strong></p>
<p><strong>产生原因：</strong>哪个改动或遗漏，在什么条件下导致了什么问题。</p>
<p><strong>引入人：</strong>有证据支持的原改动作者；无法确认则注明暂未确认。</p>
<p><strong>引入时间：</strong>原改动提交时间及其时区；无法确认则注明暂未确认。</p>
<p><strong>引入提交／MR：</strong>可核验的链接；无法确认则注明暂未确认。</p>
<p><strong>关联需求：</strong>已核实的需求链接；没有关联需求时删除整个段落。</p>
<p><strong>依据：</strong>原改动与故障之间的关系。</p>
<p><strong>修复方式：</strong>待修复完成后补充。</p>
```

TAPD 评论会折叠普通换行；不要把整份记录放进一个 `<p>` 后靠 `\n`
分行，也不要把 Markdown 的 `**字段名**` 或列表源码直接交给评论接口。
每个字段使用独立 `<p>`，标题和字段名使用 `<strong>`。字段内多项内容用
`<ul><li>…</li></ul>`；列表放在段落外，不在 `<p>` 内嵌套列表。
正文中的 `&`、`<`、`>` 等按文本转义，不能把代码片段当作 HTML；已核验的
HTTP(S) 提交、MR 和需求链接用 `<a href="…">…</a>`，属性值也须转义。

完成时保留全部适用字段，将标题改为“完成”，按最终证据更新内容。
较长的“修复方式”按以下结构组织，仍属于同一个字段，不增加顶层字段：

```html
<p><strong>修复方式：</strong></p>
<ul>
  <li><strong>改动：</strong>实际修复内容；多项行为可分成多个条目。</li>
  <li><strong>验证：</strong>已执行的验证及实际结果，包括失败及其影响。</li>
  <li><strong>未验证项：</strong>尚未执行的检查及其局限；没有时省略本项。</li>
</ul>
```

- 查阅相关代码历史、原始 diff、MR、需求和复现结果，验证引入改动与
  故障之间的因果关系。`git blame` 只提供线索，最后修改人、合并人、
  当前处理人、本次修复人都不能直接等同于引入人。
- 引入时间记录原始改动的提交时间，并注明时区；不要使用本次修复时间
  或假定首次上线时间。记录中的链接必须经过核验，不猜测提交或 MR URL。
- 多人共同引入时据实列出各自证据；需求遗漏、历史逻辑或外部变化导致的
  问题按实际原因描述。证据不足的字段写“暂未确认”及缺口，不为归责
  猜测人员，也不因无法确认历史责任而阻止已明确范围的修复。
- 没有关联需求时删除整行，不写“无”或空占位；未核实的候选需求不作为
  已有关联写入。开始阶段无法定位原因时，明确写“待定位”，完成阶段
  按最终证据补充，仍未知则保留“暂未确认”及原因。

## 授权与执行位置

对话中的预览按 [确定与执行清单规范](../../../references/execution-checklist.md)
排版：TAPD 状态、处理人、评论账号、记录时点和下面的正文预览合并到
一个“TAPD 更新与修复记录”区块。记录标题下逐条列出字段，字段名加粗；
不要另起“开始评论预览”区块或展示原始 payload。实际写入保留相同的
字段内容与完整正文；排版不改变身份、授权、查重或读回要求。

1. 只读预检复用现有定位结果，展示准确 Bug、评论账号、开始评论预览，
   并说明验证/评审通过后会按同一格式补充完成评论。原修复确认一并授权
   这两次评论；不新增常规确认，不为填满历史字段扩大预检。
   尚未知的内容明确占位，开始时不承诺实际修复结果。
2. `implementing-work` 复用绑定同一 Bug、范围、评论账号和记录规则的授权。
   旧授权未包含评论时，先展示评论操作并取得补充授权，不扩大为其他
   TAPD 写权限。独立调用时纳入原实施授权，一并展示，不另起确认轮次。
3. 在状态/处理人门禁通过、初步诊断后，第一项业务源码修改前，查重并
   写入或复用开始评论，读回核对。`NO_CHANGE` 和已待测试的 `CONTINUE`
   只跳过状态/处理人写入，不跳过本记录，也不因此重置状态或处理人。
   多仓库复用同一开始评论 ID/正文及读回，各仓库不得重复发表开始评论。
4. 全部必要仓库的实施、验证和独立评审，以及约定的跨仓库验收通过后，将标题改为
   `【Bug 溯源与修复记录｜完成】`，其余字段保持同一格式；更新最终原因
   和证据，将“修复方式”替换为实际改动、验证结果及未验证项，追加一条
   完整的完成评论。原先结论被推翻时在对应字段明确更正及依据，保留开始
   评论。按证据完善这些已授权字段不另问确认；超出已确认修复范围仍须
   回到范围确认。未通过验证或评审不得写“完成”。
   先核对所有仓库的当前源码/差异与已审查版本一致，完成正文汇总各仓库已
   证实的修复及验证事实，只追加一份；某个仓库完成不能代替整个 Bug 完成。
5. 本轮实施须先核实开始记录，再核实完成记录，才能返回 Bug `REVIEWED`。
   仅补评论/恢复时，已核实的完整完成记录覆盖当前修复范围即可，不倒补
   开始评论或重跑修复。再由原流程决定是否进入提测。月底统计以同一 Bug
   的最新有效完成记录为准，开始记录不另算一条缺陷；多轮修复按 Bug ID
   归并并保留更正历史。
   任一仓库失败或中断时保留已完成范围与评论，整个 Bug 保持 BLOCKED；恢复
   只补缺失或失效的实施/验证/评审，不能先关闭已通过仓库或重发共享记录。

## MCP 写入、查重与读回

开发者检查后人工改动导致旧完成记录失效、但本轮只请求直接提测时，按
[直接提测的记录补充](../../submitting-for-test/references/direct-submission.md#人工改动后的-bug-完成记录)
处理：以当前差异/验证和拟更正正文完成独立评审，将准确追加/复用操作与
交付清单一并确认；先追加/复用并读回覆盖当前修复的完整完成记录，再恢复
`ReviewedChange` 并交付。不重开状态、不倒补开始、不重新实施，也不覆盖
历史评论。仍有效的完成记录继续复用，失败/未知写入保留实际效果并停止。

- 使用 `tapd-mcp.get_comments` 分页读取准确 `workspace_id`、`entry_id` 下
  `entry_type=bug` 的评论。先读完整相关记录，再依据标题、正文、创建时间
  及当前会话已确认的修复范围判断本轮进度；仅标题相同不足以复用。
- 使用 `tapd-mcp.create_comments`，参数为准确 `workspace_id`，以及
  `options={entry_type: "bug", entry_id, author, description}`。
  `author` 必须是已核实并在本次授权中展示的评论账号，不能以引入人的
  名义发表评论。正文为上述开始或完成记录；不使用 `bug_remark` 冒充流转
  评论，不调用 Wiki，也不借此修改状态、人员或版本。
- 每次创建后通过 `get_comments` 读回，核对返回评论 ID、所属 Bug、作者
  和完整正文，并检查标题、字段的分段及字段内列表是否保留。服务端可能
  规范化 HTML 标签或实体，应按解码后的字段内容、链接目标和语义分段核对，
  不要求 HTML 字节完全一致；整份记录仍在单个段落内且只靠普通换行分隔
  不算格式通过。只收到创建成功响应不能宣称记录完成。评论 ID 和读回证据
  仅在当前会话内保留，不建立本地记录文件或额外运行编号。
- 同一轮重试前刷新评论：已确认同阶段、同正文的记录就复用，不重复发表；
  开始已存在只补完成，完成已存在且覆盖当前范围则不再补开始。确有新的
  增量修复时按新一轮开始/完成留痕，不把历史完成记录当作本轮完成。
  历史记录归属不明时先只读核对，不猜测复用或重复创建。
- 查重比较正文时忽略等价的 HTML 排版差异；历史单段记录的事实仍可作为
  同轮记录证据，不因新格式重复发表。新写入按上述格式校验；若读回仅格式
  未通过，保留已创建评论 ID，报告格式待修正，不自动重发。既有评论的
  排版修正须有明确请求及可用的评论编辑能力，不能删除历史记录或追加一条
  相同事实的“完成”评论来代替编辑，也不能把本格式要求套到 Wiki Markdown。
- 评论读取、创建或读回失败时，保留底层错误与已完成效果。开始记录未
  核实前不改源码；完成记录未核实时报告“代码验证/评审已通过，完成评论
  待核实”，返回 `BLOCKED`，不进入提测，也不重复修复或自动回滚。恢复后
  先只读确认是否已写入，再仅补缺失阶段；已有代码/评审证据仍当前有效时
  复用，不盲目重发评论。
