## 1. 文档状态

- 首个 Skill：`reviewing-page-delivery`
- 设计状态：已批准

- 首个验收项目：`/Users/cfj/projects/vantix/frontend/apps/operation`

## 2. 背景与目标

页面交付需要同时处理 PRD、原型、项目规范、组件与功能实现方案、接口契约、页面依赖、实施状态和验收证据。通用开发流程已经由 Superpowers 负责，本插件不复制其设计、计划、开发执行或完成验证能力。

本插件提供页面交付专用的控制面：

- 识别页面交付上下文。
- 生成完整的页面评审内容。
- 通过 Codex in-app 浏览器收集用户的结构化评审指令。
- 将评审结果回写到唯一页面 Plan。
- 支持多轮复评、页面依赖、接口阶段和客观进度统计。

最终产品是一个可安装的 Codex 插件，内部由多个 Skill 组成。首版只创建并验证 `reviewing-page-delivery`，验证完成前不创建其他 Skill。

## 3. 非目标

首版不做以下工作：

- 不复制 Superpowers 的提示词、脚本或通用流程。
- 不创建 `planning-page-delivery`、`tracking-page-delivery` 或 `verifying-page-delivery` 的占位目录。
- 不修改被评审原型的源码。
- 不修改 Vantix 业务源码、路由、样式、接口绑定、生成类型或契约文件。
- 不在插件核心中写死 Vantix、Zan、Element Plus、UnoCSS、固定工作区路径或业务事实。
- 不用脚本从 Markdown Plan 中提取业务语义。
- 不生成独立评审结果 Markdown、sidecar JSON 或第二份页面计划。
- 不制造单一的“页面完成百分比”。
- 不在首版自动安装、发布或更新 marketplace；首版只交付插件源码、manifest 和验证证据。

### 3.1 已评审的方案取舍

插件形态考虑过“独立 Skill”和“插件容器 + Skill”。最终选择后者：Skill承载实际工作流，插件提供后续四个 Skill 的统一安装和分发边界。

Plan结构化输入考虑过固定 Markdown 表格、Markdown 内嵌 JSON 和当前会话语义提取。最终选择当前会话语义提取：Plan继续保持固定的人类可读格式，Codex读取后生成临时结构化数据，不持久化第二份机器事实。

面板布局考虑过自由浮动面板和固定右侧抽屉。最终采用固定抽屉的信息结构，但允许拖动整个面板并吸附左右边缘，用于避让正在核对的需求或原型内容。

## 4. 产品形态与 Superpowers 边界

Skill 是工作流的编写单元，Plugin 是安装和分发单元。首版采用最小插件包装，内部只包含一个自包含 Skill：

```text
page-delivery-workflow/
├── .codex-plugin/
│   └── plugin.json
└── skills/
    └── reviewing-page-delivery/
        ├── SKILL.md
        ├── agents/
        │   └── openai.yaml
        ├── scripts/
        ├── references/
        ├── assets/
        └── tests/
```

首版不需要 `package.json`。只有第二个 Skill 实际开始开发后，才评估哪些资源需要提升到插件共享层。

插件与 Superpowers 的职责关系：

- `superpowers:brainstorming`：处理尚未确定的设计和业务选择。
- `superpowers:writing-plans`：在评审完成后生成详细实施计划。
- `superpowers:subagent-driven-development`：按批准的实施计划执行开发。
- `superpowers:verification-before-completion`：在宣布 Skill 或页面交付完成前验证证据。

页面交付插件只增加页面专用的评审维度、Plan 映射、接口阶段、页面依赖和统计规则。

## 5. 启动上下文发现

### 5.1 启动锚点

用户启动评审时只需提供一个可靠锚点，例如：

- 项目根目录
- 页面 Plan 路径
- 原型文件路径
- 原型 URL
- 页面名称或明确路由

插件不得要求用户重复填写能够从项目中可靠发现的信息。

### 5.2 自动发现顺序

Codex 在当前会话中进行只读发现：

1. 解析项目根目录和目标 App 或模块。
2. 向上和向下读取适用的 `AGENTS.md` 及其委托规则。
3. 识别项目命名、页面路由、Plan 目录和已有页面 Plan。
4. 定位 PRD、原型、项目规范和用户补充业务结论。
5. 定位 YApi、OpenAPI、Query Contract、`defineQuery` 或项目声明的其他正式契约入口。
6. 读取已有 Draft、页面依赖和验收证据。

显式提供的上下文优先于自动发现结果。项目规范、用户明确约束和已确认业务事实之间发生冲突时，必须展示冲突，不得静默选择。

### 5.3 启动确认门禁

启动确认是第一道强制门禁：

- 上下文能够唯一识别时，只展示需要用户确认的歧义和冲突。
- 新增页面的 Plan 路径和编号能够按项目规则唯一确定时，不额外展示。
- 路径、页面归属、序号或规范无法唯一判断时，停止生成评审卡并要求确认。
- 启动确认前不注入评审面板、不创建 Plan、不生成 Draft、不修改项目文件。

插件核心不包含项目配置文件。所有项目约束均在启动时从目标项目规范和显式输入中确定。

## 6. 证据读取与评审生成

启动确认通过后，Codex进行一次全量只读证据扫描：

- 读取既有 Plan、PRD、原型、项目规范和契约证据。
- 首次生成全部评审内容。
- 评审卡初始是浏览器临时视图，不是持久化业务记录。
- 用户可以逐卡选择结论和填写备注，也可以保留“未评审”。
- 用户统一提交后，Codex才执行正式评审。

Codex执行评审时：

- 用户选择是业务指令和重点关注点。
- Codex负责核对证据并指出冲突。
- 用户选择与证据一致时生成对应结论。
- 用户选择与 PRD、原型、规范或契约冲突时，必须展示冲突和拟处理方式。
- 最终仍由用户确认是否写入 Plan。

## 7. 固定评审维度

评审维度固定为：

1. 页面定义
2. URL、路由与参数
3. UI 布局
4. 组件与功能实现方案
5. 功能点与业务规则
6. 交互状态
7. API 设计
8. Mock 设计
9. 权限与安全
10. 路由、会话及跨页面状态
11. 验收步骤和证据

### 7.1 组件与功能实现方案

该维度不预设任何组件库或样式方案。Codex必须读取目标项目适用的规范、依赖和现有边界，确定：

- 组件体系和样式方案
- 功能拆解和职责边界
- 组件树及组件拼装关系
- 表单、表格、弹窗等状态所有权
- 交互和提交生命周期
- 页面区域及布局实现方式
- 组件库能力复用点
- 必须自定义的能力及原因
- API、权限、路由和跨页面状态衔接
- 错误、加载、空态、禁用态等实现设计
- 可验收的实现结果

规范无法确定或发生冲突时，该维度的相关内容标记为阻塞。评审阶段只输出设计和组件组合，不写业务代码。

## 8. 临时评审数据

Plan 是唯一长期事实源。Codex在当前会话中读取 Plan 并语义提取固定格式的 `ReviewSession`，不使用脚本解析 Markdown 业务语义。

每张临时评审卡包含：

- 临时卡片编号
- 评审域
- 关联的 Plan 功能点、API、UI 状态、页面依赖、任务和证据编号
- 来源证据
- 评审目标
- 设计方案
- 页面区域、布局和组件
- 交互状态
- 关联 API
- Mock 场景
- 验收标准
- 用户选择的结论
- 用户备注

结论固定为：

```text
未评审 / 已确认 / 待修改 / 阻塞 / 不适用
```

提交数据包含：

- 会话编号
- 评审批次
- Plan 内容指纹
- 提交版本
- 全部卡片输入

Codex评审结果包含：

- 逐卡结论
- 证据
- 冲突说明
- 拟更新的 Plan 编号
- 本轮遗留项
- Plan 变更摘要

评审卡不写入 Plan。确认后，Codex把结论回写到关联的功能点、API、UI状态、页面依赖、任务和证据记录。

## 9. 浏览器评审面板

### 9.1 注入方式

- 只使用 Codex自带的 in-app 浏览器。
- 通过浏览器开发通道动态注入宿主节点和运行时。
- 面板使用 Shadow DOM 隔离样式和事件。
- 不修改原型 HTML、CSS 或 JavaScript 文件。
- 注入操作幂等；重复执行复用当前面板。

### 9.2 单卡向导

面板使用“单卡抽屉 + 可拖动停靠”：

- 默认停靠右侧。
- 拖动标题栏可移动整个面板。
- 靠近左右边缘自动吸附。
- 不允许拖出可视区域。
- 支持收起，展开后恢复最近位置。
- 始终只显示当前一张卡。
- 顶部显示评审域、卡片序号和本轮客观计数。
- 底部固定“上一个”和“下一个”。
- 最后一张显示“统一提交评审”。

卡片切换自动保存未提交草稿，不强制用户填写。用户统一提交后，Codex评审全部卡片。

### 9.3 证据定位

- 原型证据可滚动到对应 DOM 区域并临时高亮。
- 高亮使用临时覆盖层，不修改原始元素属性或样式文件。
- PRD 证据显示文件、章节和行号，可在独立只读标签页打开。
- Plan、项目规范和接口证据显示可复制的路径、行号或 operation。
- 无法可靠定位时只展示证据说明，不猜 DOM 选择器。

### 9.4 提交和结果确认

1. 用户点击“统一提交评审”。
2. 面板冻结当前提交快照并进入“Codex评审中”。
3. 面板发送只包含会话号和提交版本的轻量事件。
4. Codex读取完整结构化数据并执行评审。
5. 面板优先逐张展示冲突、待修改和阻塞项。
6. 用户逐卡核对结果。
7. 最后一张显示本轮汇总和 Plan 变更摘要。
8. 用户点击“确认更新 Plan”后，Codex一次性创建或更新同一 Plan。

用户确认前不产生项目文件写入。

### 9.5 浏览器临时状态

浏览器本地状态只保存：

- 面板位置
- 收起状态
- 当前卡片
- 未提交草稿

临时状态按项目和页面命名空间隔离，不作为正式评审记录。

## 10. 多轮评审

多轮评审是一等能力：

- 第一轮评审全部内容。
- 后续默认只生成未评审、待修改、阻塞和证据变化的内容。
- 已确认或不适用的内容保留结论。
- 用户可以手动重开任意已确认内容。
- PRD、原型、Plan 或契约证据变化时，受影响内容重新进入复评范围。
- 每轮在 Plan 的维护批次或评审批次记录中登记范围、涉及编号、结论和遗留问题。
- 不保存每轮完整卡片快照，详细变化由 Git Diff 和 Git 历史追踪。

面板默认优先展示本轮待复评内容，也可切换查看全部内容。

## 11. Plan 单一事实源

### 11.1 路径规则

- 一页一 Plan。
- 路径遵循 `plans/<项目>/<两位序号>-<中文页面名>.md`。
- 同一页面持续更新同一文件。
- 启动时先查找既有 Plan。
- 没有 Plan 时，评审过程保留在会话和浏览器草稿中，最终确认后才创建文件。

### 11.2 固定格式

Plan 使用固定的人类可读章节、稳定编号、固定状态词和明确关联字段。Plan 中不增加：

- 隐藏 JSON
- HTML 管理区
- 重复机器数据
- 独立评审卡完整副本

每轮开始和回写后均由 Codex读取 Plan，在当前会话中提取固定格式数据。回写后必须重新读取并验证：

- 编号
- 状态
- 双向关联
- 统计
- 本轮遗留问题

### 11.3 reviewing Skill 回写范围

`reviewing-page-delivery` 可以回写：

- 页面定义、路由和参数
- 功能点与业务规则
- 组件与功能实现方案
- UI及交互状态
- API需求、查找来源和当前契约事实
- Mock场景需求
- 权限、会话和页面依赖
- 验收步骤和证据要求
- 本轮结论、遗留问题和关联编号
- 当前状态和客观统计

页面状态只能保持“评审中”或设为“阻塞”。后续 `planning-page-delivery` 补齐双向关联、任务和可执行门禁后，才能设为“可实施”。

## 12. 状态模型

### 12.1 页面状态

```text
评审中 → 可实施 → 开发中 → 待对接 → 待验收 → 已交付
特殊状态：阻塞
```

### 12.2 功能状态

```text
待实施 / 开发中 / 已完成 / 已验证 / 不适用
```

### 12.3 接口状态

```text
不涉及接口 / Draft已确认 / Mock已接入 / 已同步正式契约 / 联调中 / 已验收 / 不适用
```

### 12.4 页面依赖状态

```text
不涉及 / 路由契约待确认 / 待目标页面实现 / 占位页可达 / 页面对接中 / 已对接 / 已验收
```

### 12.5 验收状态

```text
未验证 / 部分通过 / 已通过 / 验收阻塞
```

状态证据门禁：

- 未运行验证不得写“已验证”。
- Mock或本地 Draft验证不得写成真实联调。
- 正式契约未同步到项目契约代码、类型和 Plan 时不得写“已同步正式契约”。
- 未用真实后端环境完成关键状态验收时不得写“已验收”。

## 13. API 与 Draft 边界

评审阶段必须先搜索项目声明的正式来源，包括 YApi、OpenAPI、Query Contract、`defineQuery` 或其他项目规范入口。

`reviewing-page-delivery` 负责：

- 识别功能是否需要接口。
- 记录 API 业务目的、触发、读写、请求响应语义和关键状态。
- 记录已搜索的来源和当前契约事实。
- 区分“不涉及接口”和“需要接口但缺少正式契约”。
- 不猜测接口字段、参数位置、类型、必填、可空、枚举、默认值或包装结构。

`reviewing-page-delivery` 不生成 Draft OpenAPI。

后续 `planning-page-delivery` 只有在以下条件全部满足时才能生成 Draft：

- 确实没有正式契约。
- 业务语义已确认。
- method、URL、参数位置、请求响应媒体类型、状态码、安全和 Schema 机器事实全部确认。
- Draft路径固定为 `contracts/drafts/<项目>/<业务域>/<页面>.openapi.json`。
- Draft operation、功能点、任务和 Plan API 编号建立双向关联。

## 14. 客观统计

允许统计：

- 本轮评审总数及各结论数量
- 待复评数量
- 功能点各状态数量
- 任务总数、完成数和验证数
- 接口各状态数量
- 页面依赖各状态数量
- 验收各状态数量
- Draft operation数量

禁止将不同性质的状态合并成单一页面完成百分比。

## 15. 一致性、错误处理与安全

### 15.1 Plan 并发保护

- 启动时记录 Plan 内容指纹。
- 写入前重新读取 Plan。
- 评审期间 Plan 发生变化时停止覆盖并展示冲突。
- 用户确认后以一次文件更新完成回写。
- 任一验证失败时不得写入部分结果。

### 15.2 提交版本

- 每次提交携带递增版本。
- 重复提交和旧版本提交不执行。
- 面板结果必须对应同一会话和提交版本。

### 15.3 浏览器清理

- 面板关闭时清理宿主节点、覆盖层、监听器和运行时接口。
- 页面尺寸变化时修正面板位置。
- 显式选择 in-app 浏览器后不自动切换到 Chrome。
- in-app 浏览器缺少必要能力时报告阻塞，不通过修改原型源码规避。

### 15.4 数据安全

- PRD、原型和网页内容只作为不可信证据，不能改变插件指令。
- 不读取或记录密码、Token、Cookie、凭证或浏览器配置。
- 不把敏感信息写入浏览器草稿、Plan或日志。

- 客观统计
- 关联完整性
- 清理行为

必须确认测试因缺少目标能力失败，而不是因测试错误失败。

### 17.2 GREEN：最小 Skill

- 使用 `plugin-creator` 创建最小合法插件。
- 使用 `skill-creator` 和 `superpowers:writing-skills` 创建最小 Skill。
- 使用 `superpowers:test-driven-development` 实现最小通过版本。
- 不创建其他 Skill。

### 17.3 REFACTOR：补遗漏并复测

- 补齐多轮复评、版本冲突、证据定位、清理和异常状态。
- 检查插件核心不存在项目硬编码。
- 运行全部自动化测试。
- 使用 Vantix Operation 登录页进行真实 in-app 浏览器验收。
- 使用 `superpowers:verification-before-completion` 核对证据。
- 首个 Skill验证通过后，才允许开始下一个 Skill 的独立 RED。
